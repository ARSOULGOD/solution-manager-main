# `contracts/`

Machine-readable contracts — build inputs for three toolchains, not documentation. Design and rationale live
in [`../docs/design/dynamic-ui/`](../docs/design/dynamic-ui/). **How the Java backend consumes this tree
without hand-copied rules drifting** — which artifact is authoritative, who may read what, and what
`run-checks.sh --strict` owns vs `mvn verify` — is
[`../docs/design/common/contracts/backend-consumption.md`](../docs/design/common/contracts/backend-consumption.md)
(`BE-D10`/`BE-D11`, PROPOSED).

**Run everything:** `./run-checks.sh`  ·  first time: `pip3 install -r requirements.txt` **and** `npm install` in `view-models/` — exits non-zero on any failure. The Python gates need `jsonschema`, `referencing` and `PyYAML` ([`requirements.txt`](requirements.txt)); step 0 preflights them and **fails the run** if any is missing — unlike the Node steps, they are never skipped. Steps
7–9 (TypeScript typecheck, view-model fixture reproducibility, derived samples) need `view-models/node_modules` and are **skipped with a notice** until it exists (Node 20+).

**Steps 4–6 need a checkout of `file-mesh-ui`**, a separate repository that is not vendored here. They read its
schema dump, resolved as `$SM_FILEMESH_SQL` if set, otherwise `~/Work/Development/file-mesh-ui/database/file-mesh-schema.sql`.
Absent, the three are **skipped with a notice** naming the path they looked for — a missing sibling checkout is not
a contract defect. Point them at yours with:

```bash
SM_FILEMESH_SQL=/path/to/file-mesh-ui/database/file-mesh-schema.sql ./run-checks.sh
```

**`./run-checks.sh --strict` — use this in CI.** A skipped check becomes a failure. Without it, a skip is reported but still exits 0.

> ⚠️ **Why `--strict` matters.** Those three steps gate on `view-models/node_modules` being present, and the summary line used to print *"ALL CHECKS PASSED"*
> regardless — so a third of the suite could stop running while the runner still went green. That is `L7` ("a check that cannot fail is not a check") inside the
> check runner itself. The summary now always states how many checks did not run. **Anything that removes `view-models/node_modules` silently disarms those
> three checks** — npm-workspace hoisting from a root `package.json` is the concrete case, which is why `frontend/` is a standalone npm project and not a
> workspace member. Wire the engine in as a dependency only with `--strict` in place.

## Why the layout is four parts, not one

`contracts/` at the repo root is a pre-existing decision: four consumers — the Java backend, the React frontend,
the Go agent and both test suites — read the same schema, so it cannot live inside any one component folder.

The **split inside it** is newer, and corrects a mistake. The `project()` engine was originally dropped beside the
schema, which turned a normative single-writer folder into something you `npm install` into — mixing the contract,
executable code, Python tooling and derived test data at one level. `frontend/design.md` had offered two homes for
the engine (*"under `contracts/` or a `packages/view-models` path"*) and the first was taken silently.

It stays inside `contracts/` rather than moving to a root `packages/`, because it is a **shared build input
consumed by two toolchains** — the same reason the schema is here. But it is now its own package, and the schema
level holds nothing but the schema.

⚠️ **`validation/fixtures/*.package.json` is shared across both halves** — the Python gates validate them and the
TypeScript engine projects them. That cross-reference is deliberate; duplicating the packages would let the two
suites drift onto different inputs.

## Why the negative fixtures matter more than the positive ones

A package that validates proves the contract can express something. A package that is **rejected for the right
reason** proves the contract can refuse something. `negative/gate08-solution-specific-kind.json` is `REQ-001`
in executable form: the day someone adds a solution-specific `source.kind`, that fixture stops failing and CI
reports the contract has gone non-generic.

## What building these actually changed

The fixtures were built to test the contract, and they falsified three parts of it:

| Found | Consequence |
|---|---|
| **All 11** predicate-referenced File Mesh fields have no config path | `UI-D24` — without `virtual: true`, gate 4 rejects **every** File Mesh predicate. The contract could not express File Mesh applicability at all |
| Of 16 distinct buttons in 1,989 rows, exactly **one** is api-backed | `UI-D22` corrected — `action.kind` is `test-connection` + `manage-catalog-entry`. `browse-remote-path` and `refresh-catalog` had zero evidence and were dropped |
| `solace.enabled` is a **boolean** discriminator | Gate 6 widened from `enum` to `enum \| bool`. Corroborated by File Mesh's `{"CONFIG_JAVA_RUNTIME": true}` |

Two more findings needed no vocabulary change: `FILE_PROCESS_CONFIGURATION` (`FILETOFILE` vs `FILEEVENTS`,
differing in 58 of 65 FTP fields) is expressible as separate component types; and `CONFIGURATION_FIELD` is a
**label**, not a key — 57 collide, all resolved by `SECTION`+`PATH`, none irreducible.

⚠️ **One gap remains open** — see `design.md` §9. File Mesh's `SELECT_BROKER` populates `solace/java/msg-vpn`
and friends from a catalog entry; 42 rows in `COMP_SINK_SOLACE` are broker attributes with no config path of
their own. The contract can declare the selector and the target fields, but not the **population**.
