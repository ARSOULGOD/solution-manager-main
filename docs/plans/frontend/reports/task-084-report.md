## Design decisions, and why

1. **`layer`/`scope` are NOT part of `WidgetConfigV1`, even though the task text says "Save scope in v1: instance scope, layer shared."** `§7`'s own field list — the one the task itself quotes — has no such entry, for a real reason: the SAME document is what a saved widget, a Phase-2 shared URL (`DM-D19`) and a `DM-D15` alert seed all carry, and none of those three has a "layer". Layer is dashboard-PLACEMENT metadata, which is why it lives on `dashboardRepository.ts`'s `WidgetConfig` (the stored, dashboard-attached wrapper: `WidgetConfigV1 & {layer, hidden?}`) instead. `SaveWidgetDialog` states the fixed scope/layer as text; `ExplorePage`'s mutation is what actually attaches `layer: 'shared'` at the one place it's stored.

2. **`dashboardRepository.ts`'s placeholder `WidgetConfig` is retired, not kept alongside the real one.** It predates this task (task 033, bundled scaffolding) and was shaped just enough to prototype a dashboard grid before `§7` existed. Keeping both would be exactly the two-copies-that-can-drift pattern this codebase repeatedly calls out (`chartStateTags.ts`, `buildQuery.ts`'s own header) — and `FE-085` (`DashboardView`) explicitly depends on `084`, so shipping a widget type FE-085 would immediately need to replace anyway serves nobody. Scoped narrowly: only `WidgetConfig`'s shape and `saveWidget`'s correlation-id return type changed; `get`/`setLayout`/`hideDefault`/`resetDefaults` are untouched, and `DashboardDoc`'s own envelope (a flat `widgets[]` array) is untouched — the hidden-default representation stays FE-087's open item, not pre-empted here.

3. **Layer vocabulary corrected from task 033's `'package-baseline'`/`'operator'` to the CURRENT design's `'product-default'`/`'shared'`.** Design §12 and Conflict C7 both use the latter; task 033 predates that text. Since this task was already reconciling the type, using the stale vocabulary forward into new code would have been choosing to propagate a known-outdated term over the one FE-087 (which owns layer rendering) will actually build against.

4. **`SaveWidgetDialog` has no per-field editor beyond `title`.** Design §11.1 step 3 ("Customize mark, axes, legend, colors, thresholds, scale") names five things to edit and zero `FE-*` tasks that build controls for any of them. Rendering a read-only summary of what Explore already resolved — rather than a second set of controls with no wiring behind them — is the same "flagged, not silently decided" posture `ExplorePage.tsx`'s own header already sets for its missing mark toggle and `EntityTypeSelector`.

5. **No "create alert" code exists anywhere in this file, not even behind a caveat.** The task's own text is explicit: *"the simpler and safer choice is to omit it in v1"* — a stricter bar than design §2.2's general rule that a shown alert affordance must state it's seed-only. This task chooses "don't show it" over "show it with a caveat," and the file has zero alert-related imports, state, or copy to prove that isn't an oversight.

6. **`saveWidget` gained `postWithCorrelation` and a `{widget, correlationId}` return, every other `dashboardRepository` method is untouched.** Only this task's own flow (`ExplorePage`'s toast, `FE-D13`) needs a real correlation id; `get`/`setLayout`/`hideDefault`/`resetDefaults` have no live caller yet (no `DashboardView`), so widening them now would be speculative.

7. **`ExplorePage`'s save-success handler sets `savedRef.current = true` rather than calling `saveExploreDraft`/`discardExploreDraft` differently.** Task 083's own discard-on-unmount effect already reads a ref at unmount time; the minimal fix is flipping that ref once a save actually lands, not restructuring the effect. Task 083's report named this exact gap as "task 084's to build" — this closes it.

8. **`GET /dashboards/:id`'s two fixture widgets were reshaped, not left stale.** `HttpResponse.json(...)` isn't type-checked against `DashboardDoc`, so leaving the old shape would have compiled fine while being silently wrong forever. A light, hand-written update (not deep, realistic per-widget data) keeps the fixture honest without doing FE-085/086's job of building real dashboard content.

## Residuals (flagged, not silently decided)

1. **`migrations.ts` has no live call site.** Every widget this console creates starts at `CURRENT_WIDGET_SCHEMA_VERSION`; nothing reads a persisted widget back yet. The engine is real and fully tested against a synthetic `v1→v4` chain — task 086 (`DashboardGrid`) is where `too-new` first renders something on screen.
2. **`buildWidgetConfig`'s `options`/`axes`/`legend`/`series`/`thresholds` are all one hardcoded default**, because no styling editor is scheduled anywhere in the plan. `legend.maxHeightRows: 4` reuses `ChartRenderer.tsx`'s own `DEFAULT_LEGEND_MAX_HEIGHT_ROWS` (§7's one concrete example) rather than a second guess.
3. **`defaultDashboardId(instanceId)` and the `GET /dashboards/:id` fixture's per-widget content are both invented** (§16 Q15) — the contract has no dashboard-lookup route and no widget document shape. Both are flagged in source; the fixture is deliberately minimal, left for FE-085/086 to build out with real content once a dashboard actually renders.
4. **`hideDefault`/`resetDefaults`/`setLayout` still return `Promise<void>`/`DashboardDoc`** with no correlation id — untouched because nothing calls them yet. FE-087 (hide/restore/reset) is the natural place to decide whether they need the same `FE-D13` treatment `saveWidget` got here.
