## Design decisions, and why

1. **One `<table>` per series, not one union-timestamp grid.** Different series can legitimately have points at different instants — a gap is a *per-series* absence (§11.2 obligation 1) — so a shared-row grid needs a "no data at this instant" cell convention of its own. That is the same zero-fill-adjacent trap obligation 1 spends itself ruling out for the chart; a per-series table sidesteps it entirely; every row is a real, rendered point, nothing is synthesized to keep columns aligned.

2. **`chartStateTags.ts` is a new file, not reuse-via-import from `ChartRenderer.tsx`.** `ChartDataTable` needs task 074's state-label/tone map so the tooltip, legend and table show one vocabulary, not three. Importing it from `ChartRenderer.tsx` directly would be circular, since `ChartRenderer` renders `ChartDataTable`. Extracting to a third file is the standard fix and costs nothing — task 074's tokens, tones and labels are unchanged, only their file moved.

3. **`ChartDataTable` short-circuits on `!open` before computing anything.** `ChartRenderer`'s live-region announcement re-renders the whole component tree on every arrow-key press (state lives in `ChartRenderer`, so a keystroke re-renders its children including the always-mounted `ChartDataTable`). Without the guard, every keystroke would re-run `summarizeChart` and format every point of every series — for a 3000-point-per-series chart, that is real, needless work happening on a hidden dialog. Caught by the existing `ChartRenderer.test.tsx` fixtures once wired in: two of its fixtures use deliberately malformed multi-digit-minute timestamps (`2026-08-30T00:010:00Z` at `i=10`) that were never previously parsed by anything — they only ever fed a raw string into the ECharts data array — and `formatDateTime`'s `Intl.DateTimeFormat` threw on them once the table started eagerly formatting every point on every render. The guard fixes both the waste and the crash; the fixtures did not need touching, since a closed table has no reason to format a point it will never show.

4. **The cursor moves along the union of every series' timestamps, not one series' own.** §18 describes one shared "time axis" cursor with a separately-focused series — if the cursor only walked one series' points, switching the focused series (`↑`/`↓`) could silently orphan the cursor at an instant the newly-focused series has no point, which is exactly the ambiguity `↑`/`↓` vs. `←`/`→` being independent axes is meant to avoid. The union is time-sorted via lexical order on the ISO-8601 `Z`-suffixed strings — the same assumption `ChartRenderer.tsx`'s own tooltip formatter already relies on (task 074, decision 3), not a fresh one.

5. **The live region announces `"{series}, {timestamp}: {value}"`, formatted from `model.series` directly by exact timestamp match — not from an ECharts event.** Same reasoning task 074 already established for the tooltip (`buildTooltipRows`): looking up the focused series' own `points` array by the cursor's timestamp means a missing point reads `gap`, never blank, never a stale value left over from the previous cursor position. Reusing that lookup pattern here rather than wiring an ECharts `dispatchAction`/`highlight` event keeps the keyboard path fully decoupled from ECharts internals — consistent with how the whole test suite mocks `echarts.init` down to a bare `setOption`/`resize`/`dispose` stub and never exercises real ECharts event wiring.

6. **No visible on-canvas cursor indicator.** The chart already visually shows the pointed-at value via the mouse-driven tooltip (task 074); a keyboard-driven duplicate marker would be a second, un-synced visual affordance for a state that already has one. The `aria-live` announcement is the keyboard-only channel for the same information, not an additional visual one — matches §18's framing of the table (not a second visual layer) as "the mitigation," and keeps this task inside "closes the stated residual" rather than adding new chrome.

7. **A visible "Open data table" button, in addition to `Enter`.** §18 only specifies the *keyboard* interaction model; it doesn't say `Enter` is the only path to the table. A small always-visible button serving the identical trigger (`setTableOpen(true)`) costs nothing, and without it a mouse-only user has no way to reach "the tabular alternative for every chart" — the same acceptance-box line the keyboard path exists to satisfy. Kept deliberately minimal: one `Button` `variant="text"`, no new layout system.

8. **`role="application"`, not `role="img"`.** A `role="img"` chart with a non-native custom keyboard model (arrow keys reassigned away from their usual meaning, `Enter` doing something) is exactly the case ARIA's `application` role exists for — it tells assistive tech this region implements its own interaction model rather than relying on browse-mode navigation. The alternative (`role="img"` plus `tabIndex`) would leave a screen reader's browse-mode arrow keys fighting the same keys this task binds.

9. **No accessibility claim beyond what §18 states.** The file header records the residual honestly, per the task's own instruction: a canvas chart still fails some screen-reader chart-exploration heuristics; the keyboard cursor and the table are the stated mitigation, not a claim that the canvas itself became accessible.

## Residual / not done here
