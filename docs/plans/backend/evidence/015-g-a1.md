## M3: how the interrupted apply was settled (measured, not fixed) - a FINDING for the integrator

`AgentCommandCrashRecoveryIT:175` (`aRestartTheAgentRanButTheDataPlaneNeverHeardAckedRestartsTheContainerExactlyOnce`) asserts `RequestState.APPLIED` after
`resumeRunning`, with the agent's session live. On the production launcher with the real agent it is different. Run 2, times relative to the `kill -9` (DB clock):

| Observation | Run 2 | Run 1 |
|---|---|---|
| SM answers HTTP again | +4.1 s | +5.1 s |
| `ApplyStartupRecovery` sweep (launcher log) | +4.7 s (17:39:23.748): `resumed apply ... landed on APPLY_INDETERMINATE (ErrorClass[token=resume.state.unknown])` | +4.7 s (17:22:22.668), same line and token |
| the agent's new `agent_session` row (fencing epoch 2) opened | +9.9 s | +6.5 s |
| `apply_request` terminal | +34.3 s | +34.6 s |

`apply_request` after recovery: `state=INDETERMINATE_RESOLVED`, `resolved_by=sm-reconciler`, `resolution_outcome=applied`, `reconcile_class` empty. States seen by `observeApply`:
`APPLY_INDETERMINATE -> INDETERMINATE_RESOLVED`.

Reading: the startup recovery sweep ran 2 to 5 s BEFORE the agent had a session again, so it could not read the host and left the request `APPLY_INDETERMINATE`
(`resume.state.unknown`); roughly 30 s later the reconciler tick resolved it as `applied` (the read proved it). The outcome is correct and the container restarted exactly once.
The path is the reconciler's, not the IT's startup-recovery one. The log token is `resume.state.unknown`, not `agent.session.absent` (the latter does not appear in the launcher log of either run);
whether the sweep's agent read failed fast on an absent session or classified an unreadable state is for the owner of `AgentRuntimeAdapter` to say. P15-3 (plan section 11) leans on the IT as the
real-agent proof; the live behaviour is a different, slower, still-correct route. No product code was changed.

## Notes

- Persisted vs restart-observed hash: they are the keyed hash of the file bytes read back and are compared only with each other (`ConfigLadderView.java:10-13`); desired and rendered carry the stored content digest, a different value that nothing may compare with them. The earlier open item (4) is closed by that, and the new assertions check content: the Cache's `application.yml` holds each generation's `max-size`.
- Measured, not asserted: the session close after `revokeAgent` is seen by a host-side poll (5.0 s here: poll plus `docker exec psql` latency). The first pass's "3.4 s" and "2 raw samples each within 5 s of the apply" were not supported by that log (the metrics query had no time filter; the revoke closed in under a second by the row). Figures in this file are only those of `015-g-a1-run.log`.
- The "launcher log: no ERROR, one WARN" statement of the first pass was a manual read. Run 1's launcher log, read after the kill and restart (the restarted process only; the log is rewritten at each start), held one WARN (`mesh publishing disabled: sm.mesh.enabled=false`) and no ERROR; a manual read, not an assertion, and not repeated for run 2.
- The settle window after the interrupted apply is a poll on the observed condition (two agent telemetry reports after the apply was terminal, so a second restart would have happened inside it), not a fixed sleep. Negative windows after undeclare and revoke are polls on a positive observation (the agent's report; the agent's refusal line) followed by the assertion.
