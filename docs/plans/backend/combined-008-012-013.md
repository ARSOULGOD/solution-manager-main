merging, and so on. A task that finds it must edit a hot file it does not own in that wave stops and reports.

**Why this shape.** The contract surface (HF3) has **thirteen** writers across the three plans (four of them
description-only); at most three per wave, in a declared order, and the dependencies between them set it at six
waves. The `sm_data` slot (HF5) has five migrations and `InventoryService`
(HF7) has five writers; the waves give each a distinct owner per wave or a same-lane sequence. Plan 013's target chain
(T1.1 → T1.3 → T1.4 → T1.5) and its user chain (T2.1 → T3.1 → T3.2 → T4) are the critical path; plans 008 and 012 fill
the other lanes around them.

### The integration point of every wave

1. Each lane's tasks pass their own module verifies (each plan's commands).
2. **One Opus review for the wave** — one reviewer per lane, in parallel — and **one fix round**.
3. The integrator merges the lanes into the wave branch **in the hot-file order above**; each later writer rebases and
   re-runs its module build first. Migration numbers are re-checked against §5 before the merge.
4. **Full gate:** `mvn -o -f backend/pom.xml clean verify` (the whole reactor, offline); `./contracts/run-checks.sh
   --strict`; `python3 backend/scripts/check-frozen-migrations.py`; `python3 contracts/openapi/postman/check-postman.py`;
   the DDL replay when `sm_data` changed (`docs/design/backend/evidence/ddl-replay/`); `git diff --check`.
5. **The wave's live gates, one at a time** on the E2E host (HF12), each leaving the host's Cache working and recording
   before/after evidence outside the repo's coordinates rule; the most disruptive (L4, the Docker daemon stop) runs last
   and alone.
6. **Push** to `integration/dp-remote-demo`, fast-forward only. The next wave branches from that head.

**The defect L2 found: `ssh.docker.command.failed` on a container with no `HEALTHCHECK`.**
`SshjDockerTransport.inspectCommand` formats `{{if .State.Health}}…{{else}}not_declared{{end}}`. On the host's Docker
25.0.16 that template fails with "map has no entry for key Health" when the container declares no healthcheck, and the
command exits non-zero. Such a Cache cannot be inspected, so it cannot be declared, probed or applied. It also means the
`not_declared` branch the unit tests pin is unreachable on a real daemon. L2 passed only after the second container was
recreated with the first one's healthcheck. Fixed in `7ff85a42`: the template reads `{{if index .State "Health"}}`. The docker CLI first runs the template on the
typed struct, then falls back to the raw JSON map with `missingkey=error` (`docker/cli` v25.0.5 `inspector.go`), and
`index` yields nil for a missing key. The fix was measured with the full five-field string on a local Docker 28.5.1. A
container with no healthcheck gives `not_declared`, a healthy one gives `healthy`, a stopped one that has a healthcheck
gives `unhealthy` (stale), and a nonexistent name gives exit 1. On 28.5.1 the old `if` form and the `with` form both fail
for the no-healthcheck case. A unit test pins the shipped string, red first. **Re-measured on the host's Docker 25.0.16
(2026-10-09, `OR-133` (2))** with the full shipped string against throwaway containers. The results matched 28.5.1:
no healthcheck gives `not_declared` (rc 0), healthy gives `healthy`, stopped with a healthcheck gives `unhealthy`, and a
nonexistent name gives rc 1. The old string failed the no-healthcheck case with "map has no entry for key Health".
