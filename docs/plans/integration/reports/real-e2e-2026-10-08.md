Ran the actual production backend (`backend/local/sm-local.sh up`, real PostgreSQL, real Flyway

## Setup notes (for next time)

1. **`backend/local/sm-local.sh`'s `-nt` jar-freshness check is broken.** Maven's reproducible
   builds pin the jar's mtime to a fixed epoch (`Jan 1 2026`), so `"$jar" -nt
   "$STATE/app/.unpacked"` never sees a freshly rebuilt jar as newer than the previously unpacked
   classpath — a rebuild silently keeps serving the **old** unpacked classes. Symptom: `up` silently
   stops after "Phase 0 already applied" with no error, because `LocalSeed.java hash`'s `javac`
   step fails with "cannot find symbol" against a stale classpath (`MasterKeyRing`,
   `EnvironmentMasterKeyProvider`, `TargetConnectionSpec`, `TargetConnectionMain` were missing) and
   `set -e` exits the script with no message. **Fix:** `rm -rf backend/local/.state/app` before a
   rebuild, or fix the script's freshness check to not rely on mtime comparison against a
   reproducible-build artifact. Not fixed here — flagging for whoever owns `sm-local.sh`.
2. **The script's own trusted-origin (`http://localhost:$APP_PORT`) doesn't match the frontend dev
   server's real-backend origin (`https://localhost:5173`, HTTPS required by `vite.config.ts` once
   `VITE_USE_REAL_AUTH=true`).** Worked around by stopping the script-started launcher and
   restarting it by hand with `SM_GATEWAY_TRUSTED_ORIGINS_0=https://localhost:5173`. `vite.config.ts`
   also hardcoded its proxy target to `:8081`; added an `SM_LOCAL_BACKEND_TARGET` env override
   (one-line, additive, default unchanged) to point it at `sm-local.sh`'s `:8080` — **left uncommitted,
   pending your call on whether to keep it** (see below).

## Finding: `identity.superAdmin`/`role`/`organizationId` do not exist on the real wire — plan 001 scope, pre-dates this session

**Severity: high.** `frontend/src/shared/auth/localSessionAdapter.ts`'s `WireIdentity` interface
(line 27) declares `role: string | null`, `superAdmin: boolean`, `organizationId: string` as
fields the real `/cp/auth/identity` and `/cp/auth/login` responses always carry, and
`toIdentity()` (line 39) maps them straight through with no fallback. **The real `Identity` schema
in `contracts/openapi/console.yaml` (line 3668) has none of these three fields** — only
`principalId, username, source, mustRotate, permissions, organizations, csrfToken`. Verified live:
the real login/identity response bodies captured during this run contain no `role`, `superAdmin`
or `organizationId` key at all.

**A second, related mismatch in the same interface:** `WireIdentity.source` is typed
`'LOCAL' | 'IDP'` (checked via `wire.source === 'LOCAL'`), but the real contract's `source` enum is
lowercase (`[local, idp]`). The real value `"local"` never matches `'LOCAL'`, so `source` always
resolves to `'idp'` against the real backend.

**Confirmed blast radius (grep, not exhaustive):**
- `frontend/src/features/inventory/solutions/SolutionsPage.tsx:101` — `identity?.superAdmin ?? false`
  gates the "Load Package" action (`FE-D9`: omitted, not disabled, for non-super-admins). Since
  `superAdmin` is always `undefined` on the real wire, **this control is permanently unreachable
  for everyone against the real backend, including a true super-admin.** Confirmed live: the
  bootstrap administrator (which holds `package.load` among 43 real permissions) saw no Load
  Package button on either Solutions or Home.
- `frontend/src/app/shell/AccountMenu.tsx:99` — `identity.role ?? t('noRoleAssigned')` degrades
  gracefully (shows "No role assigned" instead of crashing) — cosmetic, not broken, but always
  wrong against the real backend.
- `frontend/src/app/shell/AppBar.tsx:55,96` — `identity.organizationId` passed to
  `OrganizationDisplay` as `undefined`; did not crash in this run (no visible error), but the
  top-bar organization name is never shown against the real backend. Not independently confirmed
  beyond "no crash + no org name visible" — worth a closer look before fixing.

**Why no existing test caught this:** every unit/component/Playwright-fixture test in this codebase
exercises `localSessionAdapter` against MSW handlers or hand-written fixtures
(`localSessionAdapter.test.ts`, `devMockAdapter.ts`) that **also** inject a fake flat
`role`/`superAdmin`/`organizationId`/uppercase-`source` shape — the fixtures and the production
code share the same wrong assumption, so nothing in the test suite could ever disagree with it.
This is exactly the blind spot true end-to-end testing against a live backend exists to catch.

**Not fixed here.** This is plan 001 scope (closed 2026-10-01, auth + hierarchy), not any of the
five plans this session executed, and fixing it properly means auditing every consumer of
`identity.role`/`.superAdmin`/`.organizationId` (the `AuthAdapter` type, RBAC-adjacent UI, possibly
more than the three call sites found by grep) plus deciding what the *correct* behavior should be
for each (the real contract may simply not carry these concepts the same way — `superAdmin` in
particular might need to be derived from the permission set, or from a `role`-equivalent the
contract does carry, rather than ported 1:1). That's a design question, not a type fix, same shape
as the Designer/D-4 finding in plan 008. Recommend folding it into the same consolidated session.
