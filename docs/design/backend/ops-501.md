## 2. The starting point, measured in the tree

**The strategies.**

1. The gateway refuses the three strategies before any verb is asked: `ApplyOrchestrator.SERVED_STRATEGIES =
   {manual, rolling-health-gated}` throws `NotImplementedStrategyException` → `501` in `submit`, `rollback` and
   `restoreRuntime`; `FleetOrchestrator` does the same. `ApplyServiceImpl.SERVED` and `FleetService.SERVED` repeat the
   set in `dp-core`.
2. **The engine already executes two of them.** `ApplyExecutor.SUPPORTED = {MANUAL, ROLLING_HEALTH_GATED,
   ROLLING_NO_VALIDATION, RESTART_ALL}`. `SCHEDULED` is absent: *"it needs a scheduler, and there is no application
   class to host one."* `RollingApplyIT` covers `rollingNoValidationIsNotRefusedByAnAbsentHealthSignal`,
   `aRollingNoValidationApplyRestartsWithoutGating` and `restartAllRequiresAnOutageConfirmation`.
3. **In the engine, `rolling-no-validation` and `restart-all` run the same loop.** `restartAndGate(…, gated =
   strategy == ROLLING_HEALTH_GATED, …)`: one replica at a time, `startOrUpdate`, no gate, then `verifyAfterRestart`
   (read back, compare the keyed hash, `OR-53`/`OR-64` Q-G2). There is **no fixed delay** and **nothing
   simultaneous**. The only difference is the outage confirmation, enforced twice: `ApplyCommand`
   (`full_outage_confirmed`, Java) and `apply_request`'s `full_outage_confirmed` CHECK (`V002`).
4. **On SSH-Docker a placement is exactly one container.** `SshDockerRuntimeAdapter.replicas` returns one replica;
   `startOrUpdate` runs `docker restart -- <container>` and `stop` runs `docker stop -- <container>`
   (`SshjDockerTransport`).
5. **v1 applies one placement per request** (`BE-D23`; `admit` refuses an instance-wide apply,
   `ApplyExecutor.java:208-212`). So today every restarting strategy restarts **one container**. Plan 008's refresh
   (`c472bbdb`) **recommends keeping it that way** (`OQ-8.1` (b)): a rollout across an instance's placements is a
   fleet whose members are those placements (members are `(instance, placement)`, `fleet_member_named_once`), and the
   apply path does not change. Within a fleet batch the worker runs members **concurrently**, and the next batch
   opens only when every member of the current one is settled (`fleet-apply.md` §5.2 point 3).
6. **`outageConfirmedBy` is a free browser string.** `SubmitApplyRequest` and `FleetApplyRequest` pass it through
   verbatim to `apply_request.outage_confirmed_by`; nothing binds it to the session principal. `RollbackRequest`
   and `RestoreRuntimeRequest` **have no such field**, so `restart-all` on a rollback or a restore could not satisfy
   the CHECK even if it were served.
7. The ladder and the reconciler already handle ungated strategies: `ConfigLadder.restartObserved` takes the
   container-start route for every strategy but `rolling-health-gated` (`OR-112` (1)); `ReconcileDecision` branches
   the same way.

**Undeclare.**

8. **No contract operation.** `console.yaml` has no `DELETE` anywhere. `console-integration.md` §5.3 row 37 names
   `DELETE /instances/{instanceId}` and blocks it on 39 (d). `validate-openapi.py`'s `WITHHELD` set contains
   `instance.undeclare` and `instance.restart.overrideSafety`, so the contract may not use them today.
9. **The DP lifecycle has no exit.** `sm_data.instance_state.lifecycle ∈ {pending, active, abandoned}`, and the
   trigger `instance_lifecycle_moves_forward` admits only `pending → active | abandoned` (`V007`). Placements retire
   by `retired_at` (the only legal update, trigger `placement_immutable`).
10. **Nothing is deletable.** No runtime role holds `DELETE` on any `sm_data` or `sm_control` table this design
    touches (`V007` grants; `V013` header: *"It still holds no DELETE anywhere here"*).
11. **The CP never deletes a governance node** (`BE-D32` rule 7). Quota is `count(*)` over `sm_control.instance`
    joined to its catalog entry (`JdbcGovernanceRepository.countInstances`), with no lifecycle filter.
12. **What hangs off the CP node with `ON DELETE RESTRICT`:** `sm_control.dashboard` (one per instance, `V014`), and
    role bindings through the instance's `scope` row (`V003`). So the node could not be deleted even if a role
    could.
13. **What already keys on `lifecycle = 'active'`:** admission (`AdmissionService`, under the `apply_scope` row
    lock), `getInstance` ("only an ACTIVE instance is readable"), the dashboard reads (non-active is `404`), the
    attention query, and `OR-49`'s tenant list (`TenantEnumerationRepository.tenantsWithActiveInstances`), which
    drives the health poller and the metrics background loop.
14. **What SM leaves on a Docker host** for each placement: the config file it writes, and its own hidden files
    beside it, `.sm-preimage-*` (the pre-apply copy of the file, which holds whatever the file held, resolved
    secrets included) and `.sm-fp-*` (keyed fingerprints) (`SshDockerRuntimeAdapter`). `OR-109` records the
    integrator removing 20 of them from the E2E host by hand.

**Verified external facts (`I2`), fetched 2026-10-07:**

- `docker container stop`: *"The main process inside the container will receive `SIGTERM`, and after a grace
  period, `SIGKILL`."* The default grace *"is 10 seconds for Linux containers"* unless `--stop-timeout` set one at
  create (docs.docker.com, `reference/cli/docker/container/stop/`; `restart/` states the same default for its
  `--timeout`).
- Restart policies: `always` — *"If it's manually stopped, it's restarted only when Docker daemon restarts or the
  container itself is manually restarted"*; `unless-stopped` — *"when the container is stopped (manually or
  otherwise), it isn't restarted even after Docker daemon restarts"* (docs.docker.com,
  `engine/containers/start-containers-automatically/`). So a `docker stop` by SM is **not durable** for an
  `always` container across a host reboot.
- RFC 9110 §9.3.5: *"content received in a DELETE request has no generally defined semantics, cannot alter the
  meaning or target of the request, and might lead some implementations to reject the request and close the
  connection because of its potential as a request smuggling attack"* (rfc-editor.org, `rfc9110.txt`). So
  undeclare's confirmation goes in the query string, not a body.

## 3. The scenarios every option is run through

**Undeclare** (one Cache instance, one placement, on the E2E-style Docker host):

- **S1 — decommission.** The customer is retiring the instance. Its container is running.
- **S2 — mistaken declare.** An Operator declared an instance against the wrong container, which belongs to a
  running production workload. Nothing was applied yet. They want the declaration gone and the container
  untouched, then a correct declare against the same container name.
- **S3 — already removed.** The customer's CI/CD removed the container first; health reads `missing`.
- **S4 — host gone.** The VM was decommissioned; SSH is unreachable; health reads `unreachable`.
- **S5 — busy.** An apply is `RUNNING`, or an earlier apply sits in `APPLY_INDETERMINATE` after the reconciler gave
  up (`OR-59`: "stays and alerts").

**Strategies:**

- **T1 — a probe-less package.** A package that declares no health probe (File Mesh is the named case,
  `architecture.md` §9). Under `rolling-health-gated` the engine fails closed (`OR-64` Q-G1), so today the only
  choice is `manual` and the operator restarts by hand.
- **T2 — Cache, one placement.** Cache declares a liveness-only probe (`OR-53`), so `rolling-health-gated` runs.
- **T3 — after plan 008: one instance, three placements** P1, P2, P3 (three containers, one per host). Under plan
  008's recommended `OQ-8.1` (b) the rollout is a fleet whose three members are those placements.
- **T4 — a fleet of 10 Cache instances**, `batchSize` 1, `halt-remaining`.

**Scheduled** (a change approved at 14:00 for a 02:00–04:00 maintenance window):

- **W1** — the normal case.
- **W2** — at 22:00 the operator finds a mistake and wants it cancelled.
- **W3** — SM is down for an upgrade from 01:50 to 04:30.
- **W4** — the submitter is deactivated at 18:00.
- **W5** — an urgent fix is applied by hand at 23:00, a newer generation than the scheduled one.
- **W6** — the scheduled change is a **rollback** to generation 5, and a stage of generation 9 lands at 20:00,
  between submit and fire (§6.3).

## 4. Undeclare

### 4.1 What it is, and what does not change under any option

**Undeclare removes an instance from SM's inventory and management.** After it: the instance is not listed or
readable, SM polls nothing on it, collects no metrics from it, admits no apply to it, and it no longer counts against
the organization's quota (`OR-40`). The resource is the **instance** (with all of its placements), which answers the
"identify the resource first" half of 39 (i) for this operation.

**Fixed across every option below:**

- **Nothing is deleted** from `sm_data`, `sm_metrics` or `sm_control` (fact 10, `BE-D32` rule 7). Rows move to a
  terminal state. History stays for audit, archive and a possible later restore (39 i).
- **Ids are never reused.** The DP mints a fresh uuid for every declare (`OR-27`).
- **Authorization is at the owning instance** (`OR-16`), through the one enforcement point (`D10` §1.5).
- **Refused while anything is in flight** (S5): a `REQUESTED`/`RUNNING` apply or stop, an `APPLY_INDETERMINATE`
  request, or a `RUNNING` fleet that reserves one of the instance's placements. Checked under the same
  `apply_scope` row lock admission takes, so undeclare and admission cannot race (fact 13).
- **No new event.** Declare publishes none either; REST is authoritative (`OR-3`); the browser mesh stays gated by
  open items 32/33/35. A console refetches `listInstances` after its own `200`. An `instance.lifecycle` event can be
  added later as a reviewed single-writer change (`console-integration.md` §6).

### 4.2 The workload: what happens to the running container

This is open item 39 (d)'s own question: *"does undeclare require a prior stop, refuse while running, or leave it
running and orphaned?"*

| | **U-A — refuse while running** | **U-B — stop, then remove** | **U-C — release; never touch (recommended)** |
|---|---|---|---|
| What SM does on the host | A fresh SSH status read of every live placement. Proceeds only if every container is stopped or absent. | A journaled `stop` (`BE-D26`, instance-wide, one `applyId`); retires only when the stop lands `STOPPED`. | Nothing. No SSH call. |
| Verbs | `instance.undeclare` | `instance.undeclare` **and** `instance.stop` (Administrator-only today) | `instance.undeclare` |
| Response | `200`, or `409 INSTANCE_RUNNING` / `503` host unreadable | `202` + observe (two-phase: stop, then retire) | `200` |
| Caller states the outcome | implicitly | implicitly | **explicitly**: `?workload=leave-running` is required; without it, `400` |
| Engine change | a status read outside an apply | an undeclare-after-stop continuation in the worker | none |
| **S1** decommission, running | `409`; an Administrator must `stop` first, then undeclare. Two people if the caller is an Operator. | One call; the container is stopped (`SIGTERM`, `SIGKILL` after the grace, §2). An `always` restart policy brings it back after a host reboot. | One call; the container keeps running, unmanaged. The console offers "Stop first" (`instance.stop`) as an optional preceding step. |
| **S2** mistaken declare on a production container | ⛔ Cannot undeclare without stopping production. | ⛔ **Stops production.** | ✅ Declaration gone, container untouched; the freed name, container name and config directory allow the correct declare at once (§4.3). |
| **S3** already removed | ✅ absent counts as stopped | ✅ stop of an absent container lands `STOPPED` or `STOP_FAILED` (`stop.no.known.placement`) — must be read as success | ✅ |
| **S4** host gone | ⛔ `503`: never undeclarable while the host is gone | ⛔ `STOP_FAILED`: never undeclarable | ✅ |
| **S5** busy | `409` | `409` | `409` |

**Recommendation: U-C.** It is the only option that handles S2 and S4, it adds no host-touching path, and it
matches the one confirmed architectural position: SM is a **configuration** plane, not a deployment plane — the
customer's CI/CD owns the container's existence. It is not *silent* orphaning (39 d's worry): the caller must type
the disposition, the response lists each placement's last persisted health observation, and the audit rows record
both. **Its cost, stated:** a running container is left with SM's last-written config file and SM's hidden files
beside it, and from then on nobody is watching it through SM. The runbook (plan 012) gives the cleanup.

U-B's S2 failure is disqualifying on its own: an operation called "undeclare" that can stop a production workload
which was merely *pointed at* by mistake is the outage 39 (d) exists to prevent.

### 4.4 The protocol: three steps across two planes

Undeclare writes two planes, and `I7` forbids a distributed transaction, so it mirrors `BE-D32`'s declare in
reverse: the DP records the intent first, the CP releases the governance node, the DP finishes.

| Step | Plane | Commits | A crash here leaves | Finished by |
|---|---|---|---|---|
| 1 | gateway | nothing | nothing | — |
| 2 | gateway → CP | nothing: `require(instance.undeclare, instance)` | nothing | — |
| 3 | DP `beginRetire` | under the `apply_scope` lock: refuse if anything is in flight (§4.1); `lifecycle = retiring`; the `instance_retirement` row (with the request's `correlation_id`) | a `retiring` row, CP node still live | **either** an authorized retry of the `DELETE` (rolls forward under the retrying session), **or** the sweep after the window: **roll back** to `active` (`outcome = rolled-back`) |
| 4 | CP `deregister` | `retired_at`/`retired_by`, quota freed, audit row — under the requesting session's audit context | a `retiring` DP row, CP node retired | the sweep: complete (step 5 only, a DP write) |
| 5 | DP `completeRetire` | `lifecycle = retired`; placements `retired_at`; `completed_at`, `outcome = retired` | nothing | — |

**Recovery mirrors `BE-D32` exactly: the sweep never writes the Control Plane** (revision 2, finding F3). The first
draft rolled a `retiring` row *forward* from the sweep, which would have had the sweep call CP `deregister` — a write
to `sm_control.instance`, which `change_audit_trigger` audits (`V011:207`) and which `OR-25`'s fail-closed block
(`V012:92-121`, current body `V014`) refuses unless the session supplies a known operation, an actor, a well-formed
correlation id and a client address. The sweep runs inside **some other user's** `declareInstance`/`listInstances`/
`getInstance` — possibly a Viewer's — so the audit row would name the wrong session, or the write would be refused.
The rules are therefore:

- **CP deregistered, DP `retiring`** → the sweep completes step 5 (a DP-only write; the CP's audit row was written by
  the original `DELETE`'s session). This is `BE-D32`'s "a registered `pending` row is activated at any age", reversed.
- **CP not deregistered, DP `retiring`, older than the window** (`sm.dp.undeclare.rollback-after`, default ten
  minutes, as `sm.dp.declare.abandon-after`) → the sweep rolls the row back to `active` and closes its
  `instance_retirement` row `rolled-back`. Nothing on the CP side changes, so nothing there needs an audit context.
  This is `BE-D32`'s "an unregistered `pending` row is abandoned after the window", reversed. The undeclare simply
  did not happen; the caller, who received no `200`, retries.
- **CP not deregistered, DP `retiring`, younger than the window** → left alone (a `DELETE` may be between steps 3
  and 4).
- **An authorized retry** of the `DELETE` on a `retiring` row whose CP node is still live passes step 2 (the CP node
  resolves), finds its own `retiring` row at step 3 and resumes at step 4 **under the retrying session's audit
  context**. `instance_retirement.requested_by` stays the original requester; `sm_control.instance.retired_by` and
  the CP audit row name the retrying principal, which is the session that actually performed the CP write.
- **The window guard.** The orchestrator refuses to start step 4 if its `beginRetire` stamp is older than half the
  window (it leaves the row to the sweep and answers `503`), so a sweep roll-back cannot race a slow step 4. This is
  the same reliance on a window `BE-D32` already accepts, with a stated margin.

The sweep is lazy and tenant-scoped, with no background loop, exactly as `BE-D32`'s: it runs inside the requests
whose correctness a stale `retiring` row affects — `declareInstance` (names, ports and quota), and
`listInstances`/`getInstance` — for **that request's tenant only**, asking the CP (through the gateway, the one
module allowed both `-api`s) which `retiring` ids it has deregistered. That question is a **read** of `sm_control`;
neither branch writes it. **No tenant enumeration** is added (`OR-44`, `OR-49` untouched). A `retiring` row in a
tenant that never declares or lists again is invisible and holds its quota slot only until that tenant's next
declare, which runs the sweep first.

**The trigger change this implies.** `instance_lifecycle_moves_forward` admits `retiring → active` as well as
`active → retiring` and `retiring → retired`. That is the one backward move in the lifecycle, and it is legal only
when the matching `instance_retirement` row is closed `rolled-back` in the same transaction (checked by the trigger).

**Idempotency.** A repeated `DELETE` on a **retired** instance (or one whose CP node is already deregistered) is
`404`, the same as an unknown id; the sweep finishes step 5. A repeated `DELETE` on a `retiring` instance whose CP
node is live resumes, as above, and answers `200`.

### 4.7 Two residues the owner should accept or reject

- **Host files (`OPS-Q4`).** Leaving `.sm-preimage-*` behind leaves a plaintext copy of an older config file,

  **Recommend leaving them**, with the runbook giving the exact cleanup command per placement directory and the
  response saying the files remain. The live config file holds the same secrets anyway while the container runs.
- **An unresolved `APPLY_INDETERMINATE` blocks undeclare (`OPS-Q5`).** After the reconciler gives up, the request
  "stays and alerts" (`OR-59`), and there is **no API** to resolve it by hand (`architecture.md` §16.1 designs
  operator confirmation; nothing builds it). So an instance on a dead host with a stuck apply (S4 + S5) can never
  be undeclared. Options: (a) accept as a known gap and route the manual-resolution API to its own design;
  (b) let undeclare land a stuck request in a new terminal state. (b) needs a new `RequestState`, which changes the
  contract enum `OR-36` fixed, the `V006` terminal guard and the apply-outcome event. **Recommend (a).**

### 4.8 Risks (U-C)

1. A released container keeps running unmanaged; drift, health and metrics are no longer visible through SM.
   Mitigated by the explicit `workload` parameter, the response, both audit rows and the runbook.
2. Bindings on a retired instance's scope stay in `sm_control` forever (no `DELETE`). They grant and reveal nothing
   **only because** `grantsFor` skips them (§4.3, finding F9); without that filter they keep the environment visible.
3. A second organization that registered the same host (`OR-89`) is unaffected; nothing here is per-host.
4. The CP and DP disagree for the length of one crash window (§4.4). Every read already treats `retiring` as gone,
   so the disagreement is not visible to a user; the quota slot is held until the sweep runs (CP side done) or the
   roll-back window passes (CP side not done).
5. A rolled-back undeclare makes the instance reappear after up to the window (default ten minutes). The caller
   received no `200`, so nothing they were told becomes untrue; the `instance_retirement` row records `rolled-back`.

## 5. `rolling-no-validation` and `restart-all`

### 5.1 Exact semantics on Docker over SSH

**Today (one placement per request, `BE-D23`).** Both strategies run these steps on the one container:

1. `PREFLIGHT` — `docker inspect`; the config directory is writable. No probe is required (unlike
   `rolling-health-gated`, which fails closed without one).
2. `MATERIALIZE` — SFTP write, keyed hash (`OR-32`), pre-image retained with its fingerprint (`OR-102`).
3. `LIFECYCLE` — `docker restart -- <container>` (`SIGTERM`, then `SIGKILL` after the container's grace,
   default 10 s on Linux, §2). Rollout event `restart-requested`.
4. `VERIFY` — read the file back, compare the keyed hash: match → `APPLIED`; mismatch → `CONFIG_DIVERGED`
   (`verify.hash.mismatch`), **no automatic rollback** (`OR-64` Q-G2); unreadable → `APPLY_INDETERMINATE`.
5. The ladder reaches `restart-observed` when the poller sees a container start later than the write (`OR-112`
   (1)); `instance.config-state` and `instance.apply-outcome` publish as for any apply.

**So, today, on Docker, `rolling-no-validation` and `restart-all` restart the same single container the same
way.** They differ from `rolling-health-gated` only in having no gate, and from each other only in the outage
confirmation. Stated plainly, because the names suggest more: on one placement there is no "rolling" and no "all".
Their practical value now is **T1**: a probe-less package gets an SM-driven restart instead of `manual` only.

**After plan 008 — conditional on its `OQ-8.1`** (revision 2, finding F1). The first draft assumed plan 008 would
build an instance-wide fan-out inside the engine. The refreshed plan 008 (`c472bbdb`, R3/R4) measures the opposite
and **recommends not building it**: `OR-53` makes `placementId` required on apply, the engine refuses an
instance-wide apply before admission (`ApplyExecutor.java:208-212`), and its `OQ-8.1` (b) makes "a rollout across
placements" **a fleet of placement-scoped applies**, with no apply-path change. Where the ungated strategies'
multi-placement rules live therefore depends on that answer.

**Fixed under every `OQ-8.1` answer:** each placement is restarted, read back and verified exactly as the one-placement
steps above; a verify mismatch is `CONFIG_DIVERGED` with no rollback (`OR-64` Q-G2); `restart-all` needs the outage
confirmation (§5.3); both strategies need `instance.restart.overrideSafety` (§5.2).

**Case (b) — the recommended plan 008 answer: a rollout is a fleet.** Every apply stays one container. The
multi-placement behaviour is the **fleet's**, so it is set by `batchSize` and the batch rules, not by the strategy
inside one request. That has two consequences the first draft did not see:

1. **The outage across one instance's placements is set by `batchSize`.** Within a batch the worker runs members
   concurrently (fact 5). A fleet with `batchSize ≥ 2` holding P1 and P2 of one instance restarts both at once —
   under `rolling-no-validation` **with no outage confirmation**, and in fact under `rolling-health-gated` too (each
   member gates only on its own placement). And a `restart-all` **member** confirms only a single-container outage,
   so the confirmation does not describe what the operator is about to cause.
2. **A settle delay cannot live in `ApplyExecutor`**, which never sees more than one placement. It can only live in
   `FleetScheduler`, between batches.

| | `rolling-health-gated` | `rolling-no-validation` | `restart-all` |
|---|---|---|---|
| Per member (one container) | gate, then verify | no gate, verify | no gate, verify |
| Between batches | as built: the next batch opens when the current one is settled | as built, **plus a settle delay**: the next batch opens no earlier than the settle delay after the current batch's last member settled (computed from `apply_request.terminal_at`, which is persisted, so a scheduler restart keeps the delay) | as built; no delay |
| Two placements of one instance in **one batch** (`K-2`, below) | refused at submit (`422`, *recommended to plan 008's sitting*, since this strategy is plan 008's) | **refused at submit** (`422 VALIDATION_FAILED`, `fleet.batch.instance.repeated`) | **allowed**; this is what `restart-all` asserts, and the fleet's outage confirmation now covers it |
| Outage within one instance | one placement at a time | one placement at a time, for at least the settle delay apart | up to `batchSize` placements of the instance at once, confirmed |

The per-instance rule is the owner's call (`OPS-Q8`), with three shapes:

- **K-1 — nothing:** `batchSize` is the operator's control; the console warns. Status quo once plan 008 lands. A
  `rolling-no-validation` fleet with `batchSize` 3 over T3 takes the whole instance down with no confirmation.
- **K-2 — refuse at submit (recommended):** for every `rolling-*` strategy, a batch may hold at most one placement of
  any instance; `restart-all` is exempt and its confirmation covers the multi-placement outage. One check in
  `FleetService`'s submit over `members[]` (order is `members[]` order, `fleet-apply.md` §5.1), no migration, no
  scheduler change. The gated half of it amends plan 008's scope, so it goes to the same sitting as `OQ-8.1`.
- **K-3 — the scheduler reorders members** so no batch repeats an instance: changes the ruled "order is the order of
  `members[]`" and makes `observeFleetApply`'s batches differ from what was submitted. Not recommended.

Settle delay source (`OPS-Q8`): (x) a DP property `sm.dp.fleet.no-validation.settle`, default 30 s, applied between
every pair of batches of a `rolling-no-validation` fleet (uniform: simpler than "only when consecutive batches share
an instance", and the operator who wants speed raises `batchSize` across distinct instances); (y) a package
declaration (a `solution-package.schema.json` change); (z) none. **Recommend (x)**, (y) only when a package needs it.

**T3 through (b):** the fleet `{P1, P2, P3}`. `rolling-health-gated`, `batchSize` 1: one at a time, each gated —
liveness-only for Cache (open item 15: a standby reports `UP`). `rolling-no-validation`, `batchSize` 1: one at a time,
≥ 30 s apart; `batchSize` 3: **refused** under K-2. `restart-all`, `batchSize` 1: one at a time, no delay — the
strategy name does not make it simultaneous; `batchSize` 3: all three restarted concurrently, confirmed.

**T4 (fleet over 10 instances, one placement each):** each member is its own request (`fleet-apply.md` §4).
`restart-all` is 10 single-container outages, one batch at a time; K-2 never fires (no instance repeats).
`rolling-no-validation` gets the settle delay between batches. The fleet's one confirmation is recorded on the fleet
row and on each member's request.

**Case (a) — if the owner instead rules plan 008's `OQ-8.1` (a), one instance-wide request fanned out in the
engine:** the first draft's semantics apply — stage every placement, then restart one at a time; `rolling-no-validation`
waits the settle delay between placements inside `ApplyExecutor`; `restart-all` restarts back-to-back without waiting
(the engine's existing loop) or concurrently (new step code); resume continues exactly the unfinished placements.
That case costs plan 008 ≈ 2.5 slice-days and three ruling amendments by its own estimate, and plan 012 T6 then
changes the engine instead of `FleetService`/`FleetScheduler`.

**Case (c)** (plan 008's (b) plus a one-call rollout operation that builds the fleet server-side): as (b); the
server-built fleet should default `batchSize` 1, so K-2 never fires on it.

### 5.3 The outage confirmation: record the principal, not a typed name

column or CHECK changes: both are already `text`, and `requested_by` holds a principal id the same way. A
browser-supplied name is never stored. `rollbackApply` and `restoreRuntimeConfig` gain a way to confirm (fact 6).

| Frontend (integrating from the Postman collection, `OR-112` (4)) | must change field name | nothing to change; the typed name is simply not trusted | nothing now; migrate later |
| Clarity | best: a boolean says what it is | a string field whose value is ignored is a small lie in the contract | two ways to say one thing until the old is removed |
| `restart-all` with neither | `400` | `400` | `400` |

**Recommend C-2**: the frontend already integrates from the Postman collection, the semantic fix (the principal is
recorded) is the same under all three, and C-2 changes no field a client sends. C-1 is the cleaner end state and can
follow when the frontend is ready, as a reviewed contract change. *(Revision 2, finding F11: the first draft offered
only the breaking rename or the status quo.)*

**Where the check runs (finding F7).** `rollbackApply` and `restoreRuntime` mint a new instance generation
(`copyForward`/`copyLatestForward`, `ApplyServiceImpl.java:108-160`) **before** the `ApplyCommand` constructor
(`ApplyCommand.java:50-53`) checks `full_outage_confirmed`. A missing confirmation found only there would mint a
generation and then surface as an `IllegalArgumentException` → `500`. So the **gateway** validates the confirmation
before any DP call, and the DP check stays as the backstop. The order of refusals for the four operations becomes:

1. `400` — body checks, including `restart-all` without a confirmation (and `strategy: scheduled` per §6's answer);
2. `404` / `403` — `require` for the primary verb (`config.apply` or `config.rollback`) at the instance, which is
   what decides `404`, then the secondary verbs `instance.restart` and `instance.restart.overrideSafety` (`403`);
3. the DP's own refusals (`409`/`422`).

This replaces today's "`501` before any verb" order for the two served strategies; `scheduled`'s answer keeps its
place in step 1.

> **Forward pointer (2026-10-08, W2 review `W2B-1`; the text above is left as reviewed).** The gateway does not run
> steps 1 and 2 in this order. The interceptor passes the operation's **primary verb** (`config.apply` /
> `config.rollback`, `404`/`403`) **before** the request body is read, as for every other `400` in this API, so the
> built order is: primary verb (`404`/`403`) → `400` (body, including the missing `restart-all` confirmation) →
> `501` (`scheduled`) → `403` (`instance.restart`, then `instance.restart.overrideSafety`) → `404` (instance not
> active, or placement not live) → the DP's refusals (`409`/`422`). What §5.3 protects holds unchanged: a refused
> `restart-all` makes no DP call and mints no generation. `console.yaml` states the built order. Plan 012 T2's Results
> record the same departure.

`rolling-no-validation` takes no confirmation: it does not assert an outage, and the verb (B-1) is the assertion.

### 5.4 Contract and code delta

- The three `501` responses for these two values are removed from the four operations; `scheduled` keeps its own
  answer (§6).
- `Strategy`'s description changes: four selectable values (`scheduled` per §6).

- Fleets after plan 008 (case (b), §5.1): K-2's submit check in `FleetService`, and the settle delay in

- No new event, no new `ErrorCode`, no new `RequestState`, no `sm_data` migration.

### 5.5 Risks

1. **T1 with no probe:** SM restarts and verifies the file, but nothing tells SM the process came back healthy.
   The ladder stops at `restart-observed` (a container start), never more. The console must say "restart observed,
   health not verified".
2. A slow-starting MI under `rolling-no-validation` with too short a settle delay is, in effect, `restart-all`

3. A fleet `restart-all` (T4) is many outages from one click. Mitigated by `batchSize` default 1 and

## 6. `scheduled`

### 6.1 What it would mean, and why it is not simply "turn it on"

`SM-D15`: *"`scheduled` — any of the above at a chosen window"*. It is a **modifier** of another strategy, not a
fifth way to restart, which is why the engine cannot just execute it.

**Why it answers `501` — and what it is not** (revision 2, finding F5). The strategy is `SM-D15` (PROPOSED). It
answers `501` because `OR-53` says so (*"`restart-all`, `rolling-no-validation` and `scheduled` stay 501"*), because
`OR-60` widened the enum so that it answers `501` rather than `400`, and because it has no verb under open item 39 (b).
**No scope cut applies to it.** The round-5 cut in `DECISIONS.md`'s supersession table is a row for **`B/D14`** —
*"workload types `service` | `scheduled`"* — and `architecture.md` §15's *"`service` workloads only (`scheduled` cut
from v1 …)"* says the same: it withdrew the `scheduled` **workload type** (cron-style jobs run by the agent or DP as
scheduler) from v1, and *"the capability remains locked; only its v1 inclusion is withdrawn"*. That cut, and `B/D14`'s
record, are untouched by anything here; nothing in this design runs a scheduled workload.

The cut's reasoning is still **instructive** for the strategy, and is recorded as such, not as a constraint: it
cited `SM-D28`'s one-hour lease (*"a restart window hours out cannot fit inside the authority that must admit it"*).
That lease is the `host-local` agent's; under dp-remote there is no lease, and the dp-remote form of the same problem
is **authority staleness** — the grant that admitted the schedule at 14:00 may be gone by 02:00 (W4). Its second
reason, *"no v1 solution needs it"*, was about workloads, but the same question is fair for the strategy: Cache
operators can schedule a `submitApply` from their own tooling today (Sch-0).

### 6.3 Sch-2's rules (only if built)

- **Request.** `submitApply` and `rollbackApply` gain an optional `schedule: {notBefore, notAfter}` (UTC); the
  inner `strategy` stays one of the four. `strategy: "scheduled"` is then answered `422 VALIDATION_FAILED`
  (`detail`: use `schedule`) instead of `501`; the enum keeps the token (`OR-60`) and `strategy_known` keeps it,
  but no row ever stores it. ⚠️ **That `501 → 422` amends two rulings by name** (finding F11): `OR-60`'s ruled shape
  (*"the three unbuilt ones answer `501`"*) and `OR-53`'s text (*"`scheduled` stay[s] 501"*). The owner's Sch-2
  ruling must name both; without it, `strategy: "scheduled"` keeps answering `501` and only the `schedule` field is
  new. Not on `restoreRuntimeConfig` or `setLogLevel`; not on fleet in v1 (a scheduled fleet is a scheduled set of
  batches, a different design).
- **When a scheduled rollback copies its target forward** (finding F12). `rollbackApply` mints the new instance
  generation **at submit** today (`copyForward`, `ApplyServiceImpl.java:113-122`). Doing that at 14:00 for a 02:00
  window would make the old content the instance's desired head twelve hours early — every later stage, the ladder
  and drift would read against it. **Rule: a scheduled rollback stores its target (`applyId` or `generation`) and
  copies it forward at fire time, inside the admission path**, re-resolving eligibility (`OR-42`) then. At submit it
  only validates that the target is eligible now. Scenario **W6**: a stage of generation 9 lands at 20:00, between a
  14:00 scheduled rollback to generation 5 and its 02:00 window. At fire, generation 5 is copied forward as
  generation 10 (above 9, so the only-goes-up fence is untouched) and applied; the operator's generation 9 is
  superseded by the rollback they scheduled, and the schedule row records both numbers. If the owner prefers that a
  stage landing in between **cancels** the scheduled rollback (`REFUSED`, `schedule.desired.changed`), that is a
  one-line rule at fire; recommended **not**, because the rollback was the explicit, later-intended act — but it is
  stated so the owner can choose (`OPS-Q10`).
- **Bounds.** `notBefore` > now; `notAfter` > `notBefore`; `notBefore` at most `sm.dp.apply.schedule.max-lead`
  ahead (default 7 days, configurable). Response `202 {scheduleId, stateVersion}`.
  ⚠️ **Rider (2026-10-08, W3 review `W3B-4`; the line above is unedited, `I3`):** `OR-122` (2) rules "at most **7 days** ahead", so
  7 days is a **ceiling** that configuration may only lower (a larger `max-lead` refuses to boot), and `notAfter` is bounded by
  the same horizon (`422`), not only `notBefore`.
- **Firing.** At or after `notBefore`, and before `notAfter`: re-authorize the submitter (below), then admit
  exactly as `submitApply` would. A fence conflict at fire time is retried on each tick until `notAfter`, then
  `MISSED`. Any admission refusal is `REFUSED` with the engine's reason.
- **Re-authorization at fire, and where the loop lives** (revision 2, finding F6). Fleet authorizes at submit only
  because a fleet runs in minutes; a schedule may wait days. Re-checking at fire needs `require`, which is a
  `cp-api` call; a loop that finds due schedules needs a cross-tenant read of `sm_data`. **No existing module can do
  both:** `console-gateway` depends only on `cp-api` and `dp-api` (`console-gateway/pom.xml`), so it cannot call
  `TenantEnumerationRepository`, a `dp-core` persistence class that `OR-49` confines to *"persistence package only,
  feeding a per-organization scoped loop"*, with `MonitoringBoundaryTest.RULED_CALLERS` naming four `dp-core`
  classes; and a `dp-core` loop cannot call `cp-api` (`I7`). The gateway also has **no background loop** today. The
  two real shapes (`OPS-Q10`):

  | | **(c) gateway loop + a new `dp-api` port** | **(d) `dp-core` loop, authorized at submit only** |
  |---|---|---|
  | Shape | A `ScheduleFirer` in `console-gateway` (its first background loop: every loop today — `ApplyWorker`, `HealthPoller`, `FleetScheduler`, `MetricsBackgroundLoop` — is in `dp-core`, so the gateway gains its own scheduled executor); a new `dp-api` port `ApplySchedulePort` with `tenantsWithDueSchedules(now)` (tenant ids only) and `due(tenant, now)`; per due row: `require(principal, verb, instance)` via `cp-api`, then the port's `admit(scheduleId)` | A `dp-core` `ApplyScheduleLoop`, as `FleetScheduler` is: tenants from `OR-49`'s list as its **fifth named caller** (or its own list over `apply_schedule`), then `due(tenant)` and admit |
  | Cross-tenant read | **a third application-side cross-tenant read, and the first exposed across a module API** — wider than "a fifth caller"; amends `OR-44`/`OR-49`/`OR-92` | a fifth caller of `OR-49`'s list — the ruling `OR-49` itself says it needs |

  **Recommend (c)**, because W4 is precisely the dp-remote form of the reason the window idea was distrusted (§6.1),

  read crossing a module API — is stated for the owner, not assumed.
- **Cancel.** `DELETE /dp/instances/{instanceId}/apply-schedules/{scheduleId}`, verb `config.apply` at the

  `GET /dp/instances/{instanceId}/apply-schedules`, verb `config.view`.
- **Audit.** The schedule row records `requested_by`, the cancel records `cancelled_by`; the admitted apply's

## 9. Draft decisions (ids allocated 2026-10-07: `BE-D49`–`BE-D53`)

### `BE-D49` (draft O-1): undeclare releases an instance from management; it never deletes and never touches the workload

Undeclare is `DELETE /dp/instances/{instanceId}?workload=leave-running`, authorized by `instance.undeclare` at the
instance. It runs three steps — DP `beginRetire` (refuses anything in flight, under the `apply_scope` lock), CP
`deregister` (inside the request, under its session's audit context), DP `completeRetire`. Recovery mirrors `BE-D32`
and **never writes the Control Plane**: a lazy, per-request, tenant-scoped sweep completes a `retiring` row whose CP
node is already deregistered, and rolls back to `active` a `retiring` row whose CP node is still live after the
window; an authorized retry of the `DELETE` resumes at the CP step under its own session. Nothing is deleted in any
schema; `BE-D32` rule 7 stands. Bindings at a retired instance's scope grant and reveal nothing. The workload, the
config file and SM's hidden files on the host are left as they are; the caller states that explicitly. Retirement
frees the instance name (extending `OR-88`), its placements' container names, directories and ports, and its quota
slot. *(Conditional on `OPS-Q2` = U-C and `OPS-Q3` = P-1.)*

### `BE-D50` (draft O-2): the ungated strategies' exact semantics

`rolling-no-validation` and `restart-all` restart one placement with no gate and verify the read-back (`OR-64`
Q-G2); on one placement they are the same host action. **If plan 008 rules `OQ-8.1` (b) or (c)** (a rollout is a
fleet): a `rolling-no-validation` fleet waits a fixed settle delay between batches, and no `rolling-*` fleet batch may
hold two placements of one instance; a `restart-all` fleet does not wait and may, under its confirmation. **If plan
008 rules `OQ-8.1` (a)**: the delay and the back-to-back restart live in the engine's fan-out instead. *(Conditional
on `OPS-Q8` and plan 008 `OQ-8.1`, ruled in one sitting.)*

### `BE-D51` (draft O-3): overriding restart safety is a verb, and an outage confirmation is the caller's principal

Both ungated strategies require `instance.restart.overrideSafety` at the instance, in addition to `config.apply`
(or `config.rollback`) and `instance.restart`; a fleet asks it per member in `verdict()`. `restart-all` additionally
requires a confirmation (wire shape per `OPS-Q7`), checked in the gateway before any DP call; the server records the
session principal id in `apply_request.outage_confirmed_by` and `fleet_action.outage_confirmed_by`. A
browser-supplied name is never stored there. *(Conditional on `OPS-Q6` = B-1 and `OPS-Q7`.)*

### `BE-D52` (draft O-4): a scheduled apply is a DP-owned schedule record admitted as an ordinary apply inside its window

*(Only if `OPS-Q9` = Sch-2.)* `sm_data.apply_schedule` holds the request until `notBefore`; at fire the submitter is
re-authorized (shape (c)) and an ordinary apply is admitted; a scheduled rollback copies its target forward at fire,
not at submit; outside `notAfter` it lands `MISSED`; cancel is a state of the schedule row. The apply journal,
`RequestState`, the fences and the event catalog are unchanged. Amends `OR-53` and `OR-60` for `strategy:
"scheduled"` (`501` → `422`) only if the ruling names them.

### `BE-D53` (draft O-5): one placement is retired by the verb that adds one, under undeclare's rules

*(Only if `OPS-Q12` = R-1.)* `DELETE /dp/instances/{instanceId}/placements/{placementId}?workload=leave-running`,
`instance.bindTarget` at the instance; never touches the host; refused for the last live placement and while
anything is in flight on it; one DP transaction, no CP write. Ships only after plan 008 S4 (the live-placement stop
enumerator).
