# Agent Gateway — design

**Component:** `agent-gateway` (a Java Maven backend component, **designed, not built**) · **Deployment:** co-deployed inside the Data Plane v1 process, **not a separate app or process** · **Plane:** Data Plane · **Peers:** the distinct `host-local` Go agent over the `B/D16` protocol; `dp-core` over typed ports · **Stack:** Java 17 / Spring Boot (the backend reactor), gRPC over HTTP/2 with mTLS
**Date:** 2026-09-08 · **Revised:** 2026-09-08 (independent adversarial review, 23 findings; seven external Codex rounds, 63 findings — see [`decisions.md`](decisions.md) changelog) · **Status:** DRAFT. **PROPOSED, not ratified. No code. No `.proto`.**
**Decisions:** [`decisions.md`](decisions.md) — family `AGW-D*`, registered in [`../../DECISIONS.md`](../../DECISIONS.md) and [`../../README.md`](../../README.md). **`AGW-D15`/`AGW-D16` mechanism:** [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) — separately gated, **not part of the `AGW-D1`…`AGW-D14` ratification set**.
**Requirements:** [`REQ-005`](../../../requirements/REQ-005-three-runtimes.md) (the runtimes where only `host-local` works) and [`REQ-007`](../../../requirements/REQ-007-six-month-metrics.md) (the telemetry this path must land). ⚠️ **No requirement states an agent-fleet scale or availability target** — §13 routes that gap; this document does not invent one.

> ⚠️ **Nothing in this document may be implemented as settled (`I4`).** It designs the plane-side half of the `host-local` agent path — the module that terminates agent sessions, the ports through which it reaches the Data Plane, the message and state model, and how the whole thing scales behind a load balancer — so that extracting `agent-gateway` from the Data Plane deployable later is an adapter change, never a business-logic rewrite. `dp-remote` remains the first implementation path and is untouched. Open item **AG-1** / open item **6** (the agent↔plane `.proto` and state machine do not exist) is **not closed here**: this document is the *input* to closing it, and §13 routes the closure.

## 1. Objectives and non-objectives

**Objective.** Make `host-local` agents scalable — many agents, long-lived mTLS sessions, telemetry at fleet rate — without the future extraction of `agent-gateway` from the Data Plane deployable becoming a business-logic rewrite. Concretely: everything that decides *what* happens (generations, intent, outcomes, telemetry meaning, tenant scope) lives in `dp-core` behind ports; everything that decides *how bytes move* (sessions, streams, credits, reconnects, replica ownership) lives in `agent-gateway` and owns no durable business state.

**Non-objectives.** Implementing agents; writing the `.proto`; generating clients; changing `dp-remote`; deciding the broker ACL; deciding human authorization. `dp-remote` must remain independently useful with no Go agent present — nothing in §2–§9 is on `dp-remote`'s path.

**Honest scope of "scalable" in v1.** v1 ships **one** Data Plane deployable and therefore **one** gateway replica (§2.3). Everything in §5 about many replicas — the balancer, the ownership row, the fencing epoch, failover — is designed and *tested* now (the integration harness runs two gateway instances against one `dp-core`) so that the first multi-replica deployment is an extraction, not a redesign. It is not claimed to run multi-replica in v1's packaging.

**Honest scope of the lease and registry mechanisms — and why their machinery is not in this document.** Two mechanisms must exist for the ports (§3.2) and the tests (§8) to name anything: the DP-side lease request ledger and its projection (`AGW-D15`), and the DP-minted replica registry (`AGW-D16`). Both are **separately ratifiable decisions**, and each is gated on something this document does not own: `AGW-D15` ratifies only with the CP issuance contract (§13 AGW-18 — without CP-side idempotency or a status lookup by request id, a timed-out request has no safe recovery that preserves the renewal nonce), and **`AGW-D16` requires §13 AGW-17 *and* §13 AGW-20; its retirement clauses additionally require §13 AGW-19** — AGW-17 is runtime verification of reported replica identities (or the architect group's explicit acceptance of the grammar-bounded residual), AGW-20 is the report-intake contract its ordering, watermark and liveness clauses consume, and AGW-19 is the periodic-report prerequisite silence retirement needs. Their **DDL, SQL, DCL and execution obligations therefore live in their own document** — [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) — which is **explicitly not part of the `AGW-D1`…`AGW-D14` ratification set**. This document states what those mechanisms must *guarantee* (§5.2, §6.1) and reads them as joins; it does not carry their machinery, so ratifying the gateway family implies nothing about their correctness. That split is the round-6 and round-7 reviewers' meta-finding applied rather than acknowledged: a subsystem design of that size, gated on a decision outside the family, must be independently reviewable.

**Success criteria, testable.** (1) The ArchUnit rules in §2.6 hold with planted-violation proofs. (2) The contract-test kit in §3.3 passes against the in-process adapters, and *the same kit* is the acceptance test of any remote adapter. (3) Every failure scenario in §8 has a named test with an observable pass criterion. (4) No sentence in this document claims "enforced", "guaranteed", "bounded" or "refused" without naming the artifact that does it (`L19`).

### 2.1 The five plane modules

      │   │  credits · replica claim │   deliverables    │  session registry · intent rows │    │

`cp-core`, `console-gateway` and `mesh-bridge` are as `BE-D3` describes them. The change is one module, `agent-gateway`, and one rule: **it reaches the Data Plane only through the ports in §3.**

### 2.2 Ownership — what each module owns and may never own

| Module | Owns | May never own |
|---|---|---|
| `dp-core` | All durable Data Plane business state and **every write to `sm_data`**: configuration-of-record, generations, `apply_request` / `apply_step_intent` / `apply_attempt` (`BE-D13`), the **agent identity, fleet epoch, current lease, session-ownership and command-delivery rows** this design adds (§5.2), telemetry ingest and rollups, the lease request/renewal relay to the CP (`SM-D24`), event publication after commit (`BE-D1`) | A gRPC server for agents; a TLS listener on 443; per-connection session state |
| `agent-gateway` | Agent-facing gRPC/mTLS **sessions**; per-session credit windows and in-flight buffers; the **replica-side view** of which agents it owns (a cache of what `dp-core` decided); notification, payload service on pull, ack forwarding, reconnect handling, admission and drain; the L4 readiness endpoint | **Any `sm_data` table, any datasource *injection*, any JPA entity or repository, any bean lookup that could reach one** (§2.6); leases (it relays, it never mints or extends); generations; tenant scope (it forwards a DP-issued session reference, `dp-core` derives the tenant); events (it publishes none); telemetry meaning (it forwards batches, it never normalizes, aggregates or drops samples); any inbound network surface other than the agent port. **Honest scope of "no credential":** in v1 the gateway shares a JVM with `dp-core`, so the *process* necessarily holds the DP datasource; what the design guarantees in v1 is that the *module* cannot reach it (import rules + no bean lookup), and *process-level* credential isolation arrives only at extraction (§9, §12 limit 13) |
| `mesh-bridge` | All broker I/O (`BE-D3`) | Agent sessions. The broker is *not* the agent's transport in v1 (`AGW-D9`) |
| `console-gateway` | Browser sessions, tickets, byte-level `/mesh` proxy (`BE-D3`, `BE-D5`, `BE-D7`) | Agent traffic. The two gateways share a suffix and nothing else: `console-gateway` owns no schema *because it composes both planes' service interfaces*; `agent-gateway` owns no schema *because `dp-core` owns the DP's state*. Neither exemption transfers to the other |

### 2.3 Co-deployment in v1, extraction later

- **v1: one deployable, one `dp-core` instance, one gateway replica.** `agent-gateway` ships inside the single on-prem Data Plane deployable (`BE-D3`'s "one deployable", amended to five modules by `AGW-D1`). The §3 ports are Java interfaces in `dp-api`, implemented in `dp-core`, injected in-process. Because the deployable is one process, *N gateway replicas would be N `dp-core` instances*, which this design does not propose (§12 limit 8) — so v1 has exactly one replica, and the DNS indirection of §5.1 exists so that adding a balancer later reconfigures no agent.
- **Multi-replica arrives with extraction** (§9) — `agent-gateway` as its own deployable scaled independently of the single `dp-core` — or with a separately decided multi-instance Data Plane (routed, §13 AGW-14). The ownership row, fencing epoch, balancer requirements and failover sequence in §5 are designed *now* and exercised *now* by tests that run two gateway instances against one `dp-core` in the integration harness (§8 rows 1–2), so that neither path reopens this document.
- **Independently deployable from day one** means the module boundary is *build-enforced* (§2.6), the ports are *versioned* (§3.4), and the contract tests are *transport-independent* (§3.3). It does **not** mean two processes are shipped in v1.

### 2.4 What must remain DP-owned forever

Whatever is extracted, these never move into the gateway: the decision that a command exists (intent), the generation number, the idempotency key, the apply outcome of record, the tenant of any agent, the lease's issuance and renewal, the telemetry row and its meaning, the trust label on a report, and the audit record. **A gateway that could decide any of these is a second Data Plane.**

## 3. Semantic ports — the gateway ↔ `dp-core` contract

### 3.1 Rules every port obeys

1. **Defined in `dp-api`, implemented in `dp-core`, consumed by `agent-gateway`.** This is the shape `console-gateway` already uses for both planes' service interfaces (`BE-D3`); no new pattern.
2. **Every operation carries a `requestId` and is idempotent under it.** For operations an agent message causes — `claim` from `SessionOpen`, `issue` from `SessionOpen` and `renew` from `LeaseRenew`, `received`/`ack`/`ingest` from their messages — the gateway **derives** the id deterministically from the wire `message_id` (UUIDv5 over `message_id` + operation name), so an agent's wire retry and a gateway's port retry are one request and the gateway needs no durable state to remember ids; ⚠️ **`report` is the one exception and takes the same construction one level down (S6/F1):** an `ActualStateReportBatch` is a *carrier*, so its `message_id` is **transport correlation only and never an idempotency key**, and `report`'s `requestId` is derived **per item** as **UUIDv5 over `agent_id` + `item_id` + the operation name**, where `agent_id` is the **DP-resolved** identity from the `AgentSessionRef` and never a wire field (`I5`) — **the durable report identity is the pair `(agent_id, item_id)`**, because `item_id` alone is minted by each agent independently and two agents both minting `1` would otherwise derive one `requestId` (S7/F1); for gateway-originated operations (`pollDeliverable`, `heartbeat`, `record`) it mints one. A retry after a lost reply returns **its own** original result from a durable arbiter — a token/CSR key for enrolment, the insert-only `claim` ledger (§5.2), the lease grant ledger ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §3), the telemetry watermark — never a code-path guess. **Reports are deliberately absent from that list: they have no durable arbiter at all until §13 AGW-20 closes** (the exception below), so nothing here may be read as promising one (S6/F1). This is what makes the in-process → remote swap safe (§9). Enrolment follows the same rule with its own arbiter: the same token **and** the same CSR replayed returns the stored `Enrolled`; a different CSR or a second distinct request against a consumed token is `TOKEN_CONSUMED`. ⚠️ **ONE EXCEPTION, and it is not yet a guarantee at all (S4/F3): `ActualStatePort.report`.** Rule 2's durable-arbiter promise and rule 4's `COMMITTED` both presuppose a durable arbiter and a transaction that commits it. For every other port this document names one — a token/CSR pair, `agent_claim`, `agent_lease_grant`, a watermark, `agent_command`. For reports it names **none**: §5.2's six tables contain no report row, no report fingerprint, no per-replica freshness watermark and no current-state projection, and §3.5 assigns those facts to `dp-core`'s store, which this family does not specify. **Until §13 AGW-20 closes, `ActualStatePort`'s idempotency and its `Committed` reply are PROVISIONAL**: what the design guarantees today is that the *registry* half of report handling is transactional and idempotent under its own artifacts ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §4), and nothing more. Its §3.3 contract kit and its §9 remote-adapter conformance are provisional for the same reason and must not be read as settled. **Read-only operations (`resolve`, `current`) are re-evaluated on replay and are not ledgered** — they write nothing, so they bear no idempotency and claim none; a `current` reply is a snapshot of a projection that may legitimately have changed by the next call, and `NONE` is not a stored outcome. The session-resolution flow's idempotency is therefore the claim ledger's, plus the lease ledger's for any `issue` or `renew` that flow causes.
3. **Every operation that writes agent-bound state carries the `AgentSessionRef` that `claim` returned** — `{agentId, fencingEpoch}`, DP-issued, opaque to the gateway, **carrying no tenant** — on `heartbeat`, `renew`, `pollDeliverable` (which is itself a fenced write), `pull`, `received`, `ack`, `report`, `ingest` for the `AGENT` source, and `record` for agent-bound audit events. `dp-core` derives the tenant from `agentId` (globally unique by the `agent_identity` constraint in §5.2) and refuses an epoch lower than the current one with `STALE_EPOCH`. The check is *in the write statement*, not a pre-check (§5.2 shows the shape). ⚠️ **For `report` that promise had no implementing statement until S7/C1** — the registry transaction locked the identity row (revocation only) and joined `agent_session` nowhere — so its fence is now [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §4's **A1**, the same `WITH s … FOR SHARE OF se` shape, with every Phase B statement re-checking the predicate rather than trusting that A1 ran; **(L17)** is the obligation. **The port contract is therefore self-sufficient**: a remote adapter needs no caller-supplied tenant and no process-local memory to implement the fenced write. Read-only operations (`resolve`) and enrolment (which precedes any session) carry no ref; `current` carries one because its answer is session-scoped, but it writes nothing.
4. **Replies are explicit about durability.** `COMMITTED` means the enclosing `dp-core` transaction committed. The gateway never assumes it shares a transaction with `dp-core`, because after extraction it does not.
5. **Batch-shaped where volume exists, and a report batch MAY carry several replicas (S5/F3).** Heartbeats and telemetry are batched per session; **reports travel in an `ActualStateReportBatch` per session, which may contain items for more than one replica of more than one binding** — the earlier "batched per replica" reading is withdrawn, because §8 row 6 requires exactly the two-replica batch it forbade. Commands and claims are single. **Two responsibilities, deliberately not one id (S5/F3):** the batch message carries its own `message_id`, which exists for **transport correlation** — it is what the reply's `in_reply_to_message_id` names — and it is **not** an idempotency key for the reports inside it; **idempotency is PER ITEM**, keyed by `(agent_id, item_id)` — the per-item `requestId` rule 2 derives from the DP-resolved `agent_id` and the item's `item_id` (S7/F1) — so a retried batch must replay its already-committed items and apply only the uncommitted ones, never duplicate a committed sibling. Where a port operation takes a batch, rule 2's `requestId` is derived **per item** and there is no batch-level `requestId` at all: the `ActualStateReportBatch` message's `message_id` is transport correlation and nothing else (S6/F1).
6. **No port carries a secret value the gateway must interpret.** Rendered configuration passes through `CommandPayload` as opaque bytes plus hash (§7.3).
7. **In-memory callbacks are never the sole contract.** The command feed (§5.4) is a **durable poll loop** the gateway runs over `dp-core`'s deliverable index; an after-commit wake-up is a latency optimisation that may be missing, late or fire in a different process without any command being lost.

### 3.3 Contract tests — one kit, every adapter

Mirroring the publisher contract-test kit `BE-D10` introduced (`backend-consumption.md` §5.2): **seven of the nine ports — the implementation-ready ones —** ship an **abstract JUnit kit** in `dp-api`'s test-jar — `EnrollmentPortContract`, `SessionRegistryPortContract`, … — that a concrete test extends by supplying an adapter. The kit asserts the semantics in §3.1 and §5.2: for the **six mutation-bearing** ports, retry-under-same-`requestId` returns the original result; for the **one read-only** port, `AgentIdentityPort`, the kit asserts the **opposite** — `resolve` is **re-evaluated on every call and never replayed from a cached result**, so an identity revoked between two calls with the same `requestId` **resolves as revoked on the retry** (S6/F5; caching it would turn a revocation into a live identity); stale epoch is refused *and* nothing was written; `claim` is monotonic and exclusive under concurrency and refuses a revoked identity; `ingest` replay is a no-op; a lost reply followed by a retry yields exactly one row; `pollDeliverable` returns a command committed by another `dp-core` transaction within one poll interval. **For those seven, the in-process adapters pass the kit in v1 and the remote adapters pass the identical kit at extraction**, and a remote adapter that needs a different test is a semantic change the design forbids (§9). ⚠️ **`ActualStatePort` and `AgentAuditPort` are the two exceptions (S5/F4):** each may define a **provisional interface shape** — and does, in §3.2 — but neither can ship a **complete durability kit** or claim remote-adapter conformance, because a kit can only assert an arbiter and a transaction boundary that exist, and theirs are §13 **AGW-20** and **AGW-21**. What they may have meanwhile is a shape test (types, required fields, per-item correlation); what they may not have is a durability or idempotency conformance claim.

### 3.4 Versioning

`dp-api` declares `AgwPortsVersion` (an integer constant plus a `@Since` annotation per operation). In-process it is a compile-time fact — in v1's single JVM the window is trivially satisfied, and the rule exists for extraction. Remotely the gateway sends it on every call and `dp-core` supports `[N-1, N]` during a rolling upgrade, refusing older with `PORT_VERSION_UNSUPPORTED`. The wire encoding of the ports (a `.proto` or OpenAPI under `contracts/`) is **not written here** — it is an extraction-time artifact and would be a reviewed contract change (§9).

### 3.5 How the agent path meets the apply engine

`BE-D12`'s `RuntimeAdapter` is the seam. `dp-core` gains an `AgentDispatchAdapter` implementation. The six operations map as follows — **not** all of them become wire commands:

| `RuntimeAdapter` operation | On the agent path | Why |
|---|---|---|
| `prepare(placement, G)` | inserts an `agent_command` row with `operation = preflight` per replica and returns **`IN_FLIGHT`**; the agent runs its pre-flight ([`../../go-agent/design.md`](../../go-agent/design.md) §5.1) and acks with a structured `PreflightResult` in `detail` | pre-flight inspects the host; only the agent can |
| `materializeConfig(replica, G)` | `agent_command{operation = apply}` → `IN_FLIGHT`; completion via `CommandAckPort` | the agent writes the bytes |
| `startOrUpdate(replica, G)` | `agent_command{operation = restart}` → `IN_FLIGHT` | the declared lifecycle verb, on explicit command only (`AG-D3`) |
| `stop(replica)` | `agent_command{operation = stop}` → `IN_FLIGHT` | as above |
| `status(replica)` | **never a command.** Reads `dp-core`'s canonical per-replica actual-state projection defined by §13 `AGW-20`, together with `Heartbeat` facts (persisted generation, effective hash, start baseline, liveness), and returns them as `RuntimeStatus`; if the newest applicable fact is older than the health-gate deadline it returns `UNKNOWN`. Until `AGW-20` closes, this row defines required behaviour but no persistence artifact. | `status` is the engine's read-only poll, called repeatedly and during resume ([`../eda-walking-skeleton.md`](../eda-walking-skeleton.md) §2.1); a command per poll would need an intent row it does not have and would be unbounded write amplification |

**`IN_FLIGHT` is an extension of the adapter contract, and the engine gains one wait state.** `eda-walking-skeleton.md` §2.1 describes the operations synchronously; on the agent path an attempt row exists with no outcome until the ack arrives. **Resume rule (the engine's, stated here because the agent path creates the case):** an `apply_attempt` whose step has a live non-terminal `agent_command` row (`QUEUED`, `OFFERED` **or `DELIVERED`** — every non-terminal state) resumes as **awaiting completion** — the command is durable and will be re-notified on the agent's next session — and is *not* driven toward `APPLY_INDETERMINATE` by `BE-D13`'s "attempt with no outcome" reading. §8 row 20 tests it. The state ladder, fences, watermarks and idempotency rules are otherwise untouched.

⚠️ **Impact notice to `BE-D12`/`BE-D13`'s owners (§11):** the `IN_FLIGHT` return, the awaiting-completion resume rule and the `preflight` operation are extensions, not forks. If the owners prefer a distinct asynchronous adapter interface, the mapping above is unchanged; only the Java shape moves. ⚠️ **The Java shape has since moved, by `BE-D21`** (2026-09-11, [`../decisions.md`](../decisions.md)): the seam's literal signature now takes `TargetReplica` rather than `ReplicaRef`, and `materializeConfig` additionally takes a caller-owned `RenderedConfig`. The operation names, their scoping and this mapping are unchanged — the rows above are written in the abbreviated `(replica, G)` prose form precisely because they map behaviour, not parameters — but an `AgentDispatchAdapter` implements the `BE-D21` signature, not the one `BE-D12` §2.1 prints.

## 4. Agent protocol — message and state model

**Design the model first; the `.proto` follows it.** No `.proto` is written in this document, by instruction and because open item 6 / `AG-1` is the architect group's to close. Every message below is a *named shape with named fields*; the fork branch's surrogate wire (`origin/dev/go-agent:go-agent/docs/p2-wire-assumptions.md`, non-authoritative) was read as prior art and is cited where a choice answers one of its open questions.

### 4.1 Transport binding — `B/D16` is the bound

| `B/D16` clause | This design |
|---|---|
| gRPC/HTTP2 bidi over mTLS on 443, agent-initiated | One TLS connection per agent, agent-initiated, to a single published DP endpoint (a DNS name; in front of the L4 balancer when there is one, §5.1). The gateway terminates mTLS and **requires** a client certificate for everything except `Enroll` |
| transport-agnostic message set | §4.3 is a message catalogue, not an encoding. gRPC is the v1 binding; the deferred HTTP/1.1 long-poll fallback would bind the *same* catalogue |
| Enroll → Session → Steady state → Teardown | §4.2 |
| single-use target-bound token → CSR → CA-signed cert | §4.5, via `EnrollmentPort` |
| revocation active and lease-bounded; cert rotation manual v1; lease bounds authority | §4.6; the gateway never extends authority |
| apply crash-safe and idempotent | agent side: `AG-D4`; plane side: §4.7 and `BE-D13` |

**Three RPCs on the one connection**, as separate HTTP/2 streams:

| RPC | Shape | Carries |
|---|---|---|
| `Enroll` | unary | `EnrollRequest` → `EnrollResponse` \| `Error`. The only RPC accepted **without** an issued agent certificate; the enrollment token travels as call metadata and the server certificate is pinned or trusted via the install-time bundle (§4.5). **Admission-limited** (§5.6) |
| `Connect` | bidirectional stream | everything in §4.3 except telemetry |
| `Telemetry` | bidirectional stream | `TelemetryBatch` ↑ · `TelemetryAck` / `TelemetryCredit` / `TelemetryReject` ↓ (§4.10). Opened only after `SessionAccept` |

**What stream separation does and does not buy.** HTTP/2 multiplexing removes *application-level* head-of-line blocking between the two streams — a 64 KiB telemetry batch mid-flight does not delay a `Revoke` at the gRPC layer. It does **not** remove connection-level flow control (RFC 9113 applies it per stream *and* per connection) or TCP head-of-line blocking after a lost segment. Mitigation, stated as a limit: outstanding telemetry bytes per connection are capped by credits (`credits × max_batch_bytes`, §5.5) at **no more than half** the connection-level window the gateway advertises, so telemetry alone can never exhaust the connection window; TCP loss remains a shared fate for all streams and bounds how fast a `Revoke` can land on a lossy path (§12 limit 10). The alternative — a second TLS connection for telemetry — doubles session state, reconnect surface and identity checks; rejected in `AGW-D5`.

### 4.2 Phases and the gateway-side session state machine

The **agent's authority machine** (`ACTIVE`, `RENEW_DEGRADED`, `LEASE_EXPIRED`, `REVOKED`, `CLOCK_SUSPECT`, `ADMISSION_BLOCKED`, `RE_ENROLL_REQUIRED`) is `SM-D28`'s and is specified in [`../../go-agent/design.md`](../../go-agent/design.md) §4.2. The gateway does not reimplement it; it **observes** the lease state `dp-core` returns and enforces one rule from it: **no `GenerationAvailable` is sent unless the agent's lease is `ACTIVE` and admission holds** (§4.6).

The gateway's *own* per-session machine is small and entirely about the connection:

```
 CONNECTING ──TLS ok (client cert present)──────────────► ADMITTING
 ADMITTING ───token bucket ok─────────────────────────────► IDENTIFIED   (AgentIdentityPort.resolve)
 ADMITTING ───bucket empty──► SessionReject(ADMISSION_LIMITED, retry_after) → CLOSED   (no port call made)
 IDENTIFIED ──UNKNOWN / revoked / version unsupported────► REFUSED → CLOSED
 IDENTIFIED ──SessionOpen → SessionRegistryPort.claim────► ACTIVE       (epoch e)
 ACTIVE ──────lease: current() → else issue() if never granted → else the agent must LeaseRenew first (§4.6)
 ACTIVE ──────lease expired and its renewal refused ─────► SessionReject(RE_ENROLL_REQUIRED) → CLOSED
 ACTIVE ──────Drain (planned restart) ────────────────────► DRAINING → CLOSED
 ACTIVE ──────port reply STALE_EPOCH / heartbeat says superseded ─► STALE → Error(SESSION_SUPERSEDED) → CLOSED
 ACTIVE ──────heartbeat says revoked ────────────────────► Revoke → CLOSED
 ACTIVE ──────stream error / keepalive miss ─────────────► CLOSED       (release best-effort; the next claim supersedes)
 CLOSED ───────────────────────────────────────────────────  no state remains on the replica
```

**Every transition into `CLOSED` — from `ACTIVE`, `DRAINING`, `STALE`, `REFUSED` or an admission reject — runs one teardown routine** that returns the session's unspent telemetry credits to the replica's budget immediately and returns each in-flight batch's bytes when its port call completes (§5.5). Session churn therefore cannot strand budget; §8 row 28 tests it.

Admission precedes identity resolution so a storm costs no port calls (§5.6). Every state has an exit; `STALE` exists so the replica *tells the agent* it has been superseded instead of silently dropping it, which would look like a network fault and provoke a reconnect storm toward the wrong replica. Supersession and revocation are **different exits with different agent behaviour** — reconnect versus stop-and-discard — and the heartbeat reply distinguishes them (§3.2).

### 4.4 Ordering, duplicates and stale generations

1. **Per binding, notices are sent in ascending `generation`**, one outstanding `apply` at a time; `stop` may interleave (the `BE-D13` stop exemption, unchanged); `preflight` precedes the `apply` of the same generation.
2. **A `GenerationAvailable` whose `generation` is below the binding's DP watermark is never sent** — `dp-core` refuses to enqueue it (`apply_generation` monotonicity, `BE-D13` §2.2 rule 1). The agent independently refuses a lower generation (`AG-D4`); both checks exist, neither is "the" check.
3. **Duplicate notices and re-pulls are expected** (re-notification after failover, §5.3). The agent's rule holds: same `idempotency_key` + same `config_sha256` → no-op re-report; same key + different hash → `REFUSED(KEY_HASH_MISMATCH)` and `dp-core` records a protocol error against the command (it is a DP bug, never resolved by retry).
4. **Duplicate acks are harmless**: `CommandAckPort` returns `DUPLICATE` and writes nothing.
5. **`REFUSED`** covers the agent declining a command it may not execute — out-of-scope binding, lease not `ACTIVE` on receipt, admission failed on the agent side (`ADMISSION_BLOCKED` surfaces here as `detail.code`, so it is an *ack detail*, not a session state — fork M1), key/hash mismatch. The gateway forwards it; `dp-core` moves the command to `REFUSED` with the code and the apply step to its `BE-D13` failure path. **A missing capability is not the agent's refusal to make:** `dp-core` refuses such a command itself, before any notice, as `REFUSED(CAPABILITY_MISSING)` — a DP authorization outcome, recorded and audited as such, never an agent failure (§4.6).
6. **Delivery is at-least-once; execution is at-most-once per `(generation, idempotency_key)`.** The first is the gateway's property; the second is the agent's (`AG-D4`) and the DP's (`apply_step_intent` UNIQUE, `BE-D13`). Neither module claims the other's half.
7. **A `pull` for a `SUPERSEDED` command returns `SUPERSEDED`**, and the agent records that outcome without acting.
8. **Delivery and outcome are two acks.** `CommandReceived` moves the row `OFFERED → DELIVERED` and releases nothing in the apply engine; only `CommandAck` (terminal) moves it to `ACKED`/`REFUSED` and advances the step. A `DELIVERED` command is still re-notified on reclaim (the agent's journal answers from `RECEIVED` onward), and a terminal ack is accepted from `OFFERED` as well as `DELIVERED`, because the delivery ack may be lost.

### 4.5 Enrollment, identity and tenant/target binding

- **Bootstrap trust.** The install runbook ships the agent a `connect_endpoint` and the DP server trust bundle (or a pin) alongside the single-use enrollment token; the token is **target-bound** at issue (`B/D16`, `B/D7`). The `Enroll` RPC is the only path a certificate-less connection may take; anything else on such a connection is `Error(UNAUTHENTICATED_IDENTITY)` and the connection closes. `Enroll` is admission-limited per source address and capped per token (§5.6), because it is the one unauthenticated surface.
- **Identity mapping.** After enrollment, identity is the **certificate thumbprint** — `AgentIdentityPort.resolve(thumbprint)` returns the agent's `tenantId`, `targetId`, `bindingIds`, both epochs, capabilities and revocation status. **The wire never carries a tenant** and the gateway never parses one (`I5`). `assigned_target_id` on `SessionAccept` is the DP telling the agent what it is, not the agent claiming.
- **Revocation checks** run inside the **claim statement** (§5.2 — a revoked identity cannot claim), on every lease renewal, and on every `heartbeat` batch reply (`revoked[]`), so a revoked agent is disconnected within one heartbeat interval even if its lease has time left (`B/D16` "active"), and cannot reconnect.
- **Certificate lifecycle.** Manual rotation for v1 (`B/D16`); trust bundle rotation with overlapping validity via `TrustBundleUpdate`. Re-enrolment (`RE_ENROLL_REQUIRED`) is a new token issued by an operator, never an agent-initiated renewal — the gateway has no path to mint identity.

### 4.6 Lease handling and expiry mid-apply

The gateway **relays** `LeaseRenew` to `LeasePort.renew` and returns the `LeaseGrant`. It does not compute expiry, extend a lease, or cache a grant beyond the session. Rules:

- **`SessionOpen` lease resolution — three cases, and `SM-D28`'s nonce semantics are preserved in all three** (`AGW-D7` amends the `audience` and epoch claims and *nothing else*; `AGW-D15` owns the store, whose mechanism is [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md)). After `claim`, the gateway calls `LeasePort.current(session)` — **a read that writes nothing** (§3.1 rule 2). (1) **A live lease** — an unexpired projection bound to the identity's certificate — is returned as is, no CP call, and `SessionAccept` carries it (the failover case). (2) **No lease has ever been granted** — `dp-core` finds no `agent_lease` row at all, the durable "never granted" test, since projection rows are never deleted on expiry — and the gateway calls `LeasePort.issue`, the one no-nonce grant in the protocol, taken on the strength of the mTLS-proven identity and the CP's enrolment approval. A second `issue` for the same identity is refused **`ISSUE_NOT_ALLOWED`** by two artifacts, not by a code path: the `agent_lease` row's existence, which no retention deletes, and a partial unique index over the ledger, which refuses concurrent first-issues under *different* request ids but is itself pruned with the ledger row. **The one identity those two do not cover** — a first `issue` that ended `FAILED`, so nothing was projected — re-opens after `ledger_retention`; that is §12 limit 19a, not a claim of closure. (3) **A lease exists but has expired**: `issue` is **not** available, because a second no-nonce grant would bypass `SM-D28`'s single-use renewal nonce. The gateway sends `Error(LEASE_RENEW_REQUIRED)` and waits; the agent — already in `LEASE_EXPIRED` ([`../../go-agent/design.md`](../../go-agent/design.md) §4.2) — sends `LeaseRenew` presenting its last grant's nonce, and `SessionAccept` follows the resulting grant. If the CP refuses that nonce (consumed or unknown), the session is refused **`SessionReject(RE_ENROLL_REQUIRED)`** — the state the agent design already carries, meaning an operator-issued token, never an agent-initiated recovery. No path in this protocol issues a nonce-free grant to an identity that has held one (§8 rows 32, 40). **And no gateway crash strands a renewal:** the agent's next session resends the same `LeaseRenew`, whose derived `requestId` is the same, and the request is **adopted into the new epoch** rather than refused (§8 row 42) — the recovery `SM-D28`'s single-use nonce makes mandatory.
- **Offer gate** (the plane's mirror of the agent's admission rule, [`../../go-agent/design.md`](../../go-agent/design.md) §4.3): `GenerationAvailable` for `operation` is sent only if the agent's lease is `ACTIVE` as of the last `LeaseGrant`, **the lease's `capabilities[]` contains the operation's required capability** (`apply-config` for `preflight`/`apply`; `lifecycle` for `restart`/`stop` — `AG-D3`, `SM-D28`), **and** `expires_at − now ≥ verb_ceilings[operation] + admission_margin`, using the gateway's clock corrected by the last computed offset. The capability **and scope** halves are enforced **first in `dp-core`, against a durable record, inside the poll itself**: `agent_command` carries `required_capability`, `target_id` and `binding_id` from admission; the lease `dp-core` relayed is persisted as the agent's `agent_lease` row (`AGW-D15`; mechanism: [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §2.2) at every `LeasePort.renew`, **with the ceilings and margin it delivered**; `CommandFeedPort.pollDeliverable` is one fenced statement that joins the ownership row and that lease row and stamps only commands whose capability the lease grants, whose target equals the lease's, whose binding the lease still names, whose remaining time clears the lease's *stored* ceiling plus margin, and whose epochs and certificate binding are current; a command the lease cannot authorize is moved to `REFUSED(CAPABILITY_MISSING | TARGET_MISMATCH | BINDING_NOT_IN_LEASE)` by `dp-core` before any notice — so a `report-only` agent never sees a `restart`, a command for a binding the lease dropped is never offered, and the apply step records a DP authorization refusal, not an agent failure. `pull` re-checks the same predicates. Because the record is a row and the time inputs are its snapshot, a `dp-core` restart reconstructs nothing (§8 rows 27, 29). With no current lease row, nothing is offered. The time half is enforced in the gateway's notify path. **Tested** by `OfferGateTest` and `CapabilityGateContract` (§8 rows 4, 23). The agent's own checks stand; the gate exists so the plane does not offer what the agent must refuse.
- **Renewal failure:** the gateway forwards `Refused` as `Error(LEASE_RENEW_REFUSED)`; the agent enters `RENEW_DEGRADED` and, at `expires_at`, `LEASE_EXPIRED` — both agent-owned (`SM-D28`, [`../../go-agent/design.md`](../../go-agent/design.md) §4.2). The gateway stops notifying at `Refused`, not at `expires_at`.
- **Expiry mid-apply:** the plane's part is to **label**, not to intervene. `ActualStatePort` and `CommandAckPort` calls arriving after `expires_at` on the **same** mTLS session are still accepted — the session still authenticates the agent; the separate report-only credential the agent design wants for this state (§3.1 there) is not issued in this draft and is routed (§13 AGW-12, §12 limit 16) — and `dp-core` labels the resulting rows **untrusted** (§4.8). The apply step's resolution follows `AG-D5` (deterministic replay on the next `ACTIVE` session) and `BE-D13`'s `APPLY_INDETERMINATE` handling. No new state.
- **Audience and epochs.** `LeaseGrant.audience` names the **logical Data Plane** and the grant carries **two** revocation epochs (`AGW-D7`, flagged against `SM-D28` §0.1). Replica ownership is the fencing epoch's job, not the lease's.

### 4.7 Command delivery — intent before delivery, notify before pull

```
 console/API ─► dp-core apply engine (BE-D13) ─► apply_step_intent row (durable, UNIQUE key)
                                                  │  AgentDispatchAdapter (§3.5) → IN_FLIGHT
                                                  ▼
                                    agent_command row: QUEUED  (durable, tenant-keyed)
                                                  │  CommandFeedPort.pollDeliverable (owning replica, §5.4)
                                                  ▼
                              gateway r_k ─ GenerationAvailable ─► agent      agent_command: OFFERED (epoch e)
                              gateway r_k ◄─ CommandPull ─────────── agent
                              gateway r_k ─ CommandOffer (bytes) ──► agent      (CommandFeedPort.pull, session e)
                              gateway r_k ◄─ CommandReceived ─────── agent      agent_command: DELIVERED (CommandAckPort.received — non-terminal)
                              gateway r_k ◄─ CommandAck(APPLIED | …) ─ agent
                                                  │  CommandAckPort.ack(…, session e)
                                                  ▼
                                    agent_command: ACKED ─► apply engine leaves the wait state (BE-D13)
```

**Rules.** (1) No notice without a committed intent row and a committed command row (`BE-D13` §2.2 rule 0, write-before-act, extended one hop), **and no notice for a command whose `required_capability` the current lease lacks** (§4.6). (2) The command row copies `generation` and `idempotency_key` from the intent so the agent's journal and the DP's arbiter are keyed identically. (3) A command stays `OFFERED` or `DELIVERED` until terminally acked; on reclaim by another replica **every `QUEUED`/`OFFERED`/`DELIVERED` command for that agent is re-notified** (§5.3). (4) `SUPERSEDED`: when a newer generation is admitted for the binding, `dp-core` marks earlier un-acked commands `SUPERSEDED` — from `QUEUED` or `OFFERED` — and the gateway withdraws them; a pull or ack for a superseded command is answered `SUPERSEDED` and recorded as such (the agent's replay flavour, [`../eda-walking-skeleton.md`](../eda-walking-skeleton.md) §3.5). (5) Command payload is **rendered bytes + `config_sha256`**, rendered by `dp-core` with `secretRef` resolved at render time (`I6`; [`../../go-agent/design.md`](../../go-agent/design.md) §5.1); the gateway neither inspects nor persists it and only ever holds it between `pull` and the `CommandOffer` write to the stream (§7.3). (6) Operations are `preflight`, `apply`, `restart`, `stop` — CHECK-carried (§5.2); no scheduling verb.

### 4.8 Reports and the trust label

Reports arrive on the `Connect` stream. `dp-core` computes `trust ∈ {TRUSTED, UNTRUSTED}` from **its own record** of the agent's lease state **at the time the port call is received**, from the call's fencing epoch, **and from the report's scope against the current `agent_lease` row**: lease `ACTIVE`, epoch current, `binding_id ∈ binding_ids[]` and the binding's target equal to the lease's → trusted; anything else → untrusted (with the reason — `LEASE_NOT_ACTIVE`, `STALE_EPOCH`, `BINDING_NOT_IN_LEASE` — returned beside the label; durable persistence is the open §13 `AGW-20` contract, §8 row 29), "may never satisfy a convergence gate" ([`../../go-agent/design.md`](../../go-agent/design.md) §4.4). The agent's `sent_at` plays no part — an agent that backdates a report cannot move it into an earlier `ACTIVE` window. The agent does not set the label and the gateway does not compute it, so neither a compromised agent nor a stale replica can launder a report. `restart_observed_at` is the load-bearing field (`SM-D15`'s manual default depends on it); it is accepted only from a trusted report.

**Trust and freshness are two dimensions, not one (S3/F2).** `trust` answers *may this report be believed?* and is computed from the lease, the epoch and the scope **only** — nothing about a report's *content or ordering* moves it. A separate **`disposition` ∈ {`APPLIED`, `STALE`, `REFUSED(reason)`}** answers *did it carry anything new, and was it acted on?*, and the two are orthogonal: a report from a live, in-scope agent that merely arrives out of order is **`TRUSTED` and `STALE` at once**. The registry's refusals ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §4 — `REPORTER_DISPLACED`, `REPLICA_CAP_EXCEEDED`, and its own `STALE`) are therefore **dispositions and never trust verdicts**. `ActualStatePort` binds **replay** identity to the pair **`(agent_id, item_id)`** — the **DP-resolved** agent identity (`I5`) and the item's own id — from which the per-item `requestId` is derived (§3.1 rule 2's `report` exception, §3.2); the enclosing `ActualStateReportBatch`'s `message_id` is **transport correlation only and never a replay identity**, and `sequence` is **never** one either; `sequence` is a **freshness** hint whose watermark is scoped per `(agent, binding, replica)`, so one replica's counter cannot suppress another replica's state, and whose cross-restart behaviour is unresolved (§13 AGW-20, S5/F1). **The durable report row, per-replica freshness watermark and canonical current-state projection are not specified in this design set.** Their contract must maintain freshness independently for each `(agent, binding, replica)` and make `status(replica)` and convergence read only the current projection for that replica; unless a future protocol explicitly makes each sequence a complete atomic binding snapshot, a watermark scoped only to `(agent, binding)` is forbidden. §8 rows 6 and 43 state the required no-regression behavior, but do not pretend to provide its missing persistence artifact. The owner, transaction boundary and tests are tracked by §13 `AGW-20`; until it closes, report intake, `status(replica)` and report-driven convergence are not implementation-ready. The registry's own decisions remain complete using their separate per-activation watermark.

### 4.9 Heartbeat, keepalive and clock

- **Two different signals.** HTTP/2 keepalive (gateway-configured `keepalive_interval`) detects a dead TCP path; `Heartbeat` (agent-sent at `heartbeat_interval`) carries the `B/D2` Detect payload. Missing keepalive → the gateway closes the session; missing heartbeats → `dp-core` marks the agent `last_seen_at` stale and the Governance view investigates across agent / node / broker / cert / ingest / clock ([`../../architecture.md`](../../architecture.md) §10). Keepalive is **not** lease renewal (fork N3).
- **Clock.** Every ↑ message carries `agent_clock`; `HeartbeatAck` and `LeaseGrant` return `server_clock` and the computed `clock_offset_ms`. If `|offset| > skew_tolerance` (delivered on `SessionAccept.limits` — answering fork `:131`), `clock_state = SUSPECT` and the agent enters `CLOCK_SUSPECT` (`SM-D28`); the gateway stops notifying. **Ordering, trust and admission never use the agent's wall-clock** (`B/D15`): generations order commands, `batch_seq` orders telemetry, `sequence` orders reports, and trust is decided at receive time (§4.8). ⚠️ **One exception, and it is the only one:** the retired-incarnation acceptance window of §6.1 compares the agent's own `NormalizedSample.ts` against a DP-recorded interval, because the case it admits — a disk buffer flushed across a restart (`AG-D9`) — *is* a claim about the past that only the sample can carry. That narrowing, and the backdating it leaves open, are stated in §6.1 and carried as §12 limit 20; nothing else on this path reads the agent's clock.
- **Heartbeat writes are batched per replica**: the gateway calls `SessionRegistryPort.heartbeat` once per `heartbeat_interval` with every agent it owns; one statement updates them all. No per-agent write per heartbeat.

### 4.10 Telemetry stream — credits are the backpressure, and they can always recover

- The gateway grants `initial_credits` on `SessionAccept` — **reserved from the replica's budget at grant time, and zero when the budget cannot cover one batch** (a session may be accepted with no credit and wait for `TelemetryCredit`); each `TelemetryBatch` consumes one; each `TelemetryAck` returns `credits_granted` (normally one, zero when the replica's memory budget is tight, §5.5). **An agent with zero credits does not send** — it buffers on disk (`AG-D9`). This is the whole backpressure mechanism; there is no second one, and no grant is ever made that the budget has not already reserved.
- **Recovery from zero.** Because credits are only *returned* on acks, a session driven to zero under budget pressure could never speak again — so the ledger also issues **unsolicited `TelemetryCredit`** grants as budget frees (on any ack to any session that releases bytes, and on a periodic sweep at `heartbeat_interval`), round-robin over sessions at zero. §8 row 19 tests recovery.
- `TelemetryAck` is sent **only after** `TelemetryIngestPort` returns `Committed`. The `high_watermark_seq` is durable; on reconnect the agent resumes from it (`SessionOpen.resume`), so at-least-once delivery with dedupe by `(producer, stream_id, batch_seq)` gives exactly-once *storage* (§6.2).
- `gap_markers` are the agent's honest account of what it dropped (`AG-D9` drop-oldest, counted); `dp-core` stores them as gap records so freshness is never inferred from absence ([`../../architecture.md`](../../architecture.md) §10 "no zero-fill ever").

### 4.11 Errors — a closed enum

`UNAUTHENTICATED_IDENTITY` · `IDENTITY_REVOKED` · `TOKEN_CONSUMED` · `PROTOCOL_VERSION_UNSUPPORTED` · `UPGRADE_REQUIRED` · `CAPABILITY_MISMATCH` · `CAPABILITY_MISSING` · `BINDING_NOT_IN_LEASE` · `TARGET_MISMATCH` · `LEASE_KEY_MISMATCH` · `GRANT_INVALID` · `REQUEST_ID_REUSED` · `REQUEST_EXPIRED` · `IN_PROGRESS` · `LEASE_RENEW_REQUIRED` · `RE_ENROLL_REQUIRED` · `ISSUE_NOT_ALLOWED` · `REPLICA_REF_INVALID` · `REPLICA_CAP_EXCEEDED` · `REPORTER_DISPLACED` · `UNDECLARED_LABEL` · `LABEL_INVALID` · `UNKNOWN_REPLICA` · `INCARNATION_RETIRED` · `ADMISSION_LIMITED` · `SESSION_SUPERSEDED` · `LEASE_RENEW_REFUSED` · `STALE_GENERATION` · `UNKNOWN_COMMAND` · `SUPERSEDED` · `KEY_HASH_MISMATCH` · `TENANT_MISMATCH` · `PAYLOAD_TOO_LARGE` · `OUT_OF_CREDITS` · `CLOCK_SUSPECT` · `DRAINING` · `INTERNAL_UNAVAILABLE`.

Each carries `retry_after` where retry is meaningful and never where it is not (`IDENTITY_REVOKED`, `UPGRADE_REQUIRED`, `KEY_HASH_MISMATCH`, `TOKEN_CONSUMED`, `RE_ENROLL_REQUIRED`, `ISSUE_NOT_ALLOWED` — the remedy is an operator's token, not a wait; `LEASE_RENEW_REQUIRED` carries none either, because the next action is the agent's `LeaseRenew`, not a retry). Authorization failures return the code and nothing else — no hint whether the target exists (`B/D8`, no enumeration) — and are audited via `AgentAuditPort` (§7.7). The enum is **versioned with the protocol** (§4.12); adding a code is a minor version, removing one is not allowed.

### 4.12 Protocol versioning and the compatibility window

- `SessionOpen.protocol_version` is a single integer; `EnrollRequest.protocol_versions_supported[]` lets enrolment fail early. The gateway supports **`[N−1, N]`** — a rolling agent upgrade never needs a flag day, and an agent two versions behind gets `SessionReject(PROTOCOL_VERSION_UNSUPPORTED, min_agent_version)`.
- **Capabilities are a closed, versioned enum** (`apply-config`, `lifecycle`, `report-only`, plus what `AG-D*` adds) — never free strings (fork M6). `required_capabilities[]` on `SessionAccept` comes from the target's package (`B/D10`); a mismatch is `CAPABILITY_MISMATCH` with the missing set, and the target is marked "agent upgrade required" in Governance.
- **`min_agent_version`** is a per-target value from the Solution Package (`B/D10`) surfaced by `dp-core`; the gateway compares and rejects with `UPGRADE_REQUIRED`. Agent self-upgrade is deferred (the register's deferred list) and `AG-10` owns the skew question on the agent side.
- **Wire evolution rules** for the eventual `.proto`: fields only added, never renumbered or retyped; enums only appended; a removed behaviour becomes a rejected code, not a missing field. These are stated now so the `.proto` author inherits them (§13).

### 4.13 Reconnect and replay

On `SessionOpen`, the agent sends `resume` — per binding its last acked generation, per telemetry stream its last acked `batch_seq` — as a **hint**. After `claim`, the gateway (a) polls `CommandFeedPort` and re-sends `GenerationAvailable` for every `QUEUED`/`OFFERED`/`DELIVERED` command of the agent that the lease permits (the DP's cursor wins over the agent's; the agent's journal makes duplicates safe; the agent pulls what it does not already hold), (b) sends `TelemetryAck{high_watermark_seq}` per stream so the agent trims its disk buffer to the durable watermark, (c) grants `initial_credits`. Reconnect backoff and jitter are the agent's (`AG-5`); the gateway's contribution is `retry_after` on every refusal and `Drain.reconnect_after` on planned restarts.

## 5. Scaling and high availability

**Applies from the first multi-replica deployment (§2.3).** In v1 there is one replica; everything here is designed and tested now so that the second replica is an operations event, not a design event.

### 5.1 The load balancer — requirements, not a product

| Requirement | Why | Failure if violated |
|---|---|---|
| **Layer 4, TCP passthrough, no TLS termination** | the gateway needs the client certificate; a re-terminating L7 balancer would forward identity in a header — client-supplied tenant input (`I5`) | identity spoofable by anything that can reach the balancer's back side |
| One stable DNS name (`connect_endpoint`) → the balancer VIP (v1: → the single replica) | agents are configured once (`B/D1`); replicas come and go | reconfiguring every agent on every scale event |
| Idle timeout **>** `keepalive_interval` × 3 | long-lived streams must not be cut by the balancer between keepalives | periodic mass reconnects that look like a storm |
| **Health check** = TCP connect to a **readiness port** the gateway opens only after `SessionRegistryPort` answered a probe. The port speaks nothing and returns nothing — it is a socket accept, not an API | a replica that cannot reach `dp-core` must receive no agents | agents connect, claim fails, they retry — a self-inflicted storm |
| Connection draining honoured on replica removal | §5.6 `Drain` needs the balancer to stop *new* connections while existing ones finish | in-flight acks lost, re-notified later (safe but slow) |
| No per-agent stickiness required or assumed | ownership is the registry's, §5.2 | none — but a design that *needs* stickiness has hidden its ownership problem |

Distribution is **per connection**, not per agent: after a replica restart its agents land on the survivors in the ratio the balancer's algorithm gives, and the surviving replicas' memory budgets (§5.5) must absorb that until the restarted replica is healthy again. The capacity model (§5.9) sizes for N−1 replicas carrying the fleet.

    IF NEW.fencing_epoch < OLD.fencing_epoch THEN
        RAISE EXCEPTION 'agent_session % fencing epoch may not decrease (% -> %)',
            OLD.agent_id, OLD.fencing_epoch, NEW.fencing_epoch

What this document depends on is a contract, stated here so the poll below and the tests in §8 are checkable without it:

- **The lease store's contract — the poll's join contract.** There is exactly one current lease row per agent, and it carries, as typed and CHECK-validated columns: the granted `capabilities[]`, the one `target_id` and the `binding_ids[]` that scope it, both revocation epochs, the `cert_thumbprint` the grant is bound to, `issued_at`/`expires_at`, and the four verb ceilings and the admission margin **as delivered on the `LeaseGrant`** — a snapshot, never live configuration. The row advances only to a strictly newer grant under a total order, so two grants can never both read as current. Every grant and every request for one is recorded before the CP is called and completed exactly once under the session fence — and losing that fence **writes nothing**, leaving the request recoverable by the agent's next owner rather than terminal, so a retry receives its own outcome, only through a session that currently owns the agent, and no re-claim can make a consumed nonce unrepairable by the DP; `issue` is a once-per-identity operation arbitrated by an index; a request orphaned by a gateway crash is recovered by an authenticated epoch transfer and a timed-out one by a bounded takeover under its own id, so `SM-D28`'s single-use nonce is never spent on a grant no row records. **Nothing in the poll below reads anything else** — not live config, not the wire, not process memory.
- **The registry's contract.** Both label ids on an agent batch are **DP-minted**: `replica_id` once per `(binding_id, replica_ref)` and stable for the life of the replica (it is the series `source_key` surrogate), `incarnation_id` once per reported incarnation and outside series identity. Only a `TRUSTED`, grammar-valid report registers anything. Both levels are **capped**; the stable cap is a **locked cardinality row** rather than prose and counts **active** rows only, so replica-name churn does not exhaust it, and the counter moves only when a slot is consumed or released — never on a re-report of a living replica. The ephemeral cap is a count over active **and** retired-but-unpruned rows, so it is released by `registry_retention` rather than by retirement (stated, not symmetric — §12 limit 14). **Both levels are serialized by the same binding-wide cardinality row**, taken `FOR UPDATE` by every registration on the binding; only the stable level's number is stored in it, and the per-agent identity lock orders one agent's reports rather than arbitrating the ephemeral cap — which for the ephemeral cap makes the serialization over-determined, since the identity lock and the reporter gate each already prevent two agents contending for one replica's count. **And the registration transaction decides every gate before it writes anything**, so a report refused by the reporter gate or either cap leaves the registry — reporter ownership and watermarks included — byte-identical. **Exactly one incarnation of a replica is active**, by index rather than by prose; an out-of-order report changes nothing; and a report that registers nothing — the steady state, a re-reported incarnation, a stale sequence — is still answered with the **active** ids. Retirement is a timestamp; deletion is the migrator's and only when no incarnation and no `series` row still reference the row.

**The delivery poll is a fenced reservation, not a read** — `pollDeliverable` for one owned agent, in one statement, joining the ownership row on the caller's epoch **and** owner, the lease row for scope and time, and stamping the rows it returns; a replica that no longer owns the agent, or presents a stale epoch, stamps and receives nothing. **One rule decides whether a command is noticed:** the agent has not yet *spoken about it on this epoch* (`notice_acked_epoch`, set by any agent message naming the command — `CommandPull`, `CommandReceived`, `ApplyProgress`, `CommandAck` — through their fenced writes) **and** the last notice on this epoch is old enough to repeat. That single predicate covers first delivery, a lost notice, a reclaim, **and a crash between stamping and sending** — for `OFFERED` and `DELIVERED` alike — without a per-state special case. The time inputs are the lease row's own snapshot, so the DP and the agent evaluate the same ceilings:

```sql
WITH s AS (
  SELECT se.tenant_id, se.agent_id, se.fencing_epoch FROM sm_data.agent_session se
   WHERE se.agent_id = $agent AND se.fencing_epoch = $epoch AND se.owner_replica_id = $replica   -- ownership fence; 0 rows → nothing below runs
   FOR SHARE
),
eligible AS (
  SELECT c.tenant_id, c.command_id
    FROM sm_data.agent_command c
    JOIN s                          ON s.tenant_id = c.tenant_id AND s.agent_id = c.agent_id
    JOIN sm_data.agent_identity   ai ON ai.tenant_id = c.tenant_id AND ai.agent_id = c.agent_id
    JOIN sm_data.agent_fleet_epoch fe ON fe.tenant_id = c.tenant_id
    JOIN sm_data.agent_lease      l  ON l.tenant_id = c.tenant_id AND l.agent_id = c.agent_id
   WHERE c.state IN ('QUEUED','OFFERED','DELIVERED')
     AND c.notice_acked_epoch IS DISTINCT FROM s.fencing_epoch    -- the agent has not acknowledged this command on THIS epoch
     AND (c.next_notice_at IS NULL OR c.next_notice_at <= now())  -- and the previous notice on this epoch (if any) is old enough to repeat
     AND ai.revoked_at IS NULL
     AND l.cert_thumbprint = ai.cert_thumbprint                     -- the lease is bound to the cert this identity holds
     AND l.agent_revocation_epoch = ai.agent_revocation_epoch      -- a lease minted before a revocation grants nothing
     AND l.fleet_revocation_epoch = fe.fleet_revocation_epoch
     AND c.target_id = l.target_id                                 -- scope: the lease's one target
     AND c.binding_id = ANY (l.binding_ids)                        -- scope: a binding the lease still names
     AND c.required_capability = ANY (l.capabilities)              -- capability
     AND l.expires_at - now() >= (CASE c.operation WHEN 'preflight' THEN l.ceiling_preflight WHEN 'apply' THEN l.ceiling_apply
                                                   WHEN 'restart'   THEN l.ceiling_restart   ELSE l.ceiling_stop END
                                  + l.admission_margin)             -- time, from the stored, CHECK-validated snapshot
   ORDER BY c.generation
   LIMIT $limit
   FOR UPDATE OF c SKIP LOCKED
)
UPDATE sm_data.agent_command c
   SET state = CASE c.state WHEN 'QUEUED' THEN 'OFFERED' ELSE c.state END,   -- OFFERED/DELIVERED keep their state; the notice re-stamps the epoch
       offered_epoch = $epoch, offered_at = COALESCE(c.offered_at, now()),
       next_notice_at = now() + $notice_retry_interval                       -- the same session hears about it again only after this, and only if it still has not spoken
  FROM eligible e
 WHERE c.tenant_id = e.tenant_id AND c.command_id = e.command_id
RETURNING c.command_id, c.agent_id, c.binding_id, c.generation, c.operation, c.required_capability;
-- The gateway sends GenerationAvailable ONLY for rows this statement returned, ONLY after its transaction committed. If the
-- gateway dies between commit and send, the row's notice_acked_epoch still differs from the epoch, so the next poll after
-- next_notice_at returns it again (§8 row 36) — a lost notice is a delay, never a stranding.
-- A QUEUED command that fails the capability / target / binding predicate against a CURRENT lease row is moved to
-- REFUSED(CAPABILITY_MISSING | TARGET_MISMATCH | BINDING_NOT_IN_LEASE) by a sibling statement with the same s/ai/fe/l joins;
-- one that fails only the time predicate simply waits.
```

**The claim is one transaction with a ledger** — `SessionRegistryPort.claim`; **a revoked or unknown identity cannot claim**, a retry gets its **original** result, and a stale request can never become a new claim:

```sql
-- Step 0a, SERIALIZE the request key against the retention job (F3) — same lock the job takes around its delete+tombstone pair:
SELECT pg_advisory_xact_lock(hashtextextended($request_id::text, 0));
-- Step 0b, the tombstone check (F6) — the ledger insert in step 2 has no way to tell "never seen" from "retention deleted it":
SELECT 1 FROM sm_data.agent_request_tombstone WHERE request_id = $request_id;
--   found → REQUEST_EXPIRED: refused, audited, no write. Not found → step 1.
-- Step 1, the ledger lookup:

--   found, request_fingerprint = $fingerprint → the retry of a completed claim: reply with ITS epoch and current;
--                                                if current = false the caller has been superseded (SESSION_SUPERSEDED) — the retry NEVER re-claims.
--   found, fingerprint ≠                       → REQUEST_ID_REUSED: refused, audited, no write.

--                                                its transaction aborts, and it re-runs step 1 to receive the stored result — no second epoch.)
-- Step 2, a genuinely new claim: mint the next epoch, take ownership, and ledger it, in one statement.
WITH id AS (

   FOR SHARE                                           -- a concurrent revoke waits for this claim to commit, then the heartbeat sees it
),
sess AS (

  ON CONFLICT (tenant_id, agent_id) DO UPDATE
     SET owner_replica_id = EXCLUDED.owner_replica_id,

)
INSERT INTO sm_data.agent_claim (request_id, tenant_id, agent_id, request_fingerprint, fencing_epoch)
SELECT $request_id, sess.tenant_id, sess.agent_id, $fingerprint, sess.fencing_epoch FROM sess
RETURNING tenant_id, agent_id, fencing_epoch;                 -- (agent_id, fencing_epoch) is the AgentSessionRef handed to the gateway; tenant_id stays in dp-core

### 5.3 The failover sequence (the first failure test, §8 row 1)

1. Replica `r1` owns agent `A` at epoch 7 with command `C` in `OFFERED(epoch 7)` or `DELIVERED` (the agent may have journaled it before the stream broke).
2. `r1` dies. `A`'s TCP stream breaks; `A` backs off with jitter and reconnects through the balancer, landing on `r2`.
3. `r2`: TLS → admission → `resolve(thumbprint)` → `claim(thumbprint, r2)` → `AgentSessionRef{A, epoch 8}`, `resumeCursor`.
4. `r2` polls `CommandFeedPort`; `dp-core` returns every `QUEUED`/`OFFERED`/`DELIVERED` command for `A` whose capability the lease permits — including `C` — and `r2` sends `GenerationAvailable(C)` again, `offered_epoch = 8`.
5. `A`'s journal sees `C`'s key: if it already holds and applied `C`, it re-reports `APPLIED` without pulling or acting (`AG-D4`); if it holds but has not applied, it skips the pull and continues; otherwise it pulls, sends `CommandReceived`, and applies once.
6. `r2` acks with the epoch-8 ref → `COMMITTED`.
7. If `r1` was only partitioned and comes back with a late `received` or `ack` at epoch 7 → **0 rows** → `STALE_EPOCH` → `r1` sends `Error(SESSION_SUPERSEDED)` to whatever it still holds and closes.

**Pass criterion:** exactly one `ACKED` row for `C`, exactly one `apply_attempt` with a terminal outcome for `C`'s intent, `agent_session.fencing_epoch = 8`, and `r1`'s late write is observable as `agw_ack_stale_epoch_total = 1`.

### 5.4 Command routing to the owning replica — a durable poll, never a push

`dp-core` exposes **no network endpoint on the gateway and needs none**: each replica runs a **durable poll loop** — `CommandFeedPort.pollDeliverable(replicaId, session, limit)` per owned agent every `command_poll_interval` — over `dp-core`'s `agent_command_deliverable` index. The poll is the fenced reservation statement of §5.2: it joins the ownership row on the caller's epoch **and** owner, so when ownership changes the old replica's polls **return zero rows by predicate**, not by convention, and the new replica's start; a notice is sent only for rows the statement stamped and only after it committed (§8 row 2 tests the two-poller case). An **after-commit wake-up** shortens latency when the committing `dp-core` transaction and the owning replica happen to share a process (v1 always; after extraction sometimes), but **correctness never depends on it**: a command committed by a `dp-core` transaction in another process, or while the wake-up was lost, is delivered within one poll interval (§8 row 18). After extraction the poll becomes an RPC to `dp-core`; the gateway still initiates every call. The gateway therefore has **one inbound network surface**, the agent port (plus the mute readiness socket, §5.1) — the same posture `B/D1` gives the agent.

### 5.5 Bounded buffers, batching, backpressure and drop policy

| Resource | Bound | Enforcing artifact | When exhausted |
|---|---|---|---|
| Per-session telemetry in flight | `credits` × `max_batch_bytes`, and ≤ ½ of the connection-level HTTP/2 window (§4.1) | credits granted on `SessionAccept`/`TelemetryAck`/`TelemetryCredit` only, each a reservation; the gateway's `CreditLedger` refuses a batch with no credit (`OUT_OF_CREDITS`); **on every session close (§4.2) the ledger returns the session's unspent credits at once and each in-flight batch's bytes when its port call completes** — the reservation's lifetime is the session's, and `agw_credits_outstanding` returns to baseline after churn (§8 row 28) | agent buffers on disk (`AG-D9`); nothing is dropped by the gateway; recovery via `TelemetryCredit` |
| Per-replica telemetry memory | `telemetry_budget_bytes` (config) ≥ Σ sessions × credits × `max_batch_bytes` — **every credit outstanding is a reservation the ledger made before granting** | the ledger computes credits per ack as `min(1, floor(remaining_budget / max_batch_bytes))`, re-issues unsolicited credits as budget frees, and grants `initial_credits` **only from remaining budget — a new session gets `min(initial_credits, floor(remaining_budget / max_batch_bytes))`, which may be 0**; a reconnect storm therefore cannot oversubscribe the budget by one batch per session | throughput falls, no OOM; sessions at zero credits wait for `TelemetryCredit`; `agw_memory_budget_used_bytes` alarms |
| Per-session command payloads | held only between `pull` and the stream write; **never queued in memory** — the durable queue is `agent_command`, and notices carry no payload | `CommandFeedPort.pull` is called on demand | nothing to exhaust |
| Per-session reports/heartbeats | one outstanding `ActualStatePort`/`heartbeat` batch per session; the stream's HTTP/2 flow-control window is the back-stop | gRPC flow control | the agent's send blocks; heartbeats carry `buffer_depth` so the delay is visible |
| Message size | `max_message_bytes` (config, sent on `SessionAccept`) | gRPC max inbound/outbound message size; `PAYLOAD_TOO_LARGE` | a rendered config above the limit is refused at render time in `dp-core` and surfaced as an apply error — **there is no second fetch path** (§12 limit 11) |
| Sessions per replica | `max_sessions` (config) | admission limiter (§5.6) | `ADMISSION_LIMITED` + `retry_after` |
| Enrolments | `enroll_rate` per source, `enroll_attempts_per_token` | the enrol token bucket + per-token counter (§5.6) | `ADMISSION_LIMITED`; token consumed after the cap |
| Port call concurrency | bounded executor per port | rejected execution → `INTERNAL_UNAVAILABLE` with `retry_after` | agents retry with jitter |

**Drop policy, stated once:** the gateway **never drops a command** (it is durable and pausable), **never drops a telemetry batch** it has accepted a credit for (it refuses before accepting), and **never drops a report** (flow control blocks the sender instead). The only drop in the system is the agent's own `AG-D9` drop-oldest, which is counted and reported as `gap_markers`. Batching: telemetry is batched by the agent; heartbeats are batched by the gateway per replica (§4.9); ingest writes are batched by `dp-core` per batch (§6.2). No per-sample work exists anywhere between the agent's collector and the multi-row insert.

### 5.6 Reconnect storms, enrolment storms and planned restarts

- **Session admission limiter:** a token bucket per replica on *new sessions* (`admission_rate`, `admission_burst`), applied **before** identity resolution and claim (§4.2 `ADMITTING`). Admission never promises telemetry capacity: an admitted session's `initial_credits` are computed from the remaining budget at `SessionAccept` time and may be zero (§4.10, §5.5), so `max_sessions × initial_credits × max_batch_bytes` is not a constraint the operator has to keep below the budget — the ledger enforces it per grant. Above the rate, the gateway completes the TLS handshake (so the agent knows it reached a real gateway), returns `SessionReject(ADMISSION_LIMITED, retry_after = base × 2^attempt ± jitter)` and closes. The agent's backoff (`AG-5`) plus the server-supplied `retry_after` spreads the storm; the retry lands on whichever replica the balancer picks next. **A rejected connection makes no port call and no registry write**, so a storm produces no write amplification in `sm_data`.
- **Enrolment limiter:** `Enroll` is the only certificate-less RPC, so it gets its own bucket — `enroll_rate` per source address and `enroll_attempts_per_token` (after which the token is consumed and audited). Refusals are `ADMISSION_LIMITED` with `retry_after` and are audited as a sampled counter, not per attempt (§7.7).
- **Planned restart:** the replica closes its readiness socket (the balancer stops sending new connections), sends `Drain{reconnect_after}` to every session with staggered `reconnect_after` values across the drain window, waits for in-flight acks or the window, then exits. Agents reconnect spread over the window rather than at once.
- **Cold start of the whole fleet** (site power-on) is the worst case: every agent connects within seconds. The admission limiter turns it into a ramp bounded by `admission_rate × replicas`; the capacity model (§5.9) sizes `admission_rate` from the acceptable ramp time.

### 5.8 Resource limits (configuration, with defaults the implementing plan must measure, not assume)

`max_sessions`, `admission_rate`, `admission_burst`, `enroll_rate`, `enroll_attempts_per_token`, `telemetry_budget_bytes`, `max_batch_bytes`, `max_message_bytes`, `initial_credits`, `heartbeat_interval`, `keepalive_interval`, `skew_tolerance`, `drain_window`, `command_poll_interval`, `notice_retry_interval` (how long an unacknowledged `GenerationAvailable` waits before the same session hears it again; ≫ `command_poll_interval`), `pending_ttl` (how long a `PENDING` lease request may stay in flight before a caller may **take it over under its own id** — it is what each `attempt_deadline` is set from; ≥ the CP call timeout), `takeover_attempts` (how many attempts a timed-out lease request may be taken over for before it is failed `TIMEOUT` and the session refused `RE_ENROLL_REQUIRED` — the fallback while §13 AGW-18 is open; it bounds `attempt_no` **in the two statements that read it** — a CHECK cannot reference configuration, so the bound is statement-level with a test, never database-level: [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §3.4 and (L3)), `ledger_retention` (how long `agent_claim` and `agent_lease_grant` rows are kept — the idempotency horizon; ≥ 2 × the lease duration and ≥ any plausible retry delay; a retry older than this is `REQUEST_EXPIRED`; **and ≫ the lease duration**, because it also prunes the `issue`-once index row — §12 limit 19a), `retention_batch` (how many ledger rows one retention transaction deletes and tombstones; each row costs one transaction-scoped advisory lock and that pool is finite, so the job loops over batches instead of sweeping the horizon in one transaction — §5.2, §7.4), `orphan_grace` (how long past its `attempt_deadline` a `PENDING` lease request waits before the migrator's orphan sweep completes it `FAILED('TIMEOUT')`; **≫ `pending_ttl` × `takeover_attempts`**, so no live caller can be mid-recovery on a request the sweep touches — [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §5.4), `reporter_handoff_grace` (how long the current reporter of a replica must have been silent before a **different** agent's report is admitted as a handoff rather than refused `REPORTER_DISPLACED`; expressed as a multiple of `report_interval`, and ≥ the largest legitimate report delay — sketch §4 A5, the reporter gate that consumes it), **`report_interval` — an *ask*, not yet a setting the agent honours** (the periodic actual-state cadence §13 AGW-19 routes to the `AG-D*` owners; it is delivered on `SessionAccept.limits` and both `incarnation_idle_retirement` and `reporter_handoff_grace` are expressed relative to it, so until AGW-19 closes those two have no defensible value and the sweeps that read them must not run), `tombstone_retention` (how long an `agent_request_tombstone` row outlives the ledger row it replaces; **≥ 1 year** and ≫ `ledger_retention`, because it is the only thing that keeps `REQUEST_EXPIRED` decidable — §12 limit 19), `max_replicas_per_binding` and `max_incarnations_per_replica` (the registry caps; **both are validated as positive integers at configuration load and a value of `0` — or negative — refuses startup**, which is the S3/F4 fix chosen over a defensive branch in the registration transaction: a cap of zero is never a legitimate configuration, so it belongs in the one place that runs once rather than in a per-report code path that would then have to carry a comparison whose only purpose is to survive a value the operator should never have been allowed to set — and first registration relies on it, because that branch does not execute the ephemeral count at all, its count being `0` by construction, so `0 < cap` is guaranteed by the validation rather than by the statement; registration beyond either cap is `REPLICA_CAP_EXCEEDED` — the first counts **active** replicas only, against a locked cardinality row; the second counts **active plus retired-but-unpruned** incarnations and is therefore released by `registry_retention`, not by retirement, so it must exceed the restarts one replica can accumulate in that window), `incarnation_idle_retirement` (how long an incarnation may go **unreported** before the migrator retires it — the DP-observed liveness that makes a *vanished* replica become idle at all, since an incarnation is otherwise retired only by a successor; measured against DP receive time and set above the longest legitimate gap between two reports of a live replica, or a healthy replica is retired under itself), `replica_idle_retirement` (how long a stable replica may hold a cap slot with **no active incarnation** before it is retired and the slot released; ≫ the longest legitimate gap between a workload stopping and its replacement reporting, or a rolling restart retires a replica that is coming back). **Both are the migrator's, on the retention job's cadence — not the next report's:** a binding at `max_replicas_per_binding` frees a slot when the job next sweeps, so the cap must be set above the *peak* live population, and the worst-case time a vanished replica holds a slot is `incarnation_idle_retirement + replica_idle_retirement +` one job interval, `registry_retention` (how long a retired incarnation row — and a retired replica row nothing references — is kept before the migrator deletes it), `ingest_latency_target` (the p99 commit latency the §8 rows assert against), `port_timeout`, `port_retry_max`, `h2_connection_window`. Each is surfaced as a gauge so a reviewer can compare the running value to the capacity model, and **every §8 pass criterion that says "within" or "≤" names one of these values**, never an unbounded adjective.

### 5.9 Capacity model — inputs and formulas, not a number

**Inputs** (per install, from the declared inventory [`../../architecture.md`](../../architecture.md) §7): `A` agents (one per host/node; each bound to exactly one Target, `B/D7`) · `W` workloads per agent (pods, containers or processes the agent reports for — the Target's replicas, **not** additional Targets) · `S` samples per second per workload · `P` bytes per sample on the wire · `P′` bytes per sample stored (post-normalization; [`../../architecture.md`](../../architecture.md) §8 sizing, open item 2) · `B` batch bytes (`max_batch_bytes`) · `R` reconnect burst fraction (share of `A` reconnecting within `W_r` seconds) · `D` retention (`REQ-007`: six months) · **measured**: `I` = ingest batches per second one `dp-core` instance commits at the target latency; `C` = concurrent sessions one gateway replica sustains at the target memory.

**Formulas.**

- Sample rate `Λ = A × W × S` samples/s. Wire rate `Λ × P` bytes/s. Batches/s `β = Λ × P / B`.
- Gateway replicas — **an extraction-time formula; v1 has `N_g = 1` (§2.3)**: `N_g = ceil(A / C) + 1` (N−1 must carry the fleet, §5.1).
- Ingest headroom: require `β < I × N_dp × 0.6` where `N_dp` is the number of `dp-core` instances (1 in v1). If not, `B` rises (fewer, larger batches) before anything else scales. **With `N_dp = 1`, `I` is the binding ceiling of the whole path** — §12 limit 8.
- Per-replica telemetry memory `M = (A / (N_g − 1)) × credits × B` — must fit `telemetry_budget_bytes` with N−1 replicas (v1: `A × credits × B`).
- Storm ramp: `A × R / (admission_rate × max(N_g − 1, 1))` seconds to re-admit a burst; set `admission_rate` from the acceptable ramp.
- Storage: `Λ × P′ × 86400` bytes/day before rollups — feeds the storage sizing model (`SM-D8`, open item 2), it does not replace it.
- **Ledgers:** `agent_lease_grant` grows by `A × (3600 / (0.5 × lease_seconds)) × 24` rows/day (one renewal at 50 % of each lease — at the one-hour lease, 48 per agent per day) plus **one row per first-ever session of an identity** (`kind = 'issue'`) and nothing per reconnect — `current` is a read and writes no row (§3.1 rule 2), which removes the round-6 term of one ledger row per reconnect; `agent_claim` by `A × reconnects_per_day`. With `L` bytes per ledger row (measured; the grant JSON dominates) and `ledger_retention` `D_l` days, ledger footprint ≈ `A × (48 × L + reconnects × L_claim) × D_l`. For the worked example at `L = 1` KiB and `D_l = 35`: ≈ 84 MB — small, but **unbounded without the retention job**, which is why `ledger_retention` is a required setting, not a tuning knob (§12 limit 18). **`PENDING` rows are bounded separately**, because retention takes terminal rows only: the outstanding set is at most the reservation rate × (`pending_ttl` × `takeover_attempts` + `orphan_grace`), after which the orphan sweep terminalizes them and ordinary retention prunes them — so a crash loop that reserves and dies cannot grow the ledger without bound, and `dp_agent_lease_requests_pending` is the gauge that shows it if the sweep is not running ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §5.4).
- **Tombstones:** one row per deleted ledger row, at **24 bytes of payload** (`uuid` 16 + `timestamptz` 8, before per-row and index overhead), kept `tombstone_retention` `D_t` days: ≈ `A × (48 + 2 × reconnects) × 24 × D_t` bytes. For the worked example at `D_t = 365`: ≈ 22 MB per year. This is the term that lets `tombstone_retention` be years rather than weeks (§12 limit 19).
- **Registry:** `agent_replica` grows by the number of **distinct** `(binding, replica_ref)` pairs — **not** by restarts, since a restart reuses `replica_id` (F5). The cap `max_replicas_per_binding` bounds the **live** population, not the historical one: a replica with no active incarnation for `replica_idle_retirement` is retired and its cap slot released, so a fleet that renames replicas every rollout consumes `A × W` slots at any instant while accumulating `A × W × rollouts_per_D_r` rows until `registry_retention` prunes the retired ones. `agent_replica_cap` is one small row per binding, never deleted. `agent_replica_incarnation` grows by `restarts_per_day × A × W` rows/day — two uuids, one short string, one agent uuid and four timestamps each — bounded per replica by `max_incarnations_per_replica` and pruned by `registry_retention` once retired (F9). One row per **activation**, so a replica that flaps between two incarnation strings accumulates a row per flap rather than re-activating one (the disjoint-window rule, §6.1). Each row also carries the reporting agent's watermark (`last_seen_report`) beside `last_seen_at`, and the stable row carries `reporter_agent_id`/`reporter_since` — six extra bytes-plus-a-uuid per row, not a new table. Each `TRUSTED` report of a **live** replica also performs one narrow `UPDATE` of that row's `last_seen_at` — a single-row write at the report rate, no counter, no mint, no new row — which is the DP-observed liveness the retirement sweep reads. For the worked example (`A × W = 1000` replicas) at one restart per replica per day and `registry_retention = 30`: ≈ 30 000 incarnation rows, a few MB.

**Worked example (inputs are examples, not conclusions):** a Kubernetes install with `A = 50` node agents, `W = 20` pods per node, `S = 1` sample/s, `P = 200` B, `B = 64` KiB. Then `Λ = 1000` samples/s, wire rate ≈ 200 KB/s, `β ≈ 3` batches/s — **to be compared against the measured `I`; no conclusion about ingest headroom exists until `I` is measured**. The storm ramp is computable from inputs alone (`R = 1` after a site power-on: 50 sessions at `admission_rate = 10/s` is a 5 s ramp). The model's job is to make the *binding constraint* visible for a given install once its two constants are measured, and to say which knob moves it.

## 6. Telemetry and Data Plane integration

### 6.1 One ingestion contract, three sources

`TelemetryIngestPort.ingest(IngestBatch)` is the single write path for MI telemetry, called by three producers inside the Data Plane:

| Source | Caller | Where normalization happens | Tenant comes from | Source identity on labels |
|---|---|---|---|---|
| `host-local` agent | `agent-gateway`, forwarding `TelemetryBatch` **unchanged** as `IngestBatch{producer: AgentSessionRef{agentId, fencingEpoch}}` | the agent ([`../../go-agent/design.md`](../../go-agent/design.md) §6, transport-agnostic model) — the gateway forwards, never normalizes | `dp-core` resolves `agent_identity` for `agentId` **inside the port**; the epoch is fenced like every other agent-bound write | **registry ids**: `binding_id` + DP-minted `replica_id`, `incarnation_id` (`AGW-D16`) — the producer is a *reporting* agent, so the DP has a trusted report to mint from |
| Cache pull (`/actuator/*`) | `dp-core`'s poller ([`../../architecture.md`](../../architecture.md) §10, `BE-D9` context) | the poller | `dp-core` resolves the declared instance for `DeclaredInstance{instanceId}` | **inventory + DP observation**: `binding_id` + the declared inventory's `placement_id` + a `source_key` the **poller itself** observed (the endpoint it polled). No registry row, because there is no agent report to trust and none is needed |
| File Mesh broker-derived events | `mesh-bridge`'s consumer (the "real consumer" plan 003 left for later) | `mesh-bridge` (`BE-D9`, `solace_event` kind) | as above, from the subscription's declared instance | as above: `binding_id` + `placement_id` + a DP-observed `source_key` (the subscription/topic the DP itself subscribed) |

`IngestBatch{producer: AgentSessionRef{agentId, fencingEpoch} | DeclaredInstance{instanceId}, streamId, batchSeq, samples[]: NormalizedSample{seriesKey, type, ts, value, labels}, gapMarkers[], producedAt}`. **There is no `tenantId` field on the batch.** `dp-core` derives the tenant from the producer reference it owns, refuses an `AgentSessionRef` whose epoch is stale (`STALE_EPOCH`) or whose `streamId`/series labels name a target the identity does not own (`TENANT_MISMATCH`), and stamps every row (`I5`). The gateway cannot supply a tenant because the type has no place to put one.

**Why the label shape is producer-specific.** The three-uuid rule below is a rule about *agent* batches, and the round-6 review was right that it cannot be the rule for all three producers: `replica_id` and `incarnation_id` exist only because a **trusted agent report** minted them (`agent_replica.registered_by_agent` is `NOT NULL` by design), and a Cache poller or a broker consumer has no report and no agent. So the port takes **producer-specific source identity** (§3.2): an `AgentSessionRef` batch carries the registry ids; a `DeclaredInstance` batch carries `binding_id`, the inventory's `placement_id` and a `source_key` **the DP itself observed** — which is not a laundering hole, because on those paths the DP *is* the collector, so the string is the DP's own observation rather than a producer assertion. Both shapes normalize to the same series identity inside `dp-core` (`architecture.md` §8): one `series` row per `(tenant, binding, metric, source_key surrogate)`, whether that surrogate is a registry `replica_id` or a `placement_id`. `DeclaredInstance` producers **do not use the replica registry at all**, and the grammar, caps and retention of `AGW-D16` therefore do not apply to them.

**The label contract for agent batches (`I6`).** `NormalizedSample.labels` is not free text, and in v1 it is **not MI-declared either**, because the canonical Solution Package schema's `metric` entry (`contracts/solution-package.schema.json`: `name`, `metricType`, `unit`, `layer`, `when`, `source`, `additionalProperties: false`) declares **no label keys** — so there is nothing package-side to validate against, and this design does not pretend there is. The v1 rule is therefore closed and platform-owned, a **literal list**, and — after four review rounds on this paragraph — **every label value is a DP-minted identifier; no agent-chosen string is a telemetry label**:

| Key (exact) | Type | Authoritative value | DP check |
|---|---|---|---|
| `binding_id` | uuid | the binding the sample belongs to | **must be ∈ the agent's `agent_lease.binding_ids`**, else `BINDING_NOT_IN_LEASE`; the tenant and target follow from the identity, never from the label |
| `replica_id` | uuid, **DP-minted** | the stable replica the sample describes, as registered in `sm_data.agent_replica` ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §2.3) from a `TRUSTED` `ActualStateReport`. **This is the series `source_key` surrogate** ([`../../architecture.md`](../../architecture.md) §8) — it is part of series identity, so it is minted once per replica and reused across restarts | must exist in `agent_replica` for that `binding_id`, else `UNKNOWN_REPLICA` |
| `incarnation_id` | uuid, **DP-minted** | the ephemeral incarnation (a restart is visible without changing series identity, [`../../architecture.md`](../../architecture.md) §8), as registered in `sm_data.agent_replica_incarnation` — one id per **activation**, so a returning incarnation string is a new id, never the old row re-activated. It lives in `labels_jsonb` **outside** series identity, which is precisely why a restart does not split a series | must exist in `agent_replica_incarnation` for that `replica_id`, else `UNKNOWN_REPLICA`; **and if that row is retired, the sample's `ts` must fall inside the half-open `[registered_at, retired_at)`**, else `INCARNATION_RETIRED` (below) |

**A retired incarnation is not a live identity.** Round 7 found that a retired `incarnation_id` stayed acceptable forever, so a compromised or buggy agent could keep labelling *current* samples with a dead incarnation and quietly rewrite the history of a replica that no longer exists. The rule, decided: a sample labelled with a **retired** incarnation is accepted **only if its `ts` lies inside that incarnation's own half-open `[registered_at, retired_at)` interval** — the late-arriving batch a disk buffer legitimately holds across a restart (`AG-D9`) — and is otherwise rejected `INCARNATION_RETIRED`, counted in `dp_agent_ingest_rejected_total{reason}`, with **a gap marker recorded** for the affected series so the loss is visible rather than inferred from absence ([`../../architecture.md`](../../architecture.md) §10 "no zero-fill ever"). An *active* incarnation has no upper bound to check: its window is `[registered_at, ∞)`. **The retired window is half-open — `registered_at` inclusive, `retired_at` exclusive** — which is what makes the two windows of one replica disjoint rather than overlapping at the retire instant, and `incarnation_window` ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §2.5) keeps it non-empty with `retired_at > registered_at`. An incarnation cannot be registered and retired in the same transaction — only a **successor's** registration retires one — so an empty window cannot arise. §8 row 44 tests every leg below.

Three things this rule does **not** settle, stated because round 7 asserted the rule without them (R8):

- ⚠️ **The comparison uses an agent-supplied timestamp, and §4.9 says admission never does.** `NormalizedSample.ts` is the agent's. §4.9's rule — "ordering, trust and admission never use the agent's wall-clock (`B/D15`)" — is therefore **narrowed by this rule, not honoured by it**: the *label's* admission does read the agent's clock. A compromised agent cannot label a current sample with a dead incarnation, but it *can* backdate one into that incarnation's window and rewrite the history of a replica that no longer exists — the same attack, displaced by one field. What bounds it today: the window is finite (an incarnation's own lifetime) and the series is the *replica's*, not the incarnation's, so the reachable damage is confined to a past interval of one replica's series. What does **not** bound it: nothing compares `ts` against the session's measured `clock_offset_ms`, `skew_tolerance` or the batch's `producedAt`. A tighter rule — accept a retired incarnation's sample only while the *session* that sends it is within `skew_tolerance` and `ts ≥ producedAt − buffer_horizon` — is **not decided here**; it needs the buffer horizon `AG-D9` owns. Carried as §12 limit 20 and routed with AGW-17, which is already the gate on this registry's ratification.
- **The two windows meet at one instant, and the half-open interval is what separates them.** Registration retires the outgoing incarnation and inserts the incoming one in one transaction, so `old.retired_at = new.registered_at` (one transaction clock). Because the retired window excludes its upper end and the incoming window includes its lower one, a sample at exactly that instant is valid under the **incoming** incarnation and `INCARNATION_RETIRED` under the outgoing one — one instant, one valid label, by the interval's shape rather than by a tie-break rule bolted on top of a closed interval.
- **A same-`ts` collision is a batch-level rejection, not an overwrite.** `incarnation_id` is deliberately outside series identity, so both incarnations of a replica share one `series_id`, and `metrics_raw`'s primary key is `(tenant_id, series_id, ts)` ([`../../architecture.md`](../../architecture.md) §8.2). A late buffered sample from the retired incarnation whose `ts` already exists for that series is therefore a primary-key conflict on the multi-row insert of §6.2. It is resolved **`ON CONFLICT DO NOTHING`, counted** in `dp_agent_ingest_rejected_total{reason="DUPLICATE_TS"}`, and never `DO UPDATE`: the first committed value for a `(series, ts)` stands, because a later-arriving sample for an instant already recorded is a duplicate, and letting a retired incarnation overwrite a live reading is the rewrite this whole rule exists to prevent. The batch still commits and still returns `Committed` — one duplicate sample must not fail a batch — and the watermark advances as usual.

**No other key is accepted in v1** on an agent batch. Any other key is `UNDECLARED_LABEL`; a non-uuid value is `LABEL_INVALID`; a `binding_id` the lease does not name is `BINDING_NOT_IN_LEASE`; an unregistered pair is `UNKNOWN_REPLICA`; a retired incarnation outside its interval is `INCARNATION_RETIRED`. Each is an **ingest rejection with a counted metric** (`dp_agent_ingest_rejected_total{reason}`) and a `TelemetryReject` code (§4.3, §4.11) — exactly the shape [`../../architecture.md`](../../architecture.md) §8 already prescribes for exceeding the cardinality cap, and **not** a `UI-D5` quarantine (defined for undeclared *metrics*, preserving their samples; a label the platform did not mint has no legitimate home). The DP **compares** and **never overwrites** a label.

**Where the agent's strings go instead, and what bounds them** (`AGW-D16`). The agent's stable replica identity (`replica_ref`: pod name, StatefulSet ordinal, DaemonSet node, systemd host) and its ephemeral incarnation (`incarnation`: pod UID, container id, process start epoch) travel on the `ActualStateReport`, never on telemetry. On the first `TRUSTED` report naming a `(binding_id, replica_ref)` pair, `dp-core` registers it in `agent_replica` and mints `replica_id`; on each new `incarnation` for that replica it inserts a row in `agent_replica_incarnation`, mints `incarnation_id` and sets the previous row's `retired_at`. **A row is never re-activated:** an incarnation string this replica has carried before gets a *new* row and a *new* `incarnation_id`, so each activation owns one half-open window and successive windows cannot overlap ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §4, B5). `ReportAck` returns both ids, and **`replica_id` comes back unchanged for the life of the replica** — the two-level split exists because a single table keyed by `(replica_ref, incarnation)` minted a fresh `replica_id` on every restart, contradicting the stable/ephemeral split [`../../architecture.md`](../../architecture.md) §8 requires and splitting the series at each restart. Registration admits a string only if it matches a **closed grammar**, per label rather than by character class: `replica_ref` must satisfy the **RFC 1123 hostname grammar (lowercase, per-label ≤ 63, total ≤ 253)** — `^(?=.{1,253}$)[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?(\.[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?)*$` — every Kubernetes pod name, node name and hostname is (an API token, path or rendered credential containing an uppercase letter, `_`, `/`, `=`, `+`, `:` or a space is not, and neither is `a..b`, `a.-b` or a 64-character label, all of which the previous single character class wrongly admitted); and `incarnation` must match exactly one of three alternatives — uuid `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`, hex `^[0-9a-f]{12,64}$` or decimal `^[0-9]{1,20}$`. Both are CHECK constraints ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §2.3, §2.5); invalid content produces disposition `REFUSED(REPLICA_REF_INVALID)` without changing the lease/epoch/scope trust verdict. **Both levels are capped:** `max_replicas_per_binding` and `max_incarnations_per_replica` (§5.8); a registration beyond either produces disposition `REFUSED(REPLICA_CAP_EXCEEDED)` without changing trust, and the refusal is counted in `dp_agent_replicas_registered_total{outcome}` on the ordinary completed path — so one valid agent reporting a fresh `replica_ref` per second cannot grow the registry without bound (§8 row 41). **The stable cap counts *active* replicas, not historical ones** — a replica with no active incarnation for `replica_idle_retirement` (§5.8) is retired and its cap slot released — because replica names churn across deployments (a new pod name per rollout, a renamed node) and a cap over the historical population would turn every long-lived binding into a permanent `REPLICA_CAP_EXCEEDED`. **Three things that took three rounds to get right, and are stated because they are what make that claim true:** who may report a replica is **DP-owned** — the stable row carries the current `reporter_agent_id`, a report from any other agent is admitted only as a **handoff** after the incumbent has been silent for `reporter_handoff_grace` and is otherwise refused `REPORTER_DISPLACED`, because ordering reports "by DP receive order" across agents let a *delayed* report from a displaced agent retire the live incarnation and reactivate a dead one; an incarnation is retired by a *successor*, so a replica that simply **vanishes** would never become idle at all — the migrator therefore retires an incarnation whose DP-observed `last_seen_at` is older than `incarnation_idle_retirement` **before** the idle sweep runs — **and that liveness has no source until §13 AGW-19 closes**, because `last_seen_at` moves only on an `ActualStateReport` and no periodic report cadence is specified anywhere yet, so the sweep must not run and this retirement property is conditional; and both sweeps are **maintenance jobs outside the registration transaction**, because running retirement inside it made two parties take the cap row and the replica rows in opposite orders (a deadlock, not a scoping problem), so a slot is released on the job's cadence rather than inside the report that would have used it ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §5.0, §5.1). ⚠️ **They were called "the migrator's alone" until S11/F4 and that was a guarantee with no enforcing artifact** — no scheduler, role, lease or test enforced it, and the measured DCL lets `sm_dp_runtime` run both (S10/F3). The sketch now states only the measured concurrency boundaries: two concurrent §5.1 runners on one binding, and §5.4 against step-3 completion in both ledger-lock orders ((L13), (L16)). It makes no universal claim about arbitrary pairings or runner counts. The migrator remains the **recommended** scheduler; central open item 39 routes the component, multiplicity and retry policy to the `BE-D*` owners, not decided here. **Exactly one incarnation of a replica is active**, and the registration transaction retires the previous one and inserts the new one together, ignoring a report older than the active incarnation's own report sequence. Retired incarnation rows are deleted by the migrator after `registry_retention`; a retired *replica* row only when nothing — no incarnation row, no `series` row — still names its `replica_id`. Mechanism: the sketch's §4 and §5. So `metrics_raw` and its `series` dimension hold **only DP-minted uuids and inventory identifiers**; the registry holds the agent's two strings once each, grammar-shaped, capped, audited to the report that asserted them.

**The residual, named, and how it is governed.** A secret that is *itself* a valid hostname or a hex string — an all-lowercase alphanumeric token whose labels are each under 64 bytes — would pass the grammar and be stored once in `agent_replica`. That is the same residual every inventory system that accepts a reported hostname carries, including `dp-remote`'s own host discovery; it is not a *telemetry* channel (one row per replica, never per sample, never in `metrics_raw`), but it is a place an agent-chosen string persists. **`AGW-D13`'s `I6` clause therefore does not ratify until §13 AGW-17 is resolved, and `AGW-D16` as a whole does not ratify until AGW-17 *and* §13 AGW-20 both close, with its retirement clauses additionally conditional on §13 AGW-19** — either runtime verification of reported replica identities (Kubernetes API, container runtime, host), or the architect group's explicit acceptance of the grammar-bounded residual as equivalent to the hostname residual `dp-remote` already has. AGW-17 is a **ratification blocker**, not a routed nicety. **MI-declared labels are a future reviewed contract change** — a `labels` declaration on the package's `metric` entry with key set, value bounds and domains — routed as §13 AGW-16; until it lands, an MI metric that needs its own dimensions is either a distinct declared metric or not collected. The future `.proto` inherits the agent batch's three-key list, the two grammars (RFC 1123 per-label; the three incarnation alternatives) and the rejection codes as its label enum and negative fixtures (§14 item 2).

### 6.2 The write path — no per-sample synchronous write

`dp-core` handles one `IngestBatch` as one unit of work: resolve the producer (share-locked session row for `AgentSession`, §5.2) → validate shape → resolve `series_id`s ([`../../architecture.md`](../../architecture.md) §8's `series` table, batched lookup with a per-instance cache) → one multi-row `INSERT … ON CONFLICT (tenant_id, series_id, ts) DO NOTHING` into the current `metrics_raw` partition (**never `DO UPDATE`**: the first committed value for an instant stands, and a suppressed row is counted `dp_agent_ingest_rejected_total{reason="DUPLICATE_TS"}` — §6.1's collision rule) → record `(tenant_id, producer, stream_id, batch_seq)` in `telemetry_ingest_watermark` in the same transaction → commit → return `Committed{highWatermarkSeq}`. A replayed `batchSeq` at or below the watermark short-circuits to `Committed` without inserting (the watermark row is the arbiter, unique on `(tenant_id, producer_key, stream_id)`). Rollups run on their own schedule over committed rows ([`../../architecture.md`](../../architecture.md) §8.3), untouched by this design.

Under load `dp-core` may coalesce several `IngestBatch`es into one transaction; **each caller's reply is issued after *that* transaction commits** — coalescing changes when the commit happens, never whether the reply waits for it. Nothing about the agent path forces a per-sample write, and nothing in it is allowed to acknowledge before the commit.

### 6.3 Durability, freshness and gaps

- **Durable = committed.** `TelemetryAck` follows `Committed`; the agent trims its disk buffer to the acknowledged watermark. A gateway crash between `Committed` and `TelemetryAck` costs one duplicate batch on reconnect, which the watermark absorbs.
- **Freshness** per series is `now − last committed ts`, computed by the query side (`DM-D*`), never asserted by the transport. The dashboards' staleness marker (`UI-D8`) reads committed rows.
- **Gaps** are rows: `gap_markers` become `metrics_gap{tenant_id, series_id, from_ts, to_ts, reason}`; a chart shows a gap, never a flat line ([`../../architecture.md`](../../architecture.md) §10 "no zero-fill ever"). A dropped-because-of-backpressure period is therefore *visible* in Governance as the agent's `drop_count` rising and a gap row landing.

### 6.4 Tenant isolation on the telemetry path

Tenant is resolved from the certificate (§4.5) into `agent_identity`, re-derived by `dp-core` from `agentId` at the port (§6.1), checked against the batch's declared target (`TENANT_MISMATCH`), and carried on every row (`metrics_raw` PK leads with `tenant_id`, [`../../architecture.md`](../../architecture.md) §8.2). Every query is tenant-scoped by the central data-access module (`I5`). The gateway has **no query path** to make an `I5` mistake with, and no field to assert a tenant in.

### 6.5 How agent telemetry reaches persistence without gateway table access

By construction, not by convention: `agent-gateway` has no datasource dependency (pom allow-list), cannot compile a repository call (`agwUsesDpApiOnly`, `agwHoldsNoDatasource`), cannot fetch one from the shared Spring context (`agwNeverLooksUpBeans`), has no database principal of its own (the DP role topology in [`../eda-walking-skeleton.md`](../eda-walking-skeleton.md) §3.1 grants nothing to a gateway principal because none exists), and reaches rows only as `IngestBatch` through `TelemetryIngestPort`. **Stated honestly for v1:** the module and the DP share one JVM, so the *process* holds the DP datasource; the guarantee is module-level (import and lookup rules with planted-violation proofs), and becomes process-level only at extraction (§9). If a future change needs the gateway to read a table, the design is wrong, not the rule (`I7`'s own wording).

## 7. Security

### 7.1 Two authorization systems, deliberately not one

| | Browser / operator | Agent |
|---|---|---|
| Identity | human principal via `console-gateway`'s authn adapter (`BE-D8`, `BE-D15`) | mTLS certificate → `agent_identity` |
| Authorization | `D10` 🔒 RBAC verbs, deny-by-default, the `D10` amendment (open item 24, G2) | **lease capabilities** (`apply-config`, `lifecycle`, `report-only`) bound to **one target** (`SM-D28`, `B/D8`) |
| Grants | operators assign roles | operators enrol agents (a `D10` verb the amendment paper must carry — routed §13) |
| Where enforced | `cp-core`/`console-gateway` | `dp-core` (identity, lease, target scope, trust label) with the gateway enforcing only the *offer gate* (§4.6) and *admission* (§5.6) |

The agent path introduces **no human verbs, no roles, no policy language**. An agent is not a user; its authorization is "which target, which capabilities, until when" — nothing else. The operator actions *about* agents (enrol, revoke, drain, view fleet) are browser verbs and belong to the `D10` amendment, not here.

### 7.2 `I5` — tenant never client-controlled

Stated in §4.5, §6.1, §6.4. The enforcing artifacts: `AgentIdentityPort.resolve` and the `dp-core`-side re-resolution of `agentId` inside `ingest`/`report`/`ack` are the *only* sources of `tenantId`; the wire schema has no tenant field; `IngestBatch` has no tenant field; `TENANT_MISMATCH` refuses a batch whose declared target disagrees with the identity; `agent_command`/`agent_session`/`agent_identity`/`agent_fleet_epoch` carry `tenant_id` in every key and FK (`BE-D13`'s tenant-consistency rule). Test: `TenantFromIdentityOnlyTest` — a crafted batch naming another tenant's target is refused and audited; a crafted `SessionOpen.resume` cursor cannot advance any DP cursor (§4.13).

### 7.3 `I6` — secrets never in protocol storage, logs, events or telemetry

- **Rendered configuration crosses the wire** — that is the apply model ([`../../go-agent/design.md`](../../go-agent/design.md) §5.1: the DP renders and resolves `secretRef`; the agent writes bytes). It travels **only** inside the mTLS session, **only** in `CommandOffer.payload_bytes`, and the gateway treats it as opaque: never logged (a `PayloadRedactingLogValue` wrapper is the only representation the logging layer sees — the Java twin of `AG-D8`'s `LogValuer` hook), never persisted (no datasource), never held beyond the pull-to-stream-write window, never copied into a metric label or an event (`agwNeverImportsEvents`). **There is no blob store and no second fetch path** — a payload that does not fit `max_message_bytes` is refused at render time (§12 limit 11), so no resolved secret is ever at rest outside `dp-core`'s render call.
- `config_sha256` is computed by `dp-core` **over the rendered bytes it sends** and is the agent's integrity check; the *config hash of record* remains the `I6` hash over references (`apply_step_intent.config_hash`, `BE-D13`) — two hashes, two purposes, stated so they are not conflated.
- Telemetry samples, `gap_markers`, heartbeats and every `Error.message` carry **no agent-chosen string**: the normalized sample's `value` is typed; its `labels` on an agent batch are three uuids — a binding the lease names and two DP-minted replica identifiers (§6.1) — and on a `DeclaredInstance` batch are inventory identifiers plus a DP-observed `source_key`, never a producer-asserted string; `Error.message` is a code-keyed template. The agent's own replica strings travel only on the `ActualStateReport`, are admitted only if they match the closed RFC 1123 / uuid-hex-decimal grammars enforced by CHECK, and are stored once each in `agent_replica` / `agent_replica_incarnation` under per-binding and per-replica caps, audited to the trusted report that asserted them — never in `metrics_raw`. **The residual is named and gated, not hidden:** a secret that is itself a valid lowercase hostname or hex string could be registered once; `AGW-D13`'s `I6` clause does not ratify until §13 AGW-17 closes or the architect group accepts that residual explicitly, and `AGW-D16` as a whole additionally requires §13 AGW-20 (with §13 AGW-19 for its retirement clauses) — §12 limit 14. **Obligation on the future `.proto` (§14 item 2), not a test that can exist today:** its review must assert that no field outside `CommandOffer.payload_bytes` is typed to carry rendered configuration, and its negative fixtures must include a non-platform label key, a non-uuid label value and a `replica_ref` outside the grammar.
- Tokens and nonces (`enrollment_token`, `LeaseGrant.nonce`, `lease_jti`) are logged as **hashes** only.

### 7.4 Least privilege

The gateway **module** holds no database credential and no broker credential: nothing injects one, nothing can compile a call that needs one, and nothing can look one up (§2.6). In v1 the gateway shares its process with `dp-core`, so the *process* holds the DP datasource; process-level isolation is an extraction property (§9, §12 limit 13). The DP runtime role's grants on **the six tables this document owns** (§5.2) are: `agent_fleet_epoch` `SELECT`, `INSERT`, `UPDATE (fleet_revocation_epoch)`; `agent_identity` `SELECT`, `INSERT`, `UPDATE (agent_revocation_epoch, revoked_at)`; `agent_session` `SELECT`, `INSERT`, `UPDATE (…column-scoped, §5.2)` — that `UPDATE` grant is also what lets the **two** `FOR SHARE OF se` readers take their locks at all, the lease ledger's `s` CTE and now the registry transaction's **A1** ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §4.1), since a locking clause needs `UPDATE` as well as `SELECT` (sketch §7); **no new grant is required for A1**; `agent_claim` **`SELECT`, `INSERT` only**; `agent_request_tombstone` **`SELECT` only** (the migrator writes it); `agent_command` `SELECT`, `INSERT`, `UPDATE (state, offered_epoch, offered_at, next_notice_at, notice_acked_epoch, delivered_at, acked_at, outcome, outcome_detail)` — never the identity, target, binding, key, capability or generation columns; **no `DELETE` on any of the six for the runtime role**. **The other five tables' grants, and the `USAGE` grant their sequence needs, are [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §7** — including the fact that a bare `INSERT` grant cannot evaluate `nextval()`, so the ledger's ordering column needs a named sequence and an explicit `GRANT USAGE ON SEQUENCE` that an implicit-sequence column type would have hidden.

⚠️ **And here they are as SQL, because §14 item 3(c) cannot be executed against a sentence (S9/C2).** The prose above is the explanation; this block is the artifact, and the two agree column for column. Run by the migrator under `SET ROLE sm_dp_owner`, like the §5.2 DDL; `GRANT USAGE ON SCHEMA sm_data` is Phase 0's and is deliberately not repeated.

```sql
-- Runtime grants for the SIX tables this document owns (§5.2). Mixed table-level + column-scoped form, as
-- ../eda-walking-skeleton.md §3's DCL uses it and measured on PG 14 there.
GRANT SELECT, INSERT, UPDATE (fleet_revocation_epoch)
    ON sm_data.agent_fleet_epoch TO sm_dp_runtime;
GRANT SELECT, INSERT, UPDATE (agent_revocation_epoch, revoked_at)
    ON sm_data.agent_identity TO sm_dp_runtime;
GRANT SELECT, INSERT, UPDATE (owner_replica_id, fencing_epoch, protocol_version, agent_version,
                              claimed_at, last_seen_at)
    ON sm_data.agent_session TO sm_dp_runtime;
    -- This UPDATE grant is also what lets the two FOR SHARE OF se readers lock at all (the lease ledger's `s` CTE
    -- and the registry transaction's A1): a locking clause needs UPDATE as well as SELECT. No extra grant for A1.
GRANT SELECT, INSERT ON sm_data.agent_claim TO sm_dp_runtime;              -- INSERT-ONLY ledger: no UPDATE
GRANT SELECT ON sm_data.agent_request_tombstone TO sm_dp_runtime;          -- the migrator writes it
GRANT SELECT, INSERT, UPDATE (state, offered_epoch, offered_at, next_notice_at, notice_acked_epoch,
                              delivered_at, acked_at, outcome, outcome_detail)
    ON sm_data.agent_command TO sm_dp_runtime;
-- No DELETE on any of the six for sm_dp_runtime, and no GRANT naming any identity, target, binding, key,
-- capability or generation column: the column lists above are exhaustive, and (k)'s planted test expects 42501.
```

Retention is the **migrator** role's job, as `BE-D13` handles `apply_attempt` — ⚠️ **and "the migrator's" means who schedules it, not what the grants refuse (S10/F3, measured on PG 14.24).** The runtime role can execute the registry sweeps of [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §5.0, §5.1 and §5.4, because the columns they write are exactly the ones **B4**, **B2** and **step 3c** must write on the report and lease paths. What the DCL refuses is `DELETE` on any of the eleven tables, `INSERT` on `agent_request_tombstone`, every identity column, and `nextval` without the sequence grant — that is the whole of the privilege boundary, and the sketch's (L14) is the obligation that measures it. This document's parts: (1) the claim ledger — **two statements per bounded batch, in one transaction**, because the advisory lock of §5.2 is per request key and a set-based `DELETE` cannot take one (R8):

```sql
-- 1. Choose a bounded batch, lock every key in it, return the ids. (ORDER BY is the intended lock order, not a guaranteed one — sketch §5.3.)
WITH batch AS (
  SELECT request_id FROM sm_data.agent_claim
   WHERE claimed_at < now() - $ledger_retention
   ORDER BY request_id LIMIT $retention_batch          -- no row-level FOR UPDATE: the request key is taken first, the row second
)
SELECT request_id, pg_advisory_xact_lock(hashtextextended(request_id::text, 0)) FROM batch ORDER BY request_id;
-- 2. Delete those ids and tombstone them, still holding the locks, RE-CHECKING the horizon inside the DELETE — step 1 evaluated it
--    before the locks were granted, so the decision and the deletion must be the same decision (the sketch's §5.3 makes the same
--    correction for the grant ledger, where a concurrent completion could otherwise have the row PROJECTED by the time the lock arrives):
WITH gone AS (
  DELETE FROM sm_data.agent_claim
   WHERE request_id = ANY ($ids) AND claimed_at < now() - $ledger_retention
  RETURNING request_id
)
INSERT INTO sm_data.agent_request_tombstone (request_id, expired_at)
SELECT request_id, now() FROM gone ON CONFLICT (request_id) DO NOTHING;
```

`agent_claim` is **insert-only and has no non-terminal state** — a row is the completed record of a claim the moment it exists — so it needs no `state <> 'PENDING'` predicate and no projection re-check: the two predicates the grant ledger adds have no counterpart here. Its horizon re-check still matters, because `now()` moves between the two statements.

The job loops over batches; `retention_batch` (§5.8) is what keeps the advisory-lock pool from being the outage. **What the statements guarantee** is the order that matters: request key first, ledger row second — the same order every admission path uses — so the job and a retry serialize instead of deadlocking. **What they do not guarantee** is the order in which one batch's keys are locked, because the lock call sits in a select list; the design does not rest on it (one migrator instance runs retention, and an overlap costs a detected deadlock and a retry, never a second grant or a lost tombstone). Both, with the PostgreSQL citation, are [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §5.3. (2) tombstones — `DELETE … WHERE expired_at < now() − tombstone_retention` (§12 limit 19), which needs no request-key lock because a tombstone's disappearance is limit 19's horizon, not a race. The lease ledger's own `DELETE` (with the predicate that replaces the two foreign keys `agent_lease` deliberately does not carry) and both registry deletes are the sketch's §5. `agent_lease` rows are **never** deleted, because their existence is the "ever granted" test (§4.6). **Obligation (k):** the planted least-privilege test executes every statement in §5.2 as `sm_dp_runtime` and expects success — a grant list that omits a column a statement writes is exactly the defect the Codex round-5 review found, and only execution catches it; the sketch's (L14) does the same for its five tables and its sequence. Obligation: the grants are executed and their refusals proven in the same PG-14 run as the DDL (§14).

### 7.5 Certificate lifecycle

CA and issuance are the CP's (`SM-D24`); the DP relays (`EnrollmentPort`). Leaf certs: **manual rotation in v1** (`B/D16`), authority bounded by the lease not the cert TTL. Trust bundle: rotated with overlapping validity, pushed via `TrustBundleUpdate`, served during overlap. Revocation: **epoch-based** (`agent_revocation_epoch` or the tenant's `fleet_revocation_epoch` raised → the next claim is refused inside the statement, the next heartbeat reply lists the agent in `revoked[]`, the next renewal is refused → `Revoke` in-band → close), which is why no CRL/OCSP distribution is needed for *authority* revocation; certificate revocation lists remain the CA's concern for the *identity* and are deferred with auto-rotation. The gateway's own server certificate is install-provisioned; its rotation is an SM-packaging (`RT-D*`) concern.

### 7.6 Replay resistance

TLS 1.3 handles transport replay. Above it: `nonce`/`jti` single-use on leases (`SM-D28`); **the lease is bound to the certificate** — `LeaseGrant.cnf_thumbprint` must equal the thumbprint the session was claimed with, the renewal upsert refuses any other (`LEASE_KEY_MISMATCH`), and the delivery poll joins `agent_lease.cert_thumbprint = agent_identity.cert_thumbprint`, so a lease lifted from one agent grants nothing on another certificate (§8 row 30); **a nonce-free grant is available exactly once per identity** — `issue` requires that no `agent_lease` row has ever existed, so an expired lease is renewed under its single-use nonce or the session is refused `RE_ENROLL_REQUIRED`, and neither an expiry nor a retention sweep re-opens the no-nonce path (§4.6, §8 row 40); `requestId` idempotency on every port operation that **writes** (a replayed port call returns **its own** stored result from a ledger, never a second effect and never someone else's result — `claim`, `issue` and `renew` are ledgered per request, while the read-only `current` is simply re-evaluated and writes nothing; a reused id with a different fingerprint is refused; a request whose ledger row retention removed is refused from its tombstone rather than accepted as new; and a request the caller's own gateway crash orphaned is adopted into the agent's new epoch by its current session owner and by nobody else, §8 row 42); `fencing_epoch` on every agent-bound write including telemetry and audit; `(producer, stream_id, batch_seq)` watermarks on telemetry and, **provisionally**, a separate identity on reports — for reports the replay identity is the pair **`(agent_id, item_id)`** — the DP-resolved agent identity (`I5`) with the item's own id — and the per-item `requestId` derived from them (§3.1 rule 2's `report` exception), plus the **canonical fingerprint** of §3.2 — the batch `message_id` is transport correlation and **not** an identity — and the freshness watermark is scoped per **`(agent, binding, replica)`** within one reporter's counter — **not** `(agentId, sequence)`, and **not** re-based by a session epoch (S5/F1: an epoch change does not imply a counter restart): one replica's counter must never suppress another's (§4.8, §8 row 6), and the whole identity is §13 AGW-20's to settle (S4/F2, S4/F6); `(generation, idempotency_key)` on commands; trust decided at receive time, not from the agent's timestamp (§4.8). A replayed `CommandAck` or `CommandReceived` is `DUPLICATE`; a replayed `TelemetryBatch` is `Committed` with no insert; a replayed `EnrollRequest` with the **same token and the same CSR** returns the stored `Enrolled` (so a lost reply is recoverable without an operator), while a request against a consumed token with a different CSR is `TOKEN_CONSUMED`. **Replaying a CSR proves nothing about key possession** — a CSR is a signed object anyone holding its bytes can resend — which is exactly why the stored reply contains **only public material** (certificate chain, trust bundle, agent id) and **no credential of any kind**: the certificate is inert without the private key, and this draft issues no report credential anywhere (§12 limit 16, §13 AGW-12). An attacker with token and CSR bytes gets a certificate they cannot use.

### 7.7 Authorization-failure behaviour and audit

Every refusal returns a code from §4.11 and no hint (`B/D8`, no enumeration). Every enrolment attempt outcome, refusal at identity/version/capability, revocation observed, claim, forced drain and stale-epoch write is recorded through `AgentAuditPort` into the DP's audit record with `agent_id`, `tenant_id`, `replica_id`, `request_id`, code and UTC time — never the certificate, token or payload. ## 12. Capability limits — stated, not implied

1. **No exactly-once delivery.** Delivery is at-least-once; execution is at-most-once because of the agent's journal and the DP's arbiter. A broken journal on the agent host can execute twice; that is the agent's failure domain (`AG-D4`), stated here so no one reads "fencing" as "exactly once".
2. **Ownership moves only when the agent reconnects elsewhere.** A replica that is alive but wedged keeps its agents until their streams die (keepalive miss). The keepalive interval bounds that window; nothing else does.
3. **The `SM-D28` claim changes (`AGW-D7`) are proposals.** Until ratified, a strict reading of `SM-D28` makes failover a re-enrolment and gives the fleet epoch no home.
4. **The HTTP/1.1 fallback is not designed** (deferred; flagged §0.1). Environments that cannot egress h2 cannot run agents in v1.
5. **Capacity numbers do not exist yet.** `C` and `I` are measured by the implementing plan; §5.9 gives the formulas only.
6. **The DDL is executed and still not settled, and the two are different things (S11/F5; scope corrected S12/F2).** §5.2's six tables and the eleven-table set as a whole ran on `PostgreSQL 14.24 (Debian 14.24-1.pgdg13+2)` against `8551e5c` — [`evidence/pg14-execution.md`](evidence/pg14-execution.md), **224 legs, 162 `OK`, 60 `REFUSED`, 2 `N/A-engine`, 0 `FAIL`** — covering the **SQL-backed executable subset** of obligations (a)–(r) in §14 item 3 and the sketch's §8 obligations (L1) onward. What execution establishes is that the extracted statements parse, that the exercised constraints and triggers refuse what the text says they refuse, and that the named concurrency legs behave as claimed. It does **not** make the obligation set wholly green: the two `N/A-engine` legs have no executable statement in this design set, and (L9)'s projection re-check is defensive and unexercised. Nor does it establish ratification, implementation, or the sketch's other §10 gates.
7. **No `.proto`, no state-machine spec in wire terms.** Open item 6 / `AG-1` remains open; §4 is its input.
8. **v1 is one `dp-core` instance and therefore one gateway replica.** The multi-replica machinery of §5 is designed and tested in the harness, not deployed. `I` (one instance's commit rate) is the binding ceiling of the whole telemetry path until extraction or a multi-instance DP decision (§13 AGW-14).
9. **Agent self-upgrade is deferred**; the version window (§4.12) rejects, it does not remediate.
10. **Stream separation does not defeat TCP.** A lost segment stalls every stream on the connection; a `Revoke` on a lossy path lands no faster than TCP recovers. Connection-level flow control is capped so telemetry alone cannot starve control (§4.1).
11. **Rendered configuration must fit one message.** There is no chunking and no blob fetch; `max_message_bytes` is a rendered-config size limit surfaced as an apply error at render time. A large-payload path is routed (§13 AGW-13), not designed.
12. **Delivery latency is bounded by `command_poll_interval`** when the after-commit wake-up is unavailable (§5.4), not by "immediately".
13. **In v1 the gateway's process holds the DP datasource**, because it is `dp-core`'s process. The isolation the design guarantees before extraction is module-level (import, datasource and bean-lookup rules with planted-violation proofs); process-level credential isolation is an extraction property (§9).
14. **Telemetry labels are DP-minted; the replica registry is grammar-bounded and capped, not verified.** No agent-chosen string is a telemetry label on an agent batch, and a `DeclaredInstance` batch's `source_key` is DP-observed (§6.1). The agent's replica strings reach two tables, `agent_replica` and `agent_replica_incarnation`, once each, only under the RFC 1123 / uuid-hex-decimal grammars and under `max_replicas_per_binding` (which counts **active** replicas, released by `replica_idle_retirement`) / `max_incarnations_per_replica`, audited to the trusted report that asserted them; the machinery is [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md). A secret that is itself a valid lowercase hostname or hex string could therefore be registered once. **`AGW-D13`'s `I6` clause does not ratify until §13 AGW-17 closes, and `AGW-D16` does not ratify until AGW-17 *and* §13 AGW-20 both close — its retirement clauses additionally requiring §13 AGW-19** — runtime verification of reported replica identities — or the architect group explicitly accepts the grammar-bounded residual as the same one `dp-remote`'s reported hostnames already carry. MI-declared labels do not exist until the Solution Package contract gains them (§13 AGW-16), so an MI metric that needs its own dimensions cannot be collected as one series in v1.
15. **The lease store is `AGW-D15`'s, not `SM-D28`'s — and it is gated, not settled, and not in this document.** `agent_lease` gives the DP-side lease store `SM-D28` leaves to the agent sub-spec a home, a shape and write semantics; it is the record the delivery gate reads. It is its own decision so that ratifying open item 34 (two claim changes, `AGW-D7`) is never mistaken for approving a fifth table — and it **ratifies only with the CP issuance contract** of §13 AGW-18 (limit 17). Its machinery lives in [`lease-and-registry-sketch.md`](lease-and-registry-sketch.md); §5.2 states only the guarantee the poll joins against. **Ratifying `AGW-D1`…`AGW-D14` therefore asserts nothing about that machinery's correctness** — which is the point of the split.
16. **The report-only credential is not designed here.** [`../../go-agent/design.md`](../../go-agent/design.md) §3.1 wants one; this draft issues none — not at enrolment (replay would leak it) and not at first accept (no idempotent issuance arbiter is specified) — and carries it as §13 AGW-12. Post-expiry reports on the *same* mTLS session are authenticated by the session and labelled untrusted (§4.8); post-expiry reports on a *new* connection are not possible in v1.
17. **A CP grant can be wasted, and one recovery path is not ours to build.** The lease ledger reserves before the CP call and completes after it; if `dp-core` dies in between, the CP may have issued a grant no row records. **What the DP no longer does is foreclose the repair:** a completion that arrives after its session was re-claimed now writes **nothing at all**, so the request stays `PENDING` and the agent's next owner re-issues it under the same `request_id` — where round 8 completed it `FAILED('STALE_EPOCH')`, which was terminal and meant no owner ever re-called the CP, making AGW-18 unconsultable for the one case it exists for. The `PENDING` row makes the gap visible and bounded (`pending_ttl`, `attempt_deadline`) and the grant's own TTL bounds its authority, but the recovery is **taking the same request over under its own id** — because on a `renew` the nonce is single-use, so abandoning the request for a new id would consume the agent's only renewal credential and strand it at re-enrolment. Taking over therefore requires CP-side idempotency under the request id, or a CP status lookup by it, and that is **the ratification gate on `AGW-D15`** (§13 AGW-18), not a nicety. Until it exists, the honest fallback is: after `takeover_attempts` attempts the request is completed `FAILED('TIMEOUT')` and the session is refused `RE_ENROLL_REQUIRED` — an operator event, never a silent nonce-free grant. **Two recoveries, two mechanisms, and they are different failures:** a *gateway process* death raises the agent's epoch, and the request survives it by an **authenticated epoch transfer** into the agent's new session (§8 row 42) — without that, the one case the ledger exists for would be the one case that loses the nonce; a *stalled or dead CP call* is recovered by the bounded **takeover** (§8 row 35). A superseded session's completion is **discarded** either way — it writes no ledger change and no projection, the paused caller drops the grant it holds and closes its stream, and the request remains adoptable (§8 rows 39, 42). That grant is wasted authority bounded by its own TTL; the *request* is not.
18. **The ledgers need their retention job.** `agent_claim` and `agent_lease_grant` grow at the renewal and reconnect rate (§5.9) and the runtime role cannot delete from them; `ledger_retention` and the migrator's retention job are install requirements. Retention also bounds idempotency: a retry older than the horizon is refused as `REQUEST_EXPIRED` from its tombstone, never silently treated as new.
19. **The idempotency horizon is `tombstone_retention`, and beyond it a replay is a new request.** A tombstone is what makes `REQUEST_EXPIRED` a row rather than an inference (§5.2), but tombstones are themselves pruned. A replay of a `requestId` whose tombstone has also been deleted is treated as **new** — a fresh claim, or a fresh lease request. At 24 bytes a row the term is cheap enough for years (§5.9), so the mitigation is to configure `tombstone_retention` far beyond any plausible retry delay (≥ 1 year), not to pretend the horizon is infinite.
19a. **A first `issue` that failed re-opens the nonce-free path once its ledger row is pruned.** `issue`-once has two arbiters: the `agent_lease` row, which is never deleted, and the ledger's partial unique index, which retention deletes. An identity that ever *held* a lease is therefore refused forever; an identity whose only `issue` ended `FAILED` — so nothing was projected — can take a second `issue` under a new request id after `ledger_retention`, and if the CP had already minted a grant for the failed request, two grants for one identity can be live at once (the newer wins the projection; the older stays valid at the CP until its TTL). `SM-D28`'s renewal nonce is **not** bypassed — the path is open only where no nonce was ever issued. The mitigation available is configuration (`ledger_retention` ≫ the lease duration, already required, §5.8); a retention-proof arbiter would be a new column on a §5.2 table and is routed with `AGW-D15`'s gates ([`lease-and-registry-sketch.md`](lease-and-registry-sketch.md) §2.1, (L7)).
20. **The retired-incarnation window trusts the agent's timestamp, which is the one place admission does.** §6.1 accepts a sample labelled with a retired `incarnation_id` iff its `ts` is inside that incarnation's lifetime — necessary, because the case it exists for is a disk buffer flushed across a restart, and only the sample can carry that claim. The consequence: a compromised agent cannot label *current* readings with a dead incarnation, but it can **backdate** readings into that incarnation's window and rewrite a past interval of the replica's series. Nothing compares `ts` against the session's measured `clock_offset_ms`, `skew_tolerance` or `producedAt`, and the tighter rule needs the disk-buffer horizon `AG-D9` owns, so it is **not decided here**. Bounded by: a finite window, one replica's series, and `dp_agent_ingest_rejected_total` plus gap markers making the *rejected* half visible. Routed with §13 AGW-17, which already gates this registry; §8 row 44 measures the accepted forgery rather than asserting it cannot happen.
21. **A reporter handoff cannot distinguish a genuine move-back from a very late report.** Who may report a replica is DP-owned: a report from an agent that is not the current `reporter_agent_id` is refused `REPORTER_DISPLACED` while the incumbent is still reporting, and admitted as a handoff once it has been silent for `reporter_handoff_grace` (§6.1). **The residual:** a *delayed* report from a displaced reporter that arrives **after** that grace is indistinguishable from the workload genuinely moving back to that host, and is admitted — retiring the current incarnation and registering the displaced agent's. Bounded by `reporter_handoff_grace` (so it needs `report_interval`, §13 AGW-19, to have a defensible value) and by the handoff being recorded with `reporter_since` and counted; measured by §8 row 43 rather than claimed away. The alternative — refusing every cross-agent report — would make a rescheduled workload permanently unreportable, which is worse.

All of it is **PROPOSED input for the `AG-D*`/`AG-1` owners** and none of it is settled here.
