**Broker tested:** `soltr_10.25.0.177` (image `solace-pubsub-enterprise:10.25.0.177`, linux/arm64, one container, two Message VPNs), SEMP **2.48**, client library `solclientjs` 10.18.3 via the Web App SDK (plus `solclientjs` driven directly for the raw-wire legs) · **Run:** 2026-09-30, cold (volume removed, broker re-created, re-provisioned), **126 tests in 13 files, all green; 150 leg records** · **Round:** 4 — the five MINOR findings of the review that accepted round 3 (dispositions below); supersedes round 3 (same day), whose review found no blocker or major but asked for them to be fixed "before the owner relies on the doc for item 35". Round 3 had superseded round 2 (same day), which an independent review returned CHANGES-REQUIRED (1 major, 5 minor — dispositions below); round 2 had superseded round 1 (1 blocker, 2 major, 3 minor), which had superseded the 2026-09-29 run (1 blocker, 4 major, 4 minor).

> **What this document is.** [`console-integration.md` §11.3](../common/contracts/console-integration.md#113--the-broker-acl-spike-matrix-written-not-executed) is a matrix that was written and, until 2026-09-29, never executed. Harness, provisioning, tests and raw evidence: [`backend/spikes/mesh-scope-acl/`](../../../backend/spikes/mesh-scope-acl/README.md).

> **Authority.** The project owner, deciding on behalf of the architect group, said on 2026-09-29 "Let's solve this today and unblock it", and on 2026-09-30 answered "Yes, fix 32/33/35" to a request to fix the broker-permission test with two fixes (a dedicated browser client profile; a ticket-issuer rule on the user id), with **"the gates stay closed until the fixed test passes and a review accepts it."** This document is evidence for that review. >
> **Conventions.** *Measured* = observed on the running broker (client outcome, SEMP monitor/config, or a broker counter). **Round 3: the delivery claims for legs 1–3, 4–10, 11a/11b, 13, 14, 14-composed(-coexist), 17d, 19c and 19e are counted at the broker** (the publish and queue legs 12C/15 already used broker counters and the spool) — the per-client SEMP monitor counter `dataTxMsgCount` ("The number of client data messages transmitted to the Client", read from the broker's own served SEMP monitor spec, `MsgVpnClient`) — in addition to the SDK handler, because the Web App SDK only calls a handler whose *local* pattern matches and drops the handler when a subscribe fails, so a handler-side `got == []` is true by construction and cannot show a leak. *Derived* = arithmetic or a reading of the harness, not separately observed. Solace-semantics claims are cited to docs.solace.com, fetched 2026-09-30 (`I2`); a quoted sentence appears verbatim on the fetched page. Requirement: `REQ-012`.

## Verdicts

| Question | Answer |
|---|---|
| Can a Solace ACL confine a subscriber to a two-level scope (sub-organization AND environment) in §11.2's notify shape, with one substitutable identity level? | **Yes for direct subscriptions — measured, legs 1–10 pass, with delivery counted at the broker across all 8 leaf environments (leg 1: 2 messages transmitted of 18 published) — for a browser session that is bound to its own provisioned identity.** ⚠️ Three conditions. (1) **Not by the subscribe ACL alone** — a client that may *bind or create a queue* reads whatever the queue is subscribed to (leg 15d), so confinement needs the `sm-browser` client profile. (2) **The binding from a browser to that identity is not made by the broker — it is made by the ticket issuer.** *Measured:* non-browser usernames cannot be minted (16a–16d) and a ticket for one organization is refused at the other (17a–17e). *Measured on the spike's principal-bound `/ticket` stand-in:* a principal receives only its own grant, and asking for another grant, organization, audience or lifetime is refused (19a, 19b, 19e). *Measured as a hole:* the spike's unauthenticated `/token` lets any caller take another grant's scope — a caller-chosen grant id read su1/prod (19c) — and a 3650-day lifetime (19d). ⚠️ ***Not measured:* a product issuer's caller authentication, and the RBAC check that assigns a principal its grant** — the spike's credential is a static bearer string. (3) **No other Message VPN is reachable through the browser web transport** (20a–20c). |
| Is the client profile enforced by the **broker**, or only by the client library? | **The library refuses first; the broker refuses regardless.** With the library's gate forced open, the bind, create and browse still fail at the broker: `bindRequestCount` 2, `bindSuccessCount` 0, `guaranteedDeniedBindFailureCount` 2 (leg 15a-wire). Single-flag ablations: `allowGuaranteedMsgReceiveEnabled=false` stops a bind, `allowGuaranteedEndpointCreateEnabled=false` stops creation — neither substitutes for the other. |
| Legs 7/8 — subscribe-time refusal or silent no-delivery? | **Subscribe time.** `SUBSCRIBE_ACL_DENIED` from `subscribe()`; the broker-held subscription set is identical before and after each refusal, and afterwards only the granted leaf is delivered. |
| **Round 2 — can a ticket from the ruled issuer become a non-browser identity?** | **Not from the round-2 issuer; yes from the round-1 issuer (and from the measurement-only raw endpoint).** Measured: `sub="sm-internal-orgA"` over OAuth resolves to `acl-internal` + `sm-internal`, subscribes `sm/v1/>`, receives the prod event, and **publishes a forged prod event that a real subscriber receives** (16b); the broker built-in `#client-username` resolves to `#acl-profile` (connect/publish/subscribe all `allow`) and does the same (16b-system); `orgA-su1-dev-ctl` binds a prod-subscribed queue (16b-queue). | **Round 3 — temporary queues and topic endpoints (`sm-browser` advertises TEMP_ENDPOINT true)?** | **The browser cannot create either; measured at the library and at the broker.** Plain: the library refuses ("Consumer is not supported by the broker for this client"). Capability gate forced open: the **broker** refuses the temporary queue (`bindSuccessCount` 0, `guaranteedDeniedBindFailureCount` 1, "Service Unavailable") and the topic endpoint on the *granted* topic (same refusal — profile-attributable, because the subscribe ACL allows that topic) and on the prod topic ("Subscription ACL Denied"). `sm-internal` controls with the identical ACL create both, and a topic added to a temporary queue is still gated by the subscribe ACL (15j, 15k). |
| **Round 3 — is any other Message VPN reachable through the browser wss endpoint?** | **Yes, in the stock state; closed by the install check's remediation.** Measured: the broker's built-in `default` VPN is enabled, web transport on, basic authentication type `none`, and its `default` client username sits on the `default` ACL profile, which allows publish and subscribe; through `wss://localhost:9444/mesh` a browser connected as anyone/anything, subscribed `>`, published and received its own message (20a). Applied temporarily and reverted (21d); **not** part of `provision.sh`. |
| **Round 4 — durable topic endpoints (admin-created)?** | **A browser identity cannot bind them; the refusals are attributed.** With the library gate forced open the broker refuses the bind — by the client profile when the ACL allows the stated topic (`Service Unavailable`, counted in `guaranteedDeniedBindFailureCount`), by the subscribe ACL when it does not (`Subscription ACL Denied`); spools untouched. | The zero-write stream route — does it hold? | **Only if the ticket issuer guarantees the JWT `sub` contains no `/`** (measured escape, 14-escape) — which the round-2 grammar guarantees by construction — **and the composed shape (a subject that also holds a notify grant) is now measured** (14-composed): 2 granted subjects, each confined on both branches. |
| Leg 13 (§11.4) | **No pass/fail — none claimed.** Candidate (a) measured in isolation: admits exactly the one topic and delivers exactly that fact; refuses every wider or adjacent topic. |

## Solace semantics used, with sources (fetched 2026-09-30)

- **The `/` prohibition (verbatim).** "any MQTT client IDs or client usernames that contain "/" characters will never be able to match the `$client-id` or `$client-username` elements of an ACL rule." — [Granting Clients Access](https://docs.solace.com/Security/Granting-Clients-Access.htm). ⚠️ **Measured contradiction on 10.25.0.177 (leg 14-escape):** a client username containing `/` (`<victim>/s1`) *does* match `$client-username` and is allowed the other subject's branch and receives its traffic. The documentation describes a non-match; the broker produces a match. Do not rely on the documented behaviour.
- "Substitution variables must appear alone at any level in the topic exception, but they can appear multiple times in a single exception." — same page.
- "Subscribe-topic access controls are not considered when a consuming client binds directly to a durable endpoint (either a queue or topic endpoint)." — same page. Measured: leg 15d.
- "If the ACL profile disallows all subscriptions by default, wildcard characters in the subscription are not given any special treatment when establishing matching exception rules." — same page. Consistent with legs 2, 3, 7, 8.
- **OAuth username resolution and `default`** — [Client Authorization Overview](https://docs.solace.com/Security/Client-Authorization-Overview.htm): for OAuth, "the client receives a dynamically created username and is assigned the client profile and ACL profile associated with the username"; "If the client does not provide a client username, the event broker attempts to apply the client username named `default`"; "The `default` client username in not enabled by default." (sic). **The page contains no statement restricting a client username to one authentication scheme** — absence on that page, not a Solace assertion that it is impossible; the measurements (16b) show a basic-auth username *is* reachable via OAuth `sub`, and the broker built-in `#client-username` likewise.
- ACL defaults and the connect-exception behaviour on live clients — [Managing Access Control Lists](https://docs.solace.com/Security/Managing-Access-Control-Lists.htm).
- Client-profile flags — [Configuring Client Profiles](https://docs.solace.com/Security/Configuring-Client-Profiles.htm): `allow-guaranteed-message-receive` permits clients "to bind to topic endpoints or queues"; `allow-guaranteed-endpoint-create` permits clients "to create queues or topic endpoints"; `allow-guaranteed-message-send` permits "non-persistent or persistent messages"; `allow-shared-subscriptions` permits shared subscriptions. The stock `default` profile reads all of these ON on this broker (measured), hence pinned closed.
- **Temporary endpoints (round 3).** [Configuring Client Profiles](https://docs.solace.com/Security/Configuring-Client-Profiles.htm): clients "may only dynamically create durable and non-durable/temporary queues or topic endpoints on the event broker if it uses a client profile that has the `allow-guaranteed-endpoint-create` parameter enabled." [Endpoints](https://docs.solace.com/Messaging/Guaranteed-Msg/Endpoints.htm): "Temporary queues and topic endpoints are dynamically created and destroyed by client applications." That page does **not** say whether topic subscriptions on a temporary endpoint are subject to the ACL subscribe controls — that is **measured** (15j/15k controls: a topic added to a temporary queue is refused "Subscription ACL Denied"), not cited.

- **`dataTxMsgCount`.** The docs SEMP reference is a single-page app that WebFetch could not read; the definition is taken from the broker's **own served spec** (`/SEMP/v2/monitor/spec`, `MsgVpnClient.dataTxMsgCount`): "The number of client data messages transmitted to the Client." Its behaviour is validated by the positive controls: it equals the delivered count in every allowed leg and rose for the escape victim traffic (14-escape).

That the exception is evaluated against the address the broker sees — the proxy's, for a gateway path — is **measured** (21b/21c), not cited.

## Provisioning requirements this run adds (for `BE-D5`, the install runbook and the gateway ticket design)

1. **Client profile.** Every browser-facing client username — including each VPN's `default` — uses a client profile with guaranteed send, guaranteed receive, guaranteed endpoint create, shared subscriptions, transacted sessions and bridge connections **all off** (`sm-browser`); the stock `default` client profile is pinned closed; both asserted from SEMP config in the install check.
2. **Reserved browser grammar (round 2, replaces the round-1 wording).** The ticket issuer mints `sub` **only** from a reserved grammar (spike: `^br-[0-9a-f]{16}$`, a server-generated id) — an allow-list. **Every** client username in **every** VPN is either (a) matching the grammar and then `sm-browser` with a publish-disallow ACL, or (b) not matching it and then never reachable through the issuer. This covers **internal publishers, control and ablation identities, other organizations' usernames, `default`, and the broker built-in `#client-username`** — the broker offers no per-scheme restriction on a client username, so the grammar is the barrier. The install check enumerates all client usernames from SEMP (following paging) and fails on any violation (spike: `provision.sh` end section, `tests/07` 16-config, `tests/02` 12A-all; `tests/11` proves it fires). ⚠️ **This requirement stops a browser becoming an internal identity *through the issuer*. It does not stop one browser taking another browser's grant (requirement 7), and it does not cover basic authentication, which never touches the issuer (requirement 9).**
3. **Organization binding.** Each organization's VPN (or service) requires its **own** OAuth audience (or issuer); the issuer stamps the audience of the organization the browser belongs to. Pin **every** VPN's `default` client username explicitly (enabled/disabled, ACL, client profile) — never leave the stock one as the thing that happens to refuse.
4. **Revocation.** Revoking a notify grant is a SEMP write **plus** a session disconnect; removing an exception alone leaves the subscription live.
5. **Provisioner cost.** The notify tier needs a SEMP-writing provisioner (3 writes per new subject, +1 per additional scope; 4 for a subject that also streams). An ACL profile name is limited to **32 characters**.
6. **Issuer trust.** Only the gateway issuer's key may be trusted by the VPN OAuth profile; a second trusted issuer or a leaked signing key voids requirements 2, 3 and 7 (nothing else in the broker restricts `sub`).
7. **Principal-to-grant binding (round 3; UNMEASURED for a product issuer).** The ticket issuer takes `sub`, the organization/audience and the lifetime **only** from the authenticated, RBAC-checked principal's server-side grant record. The ticket request carries none of them (a request that does is refused, even if the value is the caller's own), the caller cannot extend the lifetime, and the maximum lifetime is short and fixed (spike stand-in: 900 s). Grant ids are not a secret and are sequential in the fixture, so the issuer — not the id — is the only barrier. Measured reason it is load-bearing: 19c (a caller-chosen grant id read su1/prod) and 19d (a 3650-day ticket). Measured behaviour of a stand-in that obeys it: 19a, 19b, 19b-auth, 19e. **Not measured:** real authentication, the RBAC check, credential theft. (Broker-side expiry is measured: an expired ticket is refused at login, 22a, and a live session is dropped at expiry with `disconnectOnTokenExpirationEnabled`, 22g.)
8. **Other Message VPNs (round 3).** The browser web endpoint forwards SMF for whatever VPN name the client chooses. The install check enumerates **every** Message VPN on the broker service (following paging) and requires that any VPN other than an organization's own is disabled, or has its web transport (plain-text and TLS) off; a VPN merely changed from authentication type `none` to `internal` stops the anonymous login (20b, M3) but stays reachable and is still flagged by the check as implemented. Measured mitigations: 20b/20c. The alternative — a gateway that pins the VPN name — is **not measured**. On a customer's shared broker this includes VPNs the customer owns for other purposes.

9. **Internal identities and the gateway path (round 4; measured on the fixture, not provisioned).** Any client username with a password and a non-browser ACL (`sm-internal-*`, control, ablation) is usable by basic authentication through the browser-facing gateway (21a). So: (a) the credentials of internal identities are **never** held by, or delivered to, a browser, are strong random secrets (the spike's password = username is a throwaway) and are rotated; (b) internal identities must not be usable from the browser path — measured mitigation 21c: the identities' ACL profile has client-connect default `disallow` and an exception for the backend's source address(es), which also refused an OAuth login with a raw token naming the identity; it holds **only if the gateway and the backend present different source addresses to the broker** (they do here: proxy container vs Docker network gateway) and that is a deployment fact the runbook must check, not something this run establishes for an on-prem co-located install; and **only if nothing a browser can reach connects to the broker from the allowed address**, i.e. the broker's non-gateway listeners are not browser-reachable (derived from 21b/21c, not separately measured); (c) the install check should assert (b) — it does not today. Alternatives not measured: client-certificate authentication for internal identities, or a separate Message VPN/service for internal traffic.
10. **Durable topic endpoints (round 4).** Client profile `sm-browser` (requirement 1) also stops a browser binding an administrator-created durable topic endpoint (15l); administrators who create endpoints in a VPN with browser identities need no extra rule for them, but note the ACL is consulted for a topic-endpoint bind's stated subscription, which is *not* the queue behaviour (15d).

## Limits of this run

One broker container, one platform (linux/arm64), Enterprise 10.25.0.177, client library 10.18.3; two VPNs on the same broker rather than two broker services; loopback-only; OAuth via a spike issuer with a static JWKS. The hostile-client simulation forces two library latches open and is not a raw-protocol fuzzer; the raw-wire legs (16d, 17a–17e) use `solclientjs` directly, which is a real client but not a hand-built SMF frame. The issuer grammar guarantee is an *issuer* property, not a broker one: it holds only while the issuer is the sole trusted signer (requirement 6). **Not measured:** OAuth authorization-group mode (an alternative that would not derive the username from `sub`), broker restart, HA, **token expiry during a live session is measured (22g) but clock skew between a real gateway and broker, `nbf`, JWKS refresh timing and a `kid` the JWKS does not list are not**, key rotation and key management, the combined access-token-plus-ID-token presentation (refused when valid; not explained), the client-connect address restriction on a deployment where the gateway and backend share a source address (and IPv6), client-certificate authentication for internal identities, bypass attempts on a durable topic endpoint beyond the three variants run (15l), **real caller authentication and the RBAC check that assigns a principal its grant (the `/ticket` credential is a static string)**, a gateway that pins the VPN name, the TLS web service on the other-VPN path, a Solace Cloud service-per-organization deployment. Delivery counts come from the broker's `dataTxMsgCount`, whose definition is the broker's own served spec; it counts client data messages transmitted, so a message the broker discarded before transmit does not appear — which is the property being asserted. Counts marked *derived* are not measurements.
