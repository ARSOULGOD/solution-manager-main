### 1.2 Authorization is scope-evaluated, with downward inheritance

Approved: **canonical role bindings and downward scope inheritance**. A binding is
`(principal_id, role_id, scope_id)` referencing a **canonical scope record** — never a name, never a path string,
never an id array. A grant at a scope reaches that scope and everything beneath it; it reaches nothing beside it.

⚠️ **Visibility is prefix-comparable in *either* direction, and that is a correctness requirement, not a
generosity.** `SM-D33`'s own text says so and records that **two earlier drafts got it wrong**: a scope is visible
when it is at or below a held grant **or is an ancestor of something held**. Without the ancestor direction a
principal granted at `[org, unit, dev]` would `404` on its own parent unit, and the hierarchy cascade the declare
flow depends on would be unreachable to the very principal the grant was made for. **Reaching** (may I act here?)
is downward-only; **seeing** (may I navigate to it?) is bidirectional. Both halves are approved.

**This closes `BE-D15` §5.1's flagged v1 deviation by rejecting it.** That deviation proposed *whole-install*
evaluation for v1; it is **not** approved. `REQ-006`'s acceptance sentence — *"a user's effective permissions derive
from scoped assignments"* — is satisfied literally, not narrowed. `SM-D33`'s prefix algorithm is therefore
**confirmed in substance** by this approval; its *family* status is untouched (the `SM-D*` set still ratifies as a
set — the ratification matrix's `SM-D1`–`SM-D34` row; ⚠️ open item 8's own enumeration stops at `SM-D31` and does
not yet name `SM-D32`–`SM-D34`, so cite the matrix row, not the item), and `SM-D32`'s hierarchy is the scope tree
the bindings resolve within.

### 1.3 Identity, sessions and bootstrap

### 1.4 Append-only control-plane audit

Privileged **CP and gateway** actions write an append-only `sm_control.audit_log`
`(at, actor_principal_id, verb, resource_kind, resource_id, tenant, outcome, detail jsonb)` synchronously inside
their own transaction. Append-only is an **artifact, not a convention**: `GRANT SELECT, INSERT` to the CP runtime
role and no `UPDATE`/`DELETE`, with a runtime-`UPDATE` refusal test.

Privileged **DP** actions (`config.apply`, `config.rollback`, `instance.restart`) are audited by `apply_request`
itself, which `BE-D13` §3.1 already designed as audit-grade. The two sources are unioned **at query time** in the
gateway; a DP mutation writing the CP's table synchronously would require exactly the cross-plane transaction `I7`
forbids. This split is approved as designed.

### 1.5 One enforcement point

`authorizationService.require(principal, verb, resource)` — **every** endpoint, gateway and core services alike.

**Approved as prohibitions, because that is the half that is testable:**

- **No controller-local role checks.** No annotation that encodes a role name. No second path.
- **No production super-admin bypass.** The administrator is a built-in role with every catalog verb *bound* —
  special by grant, never by code path. No `isAdmin` branch, no numeric role level, no development-only flag that
  can be set in production.
- **`superAdmin` in an API response is a badge, not a bypass.** The frontend overlay is cosmetic; the server
  authorizes every request regardless of what the overlay rendered.
- Enforced by an ArchUnit rule with a planted-violation proof: nothing outside the authorization package
  references role names or binding tables.

### 1.6 Introspection

`authz.introspect.self` grants sight of one's **own** effective permissions; `authz.introspect.any` grants sight of
**any** principal's. The split is approved — it is the amendment's own §4 answer to the permission-enumeration
question, and `.any` is high-consequence.

⚠️ **Five consequences of those lists, recorded rather than quietly fixed** — ⚠️ **five, not four; a fifth was added when a review found introspection unaccounted for** — each is a real operational gap that
follows from the ruling as given, and none is changed here:

1. **An Operator cannot open a live chart tail.** It holds `mesh.ticket.mint` (so it joins the mesh and receives
   notify events) but **not** `mesh.stream.grant`, and a raw chart tail needs a stream grant
   ([`console-integration.md`](common/contracts/console-integration.md) §10.1). Operators get live *invalidation*
   and REST charts; live tails are Administrator-only.
2. **An Operator cannot stop an instance.** `instance.stop` is Administrator-only, while `instance.restart` is an
   Operator verb — so the role that may cause an outage by restarting may not cause one by stopping. That may be
   deliberate (a stop is the more durable action) and it is worth the owner confirming. ⚠️ **ROUTED, not silently
   left open** (`docs/checklists/spec-review.md`: *"anything undesigned is explicitly routed — never silently
   absent"*): carried as a **handover question to the project owner** alongside the scope-tree question in
   [`plans/backend/006-local-identity-and-scoped-rbac.md`](../plans/backend/006-local-identity-and-scoped-rbac.md).
   ⛔ **Until the owner answers, the lists stand exactly as ratified** — do not move `instance.stop` into
   `Operator`, and do not remove `instance.restart` from it.
3. **Nobody but an Administrator can read the audit log**, `audit.view` being Administrator-only. An auditor role
   was among the mockup's proposals and is not approved, so audit review is an administrative act in v1.
4. **An Operator cannot export metrics or force the raw tier** (`metrics.export`, `metrics.forceRaw` are
   high-consequence per `architecture.md` §16), so CSV export is Administrator-only.
5. ⚠️ **Neither Viewer nor Operator holds any introspection verb.** `authz.introspect.self` is outside both lists,
   so it is Administrator-only — which is survivable **only because of OR-15**: reading the *current* principal
   needs no verb at all. What it does mean is that the Admin **access-review** screen, which is what
   `authz.introspect.self` governs, is Administrator-only. ⚠️ The two rulings are load-bearing **together**: were
   OR-15 revisited, a Viewer would render an empty permission overlay while still being able to act.
