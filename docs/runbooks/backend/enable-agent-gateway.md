## When to use

You are enabling the agent-facing gRPC/mTLS listener for the first time, or enrolling another `host-local` agent. The agent is outbound-only: it dials the Data Plane; the Data Plane never dials the host. A dp-remote-only installation needs none of this: with `SM_AGENT_GATEWAY_ENABLED` false (the application's default; `runtime/compose.yml` now takes `${SM_AGENT_GATEWAY_ENABLED:-true}`) the application opens no agent port and reads none of the material below. **A compose install still requires every file under `./certs` and `SM_AGENT_ENDPOINT`** (compose secrets and the `:?` interpolation fail closed whether or not the gateway is on), so create placeholders for them if you turn it off.

## Preconditions

- Docker with Compose v2 on the Data Plane host; `openssl` 3.x; a JDK `keytool` (17 or 21) on the host that makes the keystore; PostgreSQL 14 (compose brings one; production should use yours).
- The image, built only through `runtime/scripts/build-image.sh <tag>` (see [`release-the-images.md`](release-the-images.md); `--check` proves the build reproducible). Pin the tag you deploy in `SM_IMAGE`.
- **No database password and no keystore password is typed or put on a command line in this runbook**: the five database role passwords are generated by `runtime/scripts/init-secrets.sh`, and the CA keystore password is generated into a `0600` file below. (The **bootstrap administrator secret** is the exception: hashing it is the procedure in `backend/README.md` step 4, which puts the secret in a shell command; do that on a host you control and clear the history.) There is **no SQL provisioning** of agents, tokens, registrations or roles: everything agent-specific goes through the API.
- The solution the agent will manage is **loaded and entitled** in the organization (an enrolment names a catalog `solutionId` and one of its loaded `packageVersion`s; an unloaded one is `422`).
- A principal who holds `agent.enrol` **and** `target.create` at the environment (the Administrator role; the Operator holds `agent.view` and `agent.drain` only, the Viewer `agent.view`).
- **Certificates and the CA keystore** (next section). Agent client certificates live **30 days** (`SM_AGENT_CA_LEAF_TTL`) and **there is no in-place renewal**: read [Before an agent certificate expires](#before-an-agent-certificate-expires) before you enrol the first agent.

### Certificates and the CA keystore

Everything lives in `runtime/certs/` (gitignored). Compose delivers each file as a read-only secret (`/run/secrets/...`); `up` fails if one is missing. The commands below keep the keystore password out of argv, out of the environment and out of shell history: it is generated into a file created under `umask 077`.

```bash
cd runtime && mkdir -p certs && cd certs
umask 077                                                          # every file below is created 0600
openssl rand -base64 32 > agent-ca.password                       # the keystore password: ONE line, newline-terminated (the launcher strips the newline; keytool and openssl read the first line)
# 1. the agent CA: signs every agent client certificate; its key sits in the keystore under the alias `agent-ca`
openssl req -x509 -newkey rsa:3072 -nodes -keyout agent-ca.key -out agent-ca.pem -days 1095 -subj "/CN=Solution Manager agent CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign,digitalSignature"
openssl pkcs12 -export -inkey agent-ca.key -in agent-ca.pem -name agent-ca -out agent-ca.p12 -passout file:agent-ca.password
# 2. the gateway's server certificate: its subjectAltName must cover EXACTLY the host in SM_AGENT_ENDPOINT
openssl req -newkey rsa:3072 -nodes -keyout gateway.key.rsa -out gateway.csr -subj "/CN=sm.example.test"
printf 'subjectAltName=DNS:sm.example.test\nextendedKeyUsage=serverAuth\nbasicConstraints=CA:FALSE\n' > ext.cnf
openssl x509 -req -in gateway.csr -CA agent-ca.pem -CAkey agent-ca.key -CAcreateserial -out gateway.crt -days 365 -extfile ext.cnf
openssl pkcs8 -topk8 -nocrypt -in gateway.key.rsa -out gateway.key          # the gateway reads an unencrypted PKCS#8 key
rm gateway.key.rsa gateway.csr ext.cnf agent-ca.srl
```

(The `openssl x509`/`pkcs8` commands are carried over from the previous revision, where they were run by hand on 2026-10-07. The `-passout file:` form reads the first line of the file only (`man openssl-passphrase-options`, OpenSSL 3.6.4). The keystore alias `agent-ca` is what `compose.yml` sets in `SM_AGENT_CA_KEY_ALIAS`. No `pass:` argument, no `export` and no typed password remain.) **The gateway certificate is valid 365 days**: put its expiry in your monitoring too.

#### The lease-nonce HMAC key (required before the first start)

The control plane signs lease nonces with an HMAC key that is a **secret-key entry in the same CA keystore**, opened with the same password. Create it **before the first start**. Without it no lease is issued and, with `sm.control.agent-gateway.ca.required` true (it follows `sm.agent.gateway.enabled`), the process does not start (`AgentGatewayBootGuard`).

```bash
# one line on stdin = the secret (64 hex characters = 64 bytes); the keystore password comes from the file
openssl rand -hex 32 | keytool -importpass -alias lease-nonce-hmac -storetype PKCS12 -keystore agent-ca.p12 -storepass:file agent-ca.password
keytool -list -storetype PKCS12 -keystore agent-ca.p12 -storepass:file agent-ca.password   # expect agent-ca (PrivateKeyEntry) and lease-nonce-hmac (SecretKeyEntry)
```

⚠️ **Do not feed the keystore password to `keytool -importpass` on stdin.** A pipeline such as `{ cat agent-ca.password; echo; openssl rand -hex 32; } | keytool -importpass ...` (this runbook's first revision) stores the secret from whichever line comes second. With a password file that ends in a newline (what `openssl rand ... > file` and every editor produce) that line is empty: `keytool` exits 0, `keytool -list` shows a `SecretKeyEntry`, and the launcher then fails at boot with "lease nonce key cannot be loaded". The form above has one stdin line, the secret, and cannot be shifted.

What was **measured** (2026-10-12, with `keytool` and a Java probe that reads the entry the way `Pkcs12LeaseNonceSigner` does: `KeyStore.getKey`, `getFormat()`, `getEncoded()`; on Microsoft OpenJDK 17.0.17 and Homebrew OpenJDK 21.0.12.1; the commands above run exactly as written, once per JDK, with a base64 password file made under `umask 077`):

- Both JDKs: `rc=0`, the entry reads back as `RAW` with **64 bytes**, the CA private key in the same keystore still reads with the same password, the password file is `-rw-------`. A keystore written by either JDK was read by both earlier in the session.
- The old form above, run on a newline-terminated password file: `rc=0` and `keytool -list` shows the `SecretKeyEntry`, but `KeyStore.getKey` throws `Get Key failed: Empty key` on both JDKs.
- `keytool` stores the secret as `PBEKey`, with as many bytes as the secret has characters; the application **refuses an entry shorter than 32 bytes** and `keytool` itself accepts a 31-character secret (measured), so use 32 or more characters. It refuses an alias that already exists (`Secret Key not generated, alias <...> already exists`, exit 1). Piped, no confirmation prompt is read.
- **The `keytool` inside the launcher image (measured 2026-10-12, plan 015 Final, docker context `default`; image built by `runtime/scripts/build-image.sh`, manifest `sha256:a75d9fc0fb93adb70f5ab6e1a28f065bd428e06ad9aa29929caaf58276671de2`, base `eclipse-temurin:21-jre-jammy` at its pinned digest):** the JRE image **has** `keytool` (`/opt/java/openjdk/bin/keytool`) and runs it as uid 10001 (`sm`); its Java is `Temurin-21.0.12.1+1`, the same 21.0.12.1 as the Homebrew JDK measured above. With a keystore made by this runbook's commands (host `keytool -importpass`, one stdin line; password from a file, never argv) bind-mounted read-only, `docker run --rm -v "$PWD:/w:ro" --entrypoint keytool sm-launcher:<tag> -list -storetype PKCS12 -keystore /w/agent-ca.p12 -storepass:file /w/agent-ca.password` exits `0` and prints `agent-ca ... PrivateKeyEntry` and `lease-nonce-hmac ... SecretKeyEntry` (`-list -v -alias lease-nonce-hmac` prints `Entry type: SecretKeyEntry`, exit `0`). The image's own `keytool -importpass` (the same one-line-stdin form, `docker run -i`) exited `0`, and its keystore listed both entries under the image's `keytool` and under the host's. **Not measured:** the entry's byte length as the application reads it after an *in-image* `-importpass` (only the entry type was listed); the 64-byte read-back above is from the host JDKs, whose 21.0.12.1 is the image's version. If a future image drops `keytool`, run the same commands with a JDK `keytool` on the operator's machine: the keystore is a plain PKCS12 file.
- The alias defaults to `lease-nonce-hmac`; it is the property `sm.control.agent-gateway.ca.lease-nonce-key-alias` (not mapped to a variable in `compose.yml`; changing it needs an overlay property).

Facts to keep: the key is **read once per process**, **never logged**, and **not backed up with the configuration** (back the keystore up like a key). **Rotating it needs a restart.** What that does to agents (read from `JdbcAgentLeaseRepository` and `go-agent/internal/msg/classify.go`; not run): an agent that holds a nonce still renews, because the digest of the nonce the agent holds is what is compared; only a **lost-reply replay** is recomputed under the new key and fails, `LEASE_RENEW_REFUSED`, so the agent gets `SessionReject(RE_ENROLL_REQUIRED)` and **halts**. It does not re-enrol by itself: the operator revokes and re-enrols it.

Keep `agent-ca.key` offline once the keystore is built. The application needs only `agent-ca.p12`, `agent-ca.password`, `gateway.crt`, `gateway.key` and `agent-ca.pem`. Compose mounts them as secrets and the files must be readable by uid 10001 (the image's `sm` user), e.g. on Linux `chown 10001 certs/* && chmod 0400 certs/*`. The trust bundle you hand agents is `agent-ca.pem`.

### Database role passwords (`OR-138`)

`runtime/scripts/init-secrets.sh` is run **once, on the host, before `docker compose up`** (it is not a compose job: compose creates its secret mounts from files that must already exist, and `db` needs `db_superuser_password` before any job could run).

**The script also generates the data-plane master key, `dp_master_key`** (32 random bytes, standard base64, 44 characters with **no trailing newline**; `0600`, or `0640` with `--group`; never overwritten). The launcher **refuses to start without it** (`SM_DP_MASTER_KEY_FILE`, delivered as a compose secret), and compose also needs its label: set `SM_DP_MASTER_KEY_ID` in `.env` (letters, digits, `.`, `_`, `-`; up to 64; keep it stable). **Back the key up like a key: it seals every secret value the data plane stores, and losing it (or replacing it with another) fails the start-up canary and loses every sealed value.** Never regenerate it over a running installation.

- It writes five files into `./secrets` (or `--dir`, or `SM_SECRETS_DIR` from the environment or `.env`): `db_superuser_password`, `cp_migrator_password`, `cp_runtime_password`, `dp_migrator_password`, `dp_runtime_password`. The directory is created `0700`, the files `0600`, each **48 random alphanumeric characters** from `/dev/urandom`. It **never overwrites** an existing file (re-running changes nothing and warns about a file that is not a plain 48-character alphanumeric one).
- On **Linux** a bind-mounted file keeps its host owner, group and mode, so the image's user cannot read a `0600` file you own: run `sudo scripts/init-secrets.sh --group 10001 --dir ./secrets` to give the four role files that group at `0640` (the directory stays `0700`, the superuser file stays `0600`). `sudo` drops `SM_SECRETS_DIR`, so pass `--dir` or set it in `.env`.
- **Back up `./secrets` like a key. It is not configuration.** Losing the password files means resetting the roles' passwords by hand as the superuser; losing `dp_master_key` loses every sealed secret value, with no way to recover them. A copy of it is a credential. It is gitignored.
- `.env` carries **no password**, and `docker compose config` shows none.
- A future option, **not built**: make the two migrator roles `NOLOGIN` between upgrades so a leaked migrator password is useless outside an upgrade window.

Rotation is in [Rotating a database role password](#rotating-a-database-role-password-and-the-operator-tools) below.

## Steps

### 1. Configure

```bash
cd runtime && cp .env.example .env     # fill every empty value; compose refuses to start with one left empty (`:?`)
scripts/init-secrets.sh                # see above
```

`.env` values that matter for the agent path:

- `SM_AGENT_ENDPOINT`: the `host:port` agents are told to dial; it must be covered by the gateway certificate's subjectAltName.
- `SM_TRUSTED_ORIGIN`.
- `SM_TRUSTED_PROXY`: **set a placeholder IP literal now** (for example `192.0.2.1`, a documentation address) and replace it in step 3. Compose interpolates the whole file, so `SM_TRUSTED_PROXY` unset fails every compose command, not only `up` (measured 2026-10-12: `docker compose --profile bootstrap config` and `--profile migrate config` both stop with "required variable SM_TRUSTED_PROXY is missing a value"; `run` itself was not run).
- `SM_CONTROL_BOOTSTRAP_CREDENTIAL_HASH`: an Argon2id hash of the bootstrap administrator secret; there is **no hashing command in the image** (`runtime/launcher/bin/` has none): compute it as `backend/README.md` step 4 shows. The hash contains `$`, so **single-quote it in `.env`**: `SM_CONTROL_BOOTSTRAP_CREDENTIAL_HASH='{argon2id}$argon2id$...'`. Docker documents that unquoted and double-quoted values have interpolation applied and single-quoted values are used literally (docs.docker.com, variable interpolation, read 2026-10-12); an unquoted hash is corrupted.

### 2. Bootstrap and migrate the database

```bash
docker compose --profile bootstrap run --rm bootstrap       # Phase 0, as the superuser: roles and schemas. NOT idempotent by design.
docker compose --profile migrate  run --rm migrate          # Phase 1, as the migrator roles, in a separate JVM
```

If Phase 0 fails **after** its SQL ran, the roles exist without passwords: run `scripts/init-secrets.sh rotate all`. The heads after plan 015 W4, all anchored, were `sm_control` **V022**, `sm_data` **V031** and `sm_metrics` **V004**; after the reconciliation into `UAT` (`OR-147`) plan 015's migrations are `sm_control` **V026**/**V027** and `sm_data` **V043**–**V046**, so the heads are `sm_control` **V027**, `sm_data` **V046** and `sm_metrics` **V004**. (Record, not a check this runbook makes: the plan 015 W3 and W4 integration records.)

### 3. The console behind a TLS reverse proxy (`OR-136` (4))

The launcher's console listens in **plain HTTP** and compose publishes it on the host's loopback only (`127.0.0.1:8080`). Browsers reach it through a TLS reverse proxy that **you** run:

1. The proxy serves **exactly** the origin in `SM_TRUSTED_ORIGIN` (scheme, host, port) and forwards to `127.0.0.1:8080` on the Docker host. It must **overwrite** `X-Forwarded-Proto` with its own listener's scheme (a proxy that passes a client-sent value through lets that client assert `https` over plain HTTP).
2. `SM_TRUSTED_PROXY` is the address the proxy's connections arrive **from, as the launcher container sees them**. For a proxy on the Docker host that is the compose network's gateway address, **not `127.0.0.1`**. The network exists only after step 2 has run a compose command (reasoned: compose creates the project's default network when it starts a service; not run). Read the address and **replace the placeholder in `.env`**:

   ```bash
   docker network inspect sm_default --format '{{(index .IPAM.Config 0).Gateway}}'
   ```

   (The Go template was verified on a default Docker network on 2026-10-12. The name `sm_default` follows from `name: sm` in `compose.yml` and compose's `<project>_default` naming; confirm it with `docker network ls`. On Docker Desktop for macOS the proxy's address is that of the virtual machine's side, which this command does not tell you: verify with check 4. If the network is ever recreated its subnet may change: read the address again.)
3. The launcher **refuses to start** unless exactly one of `sm.gateway.trusted-proxies` (non-empty; compose sets it from `SM_TRUSTED_PROXY`) or `sm.gateway.direct-client-connections=true` is set; both unset, or both set, fail (`GatewayProperties`). Compose sets the first.
4. Verify through the proxy after step 4: `issueAgentEnrolment` (and `registerTarget`, `createUser`) must not answer `403 INSECURE_TRANSPORT`. That response means the proxy's address is not the one in `SM_TRUSTED_PROXY`. See also [`../operations.md`](../operations.md#behind-a-tls-terminating-proxy-insecure_transport).

The **agent port** (`9443`, mTLS) is published on all addresses and is not behind the proxy: agents dial it directly. The readiness socket (`9444`) is container-internal.

### 4. Start the application

```bash
docker compose up -d launcher
docker compose ps       # "healthy" once the readiness socket accepts, i.e. while the TLS listener runs (the HEALTHCHECK is every 10 s after a 90 s start period; the time to healthy was not measured)
```

The launcher verifies the CA keystore, the CA key and the lease-nonce key entry **at startup**; a missing or unreadable one fails the start with a message that names the missing piece and no key material.

Settings (defaults from `backend/launcher/src/main/resources/application.properties`; "passed" means `runtime/compose.yml` passes the variable through, so a value in `.env` reaches the container):

|---|---|---|---|
| `SM_AGENT_GATEWAY_ENABLED` | `true` in compose | yes | the gateway switch |
| `SM_AGENT_GATEWAY_ENDPOINT` (compose reads `SM_AGENT_ENDPOINT`) | none | yes | what enrolled agents are told to dial |
| `SM_AGENT_CA_LEAF_TTL` | `30d` | yes | agent client certificate lifetime (a ceiling) |
| `SM_AGENT_ENROLMENT_TOKEN_DEFAULT_VALIDITY` / `_MAX_VALIDITY` | `24h` / `30d` | yes | the token an issuer gets when it names no lifetime, and the longest it may ask for; the launcher refuses to start if the default exceeds the maximum |

#### The two scheduled jobs (`OR-140`)

Both run **whether or not the gateway is enabled**, under a **system actor** (`sm_control` `V027`, written `V022` before `OR-147`), so the audit trail says the system did it, not the principal who issued the token. A read (`listTargets`, `getHealth`) writes nothing.

- **The enrolment sweep** (`sm.gateway.agent-sweep.*`): retires an enrolment **interrupted between the two planes**: the token was used (the control plane has the agent target) but the target's data-plane connection never landed. Once the token has expired **and** `sm.dp.declare.abandon-after` (ten minutes by default) has passed, it revokes the registration and then retires its target (`AGENT_REVOKED`, `TARGET_RETIRED`, actor: system). With it disabled such an enrolment stays listed as `degraded` until an operator revokes the agent and retires the target. **An unused token (`pending`, or `expired`) is not swept**: it holds its target name until `revokeAgent`.
- **The staleness job** (`sm.dp.agent.staleness-job.*`): marks a silent agent's placements `unreachable` (and fires `instance.health`) once no report arrived within `sm.dp.agent.report-staleness` (five minutes by default). With it disabled a silent agent's last verdict stands. Cost of leaving it on with the gateway off: one indexed query per interval.

Both are exactly-once by construction (every move is conditional), so a second instance changes nothing; the residual is duplicated read work.

### 5. Issue an enrolment token (API)

As a principal holding `agent.enrol` **and** `target.create` at the environment, `issueAgentEnrolment` (`POST /api/cp/environments/{environmentId}/agent-enrolments`, with the CSRF token and a secure connection):

```json
{ "targetName": "host-a", "allowedConfigRoot": "/srv/cache/conf", "allowedContainerPrefix": "cache-",
  "solutionId": "<catalog id>", "packageVersion": "<a loaded version>" }
```

- **The envelope** (`allowedConfigRoot`, `allowedContainerPrefix`) is fixed by this call and **immutable**: it becomes the agent target's envelope and bounds every placement discovery registers. `allowedConfigRoot` is an absolute path (`^/([A-Za-z0-9._-]+/)*[A-Za-z0-9._-]+$`); `allowedContainerPrefix` starts alphanumeric, up to 64 characters of `[A-Za-z0-9_.-]`. A container whose config file is outside the root, or whose name does not carry the prefix, is refused `agent.discovery.outside.envelope` and not registered. Choose them narrow.
- `201` answers `{agentId, enrollmentToken, expiresAt, ...}`. **The token is shown once**, in this response and nowhere else (not in `getAgent`, `listAgents`, a log or the audit); store it where the host's operator will read it. It is single-use and valid until `expiresAt` (24 hours unless you configured otherwise).
- `409` the target name is taken by a live target or held by another pending token; `422` an envelope value fails its grammar, or `solutionId`/`packageVersion` is not a solution and loaded version of this organization; `400` a malformed body (a stray property included).
- Capabilities are **fixed by the server** (`apply-config`, `lifecycle`); they are not a body field.
- The entitlement and the instance quota are enforced when the agent's containers register, not here.

### 6. Prepare the host

The managed container opts in by **labels** and bind-mounts its configuration directory read-write:

| Label | Meaning |
|---|---|
| `com.solace.sm.instance=<name>` | opts the container in; the value is the instance's name and a part of the discovery key (see [`revoke-or-change-an-agent.md`](revoke-or-change-an-agent.md#discovery-tombstones-the-state-an-operator-watches)) |
| `com.solace.sm.config-file=<absolute path in the container>` | the config file the agent writes; it must sit under a **bind mount** (the agent writes on the host), and inside the token's `allowedConfigRoot` once mapped to the host path |
| `com.solace.sm.health-port=<port>` | optional; a **host** port. The agent's probe dials `127.0.0.1:<host port>` on the host. The Data Plane uses the label only when Docker published no host port for the package's declared probe container port. **It is not a container port**: a container port here probes the wrong port and the health is silently wrong |

Telemetry endpoints are re-mapped to the host ports Docker **published**; publish the scrape port (`-p 127.0.0.1::<port>`) or the metrics are not reachable. The container name must carry `allowedContainerPrefix`. At most 16 live placements per agent target (`SM_DP_AGENT_MAX_PLACEMENTS_PER_TARGET`); an agent reports at most 64 containers, and the Data Plane looks at no more than 256 items per report (`sm.dp.agent.max-discovery-items-per-report`), refusing the rest `agent.placement.cap`.

### 7. Start the agent (the first start enrols)

There is **no `enroll` subcommand** in `sm-agent`: the first start with a token enrols, and the identity is then stored in `--data-dir`. Pass the token through the **environment**, not a flag (argv is visible in `ps` and `docker inspect`):

```bash
SM_AGENT_ENROLL_TOKEN=<token> ./sm-agent --data-dir /var/lib/sm-agent \
  --connect-endpoint <SM_AGENT_ENDPOINT> --trust-bundle agent-ca.pem --roles control,telemetry
```

(Flags and variables: `go-agent/README.md`, "Configuration". Telemetry declarations are pushed by the Data Plane; `--telemetry-config` is an optional development seed.) On success the agent target appears in `listTargets` with `transport: agent`, and the labelled containers appear as instances in the environment (auto-registration, `OR-27`) once the agent's first discovery report has been processed (not timed here; G-A1 records it). **Restart the agent without the token**: it holds an identity and reconnects. **Never copy a data directory to a second host**: measured with the real agent, when two processes present one identity the lease nonce is single use, so the process that presents an already-used nonce is told to re-enrol and **halts** (`RE_ENROLL_REQUIRED`). Which of the two halts is a race, so the original can be the one that halts; recovering it is a re-enrolment, which creates a new agent id and new instances (see "Before an agent certificate expires").

**Where the agent runs.** The supported shape is the **binary on the host**. The agent probes the managed container's health at `127.0.0.1:<host port>` and scrapes every published port at `127.0.0.1:<published port>` (`go-agent/internal/runtime/docker`: `ScrapeAddr`, the probe URL; reasoned from the code, not run). Inside a container on Docker's default bridge network, `127.0.0.1` is the **agent container's own loopback**, so every probe and every scrape of a published port fails. A containerised agent therefore needs **host networking** (`--network host`, Linux only; Docker Desktop's host networking is **not** the supported shape). G-A1 runs the binary on the host and will not catch this; the containerised form is for T4.4 or a later gate to prove. The agent image (`go-agent/Dockerfile`, distroless, runs as user `nonroot`) also needs: the data volume at `/var/lib/sm-agent` **writable by that user** (a fresh named volume is likely root-owned: reasoned, not run), the Docker socket, the host's docker group (`--group-add`), and **each managed config directory mounted at the same absolute path it has on the host**, or every apply fails `FAILED_NO_EFFECT`.

## Verification

- `getAgent` / `listAgents`: `status` `active`, `session.state` `connected`, `session.lastSeenAt` advancing, `session.leaseExpiresAt` in the future. (A fresh token reads `pending`; a lapsed one `expired`.)
- `listTargets` shows the target with `transport: agent`.
- The instances appear in the environment; apply a configuration and confirm the file on the host equals the rendered bytes and the container restarted once (`docker inspect` start time).
- A silent agent's placements go `unreachable` within `report-staleness` plus one staleness interval.

## Before an agent certificate expires

Agent client certificates live **at most 30 days** (`SM_AGENT_CA_LEAF_TTL`, a ceiling) and **nothing renews one in place and nothing alerts before one expires**. Read from the code; none of this was run:

- **How to read the expiry.** The API does not carry it (`Agent` has no certificate field). Use `enrolledAt` from `getAgent` plus the configured lifetime as an upper bound, or on the agent host `openssl x509 -noout -enddate -in <data-dir>/identity/cert.pem` (`identity/cert.pem` under `--data-dir`, from `go-agent/internal/identity`). Put that date in your own monitoring.
- **What happens at expiry.** The agent can no longer connect and, per the T5.2 review's reading of the agent code, retries forever rather than halting. It is not told why.
- **The only procedure on this tree is the full cycle, per agent, every 30 days:** (1) `undeclareInstance` every instance the agent registered (`DELETE /api/dp/instances/{instanceId}?workload=leave-running`; the containers keep running); (2) `revokeAgent`; (3) `retireTarget`; (4) on the host stop the agent and delete its data directory; (5) `issueAgentEnrolment`; (6) start the agent with the new token.
- **Consequence.** The new agent has a new id, so every labelled container is a **new discovery key** and registers as a **new instance**: not the old instance continued, **and also the containers you had undeclared on purpose** (to keep a container out of management, remove its `com.solace.sm.instance` label). Whether history and metrics continue across the new instance was not traced. **Whether re-creating instances every 30 days is acceptable, or an in-place renewal is needed, is an owner question: plan 015 section 10, item 25.**

## A first-issue agent that never gets a lease

**Symptom.** The agent enrolled (`status` is `active`) but never shows a session, or shows `disconnected` with no `lastSeenAt` movement, and reconnects repeat. In `sm_data.agent_event` (read-only access needed) each reconnect leaves a row. Read-only:

```sql
SELECT agent_id, occurred_at FROM sm_data.agent_event
 WHERE code = 'gateway.refusal' AND detail_code = 'LEASE_RENEW_REQUIRED' AND request_id LIKE 'renewal-timeout-%'
 ORDER BY occurred_at DESC;
```

(The audit call also names the subject `agent-renewal-timeout`, but `JdbcAgentAuditRepository` does not persist the subject: the string is **not** in the table. The row is identified by the three columns above; confirmed from `AgentGatewayService` and `JdbcAgentAuditRepository`, and `GatewayCode.LEASE_RENEW_REQUIRED` having no separate wire string. Not read from a live table.)

**Why (`T3.2` review, owner-visible known limit).** The control plane's lease issuer folds the certificate-class first-issue refusals (`NOT_ENROLLED`, `CERTIFICATE_MISMATCH`, `CERTIFICATE_EXPIRED`) into one code. On a first session open the gateway cannot tell those from an ordinary race, so it asks the agent to renew; the agent has no grant to renew, and the open timeout closes it. A lost first `SessionAccept` strands an agent the same way, and routing it to `issue()` would not recover it (the lease nonce is bound to the first attempt's request id). No operator-visible reason exists beyond that audit row (`OR-141`: audit-only in v1). A distinguishing code (a change to the HF18 port set) is needed before `SessionReject(RE_ENROLL_REQUIRED)` can be sent; **it is not built**.

**Clear it: revoke and re-enrol.**
1. `revokeAgent` for the agent (it is sticky and idempotent).
2. `retireTarget` for its target (allowed after revocation even with the agent offline; the name is then free). If instances exist, `undeclareInstance` them first (`?workload=leave-running`), or it answers `409 CONFLICT`.
3. On the host: stop the agent and **delete its data directory** (a stored identity is what makes it skip enrolment), and remove nothing else.
4. `issueAgentEnrolment` again (same or a new target name), start the agent with the new token. Check the agent's certificate chain and the clock (a certificate expired, or a host clock far off, are the usual causes of the certificate-class refusals).

## Rotating a database role password and the operator tools

- `scripts/init-secrets.sh rotate all` (or one or more of `cp_migrator cp_runtime dp_migrator dp_runtime`; duplicates are collapsed, `all` takes no other arguments; a lock in the secrets directory refuses a concurrent rotation). It writes `<role>_password.next` (copying the live file's owner, group and mode), applies all named roles in **one transaction**, and only after the database accepted it replaces the live files. If it fails the live files are untouched, and **re-running `rotate` is the recovery in every case**. The superuser password is the database container's own init secret and is not rotated by this script.
- Rotating a **runtime** role leaves the running launcher holding the old password, so its new connections fail until it is recreated: `docker compose up -d --force-recreate launcher`. That is a **maintenance restart** (the console and gateway restart, with a drain); the script prints the command with a warning and **does not do it**. `migrate` reads its files on each run.
- Operator mains that read the runtime passwords from the environment (`SmControlLockoutRecoveryMain`, `BrokerConnectionMain`, `KeyRotationMain`, `TargetRegistrationMain`, `TargetConnectionMain`) no longer find them in a plain `docker compose exec launcher java ...`. Run them through the wrapper: `docker compose exec launcher /opt/sm/bin/sm-tool <main-class> [args...]`. It reads the same secret files as `sm-launcher`. On Linux the files must be group-readable by 10001 (`--group 10001`).
- Generated passwords are ASCII; do not replace a file with a non-ASCII password (the verifier is computed without SASLprep).

## Rollback

1. Set `SM_AGENT_GATEWAY_ENABLED=false` in `.env` (compose now passes it through) and recreate the container (`docker compose up -d --force-recreate launcher`). New sessions stop; no row is deleted; agents back off and retry. (The two scheduled jobs keep running; see above. Compose still requires the `certs` files and `SM_AGENT_ENDPOINT`.)
2. In-flight commands reach a terminal state or stay in `agent_command` and are re-notified when the gateway is re-enabled.
3. Roll the image back only to a version that understands the same migrations. **Do not downgrade schema state with ad-hoc SQL.**
4. To retire one agent, see [`revoke-or-change-an-agent.md`](revoke-or-change-an-agent.md).

## Limits to read before relying on this

- **One gateway replica.** No multi-replica deployment is supported or tested. Two signals reach **only the replica that holds the agent's session**: an operator `drainAgent`, and the declarations-changed push (a second replica is not told; the lease renewal is the backstop).
- Certificate rotation is manual and there is no in-place renewal (see [Before an agent certificate expires](#before-an-agent-certificate-expires)); nothing warns before an agent certificate (30 days) or the gateway certificate (365 days) expires.
- `report-only` capability is not issued (central item `AGW-12`).
- A command in flight at the moment of revocation is indeterminate.
- **`Enroll` is outside the admission limiter** (final review MINOR-6, known limit, availability only). `Connect` is rate- and count-limited before identity is resolved; `Enroll` is not, and each call costs a TLS handshake plus one control-plane transaction on the gateway's bounded gRPC pool. An unauthenticated client that floods the gateway port can slow enrolments and sessions (token entropy makes guessing irrelevant, so this is not a confidentiality risk). Keep the gateway port reachable only from the agents' network; admission for `Enroll` is not built.
- **dp-remote adapters never mark a failure as dispatched** (`afterDispatch`): only the agent adapter does, so a dp-remote lifecycle failure after a restart verb is still terminal `CONFIG_DIVERGED` (a known limit of `OR-146` (1), which is scoped to the agent adapter).
- `docker stop` of the launcher exits **143** after a clean drain; that is the JVM's signal convention, not a failure.
- The gateway's management listener (health and Prometheus text) is off unless a management port is configured; compose does not map it. When enabled it binds **127.0.0.1** by default (`SM_AGENT_GATEWAY_MANAGEMENT_BIND_ADDRESS`, default `127.0.0.1`), which a published container port cannot reach: set it to `0.0.0.0` (or the interface you need) as well as publishing the port, and keep it off the public network.
- **After a long data-plane outage an agent can take up to 5 minutes to return.** The agent backs off `min(5 min, 1 s * 2^attempt)` with full jitter, so once an outage has outlasted the first attempts the next dial is anywhere in the first 256 s to 5 min. Fleet recovery is bounded by that plus the admission limits; do not read a quiet minute after the data plane returns as a failure.
- Telemetry that an agent's clock skews beyond five minutes (the measured offset) is dropped for good and counted `clock_skew` (**plan 015 section 10, item 21**, open).

## Escalation

Backend owners for gateway and port failures; control-plane owners for enrolment or lease issuance; whoever owns the CA keystore for signing failures. Include the `agent_event` rows and the `agent_command` row of the affected command; never the token, the keystore, the password files, or any rendered configuration.
